## Clarifications needed

### C1: How should the pause length cap and its warning/auto-cancel be surfaced? (G1)
**Question**: Decision 0004 already fixes the 8-week cap, the 6-week warning email, and the 8-week auto-cancel with slot release. Should this spec add FRs for that behaviour verbatim, or does the PM want different wording/timing for this feature specifically?
**Options**: 1. Add FRs that restate decision 0004 exactly (cap, warning, auto-cancel) · 2. Reference decision 0004 by ID and add only what's pause-specific (e.g., does the 6-week warning replace or duplicate US-3's "reminder before boxes start again"?) · 3. Escalate to the founder/head of ops if the PM wants to change the ratified 8-week limit for this launch.
**Why it matters**: Without this, engineers have no source of truth for the cap/cancel behaviour and may either ship without it or reinvent it differently from decision 0004.

### C2: How does pause interact with an already-lodged Direct Debit collection? (G2)
**Question**: A customer pausing in the Thursday-lodge-to-Friday-cutoff window has money already committed via GoCardless that cannot be pulled back. What should happen?
**Options**: 1. Treat it as a refund (3-5 day turnaround), and tell the customer that in the confirmation UI · 2. Block pause requests inside that window until after the cut-off, with a clear message · 3. Let the pause take effect for the *following* box only for Direct Debit customers, mirroring the after-cut-off edge case already defined for everyone.
**Why it matters**: FR-003 as written promises no charge from the moment of request; for ~22% of the base (Direct Debit) that promise can be broken by GoCardless timing unless one of these is chosen deliberately.

### C3: Is FR-008 (send a paused box as a gift) in scope for this spec? (G3)
**Question**: FR-008 has no story, no acceptance criteria, and implies new UI the Intent section rules out. Was this meant to be included in this run?
**Options**: 1. Drop FR-008 entirely — out of scope for pause · 2. Keep it, but write it up properly as a new story next round (adds a screen, changes the UX-bearing ruling to yes) · 3. Confirm it's a mis-paste from a different concept ("gift subscription") and remove both that FR and the Out-of-scope line that references it.
**Why it matters**: As written it's unbuildable — nobody knows what "send to a friend" means operationally (address capture? notification? does the friend need an account?) — and it silently expands the UX surface the spec claims doesn't exist.

### C4: What's the actual data shape for a pause? (G5)
**Question**: Key Entities implies a history of pause records; Constraints/Technical notes implies a single boolean-plus-dates on the customer row with no history.
**Options**: 1. Boolean + dates only — accept that repeat-pause counts and "ended early" history aren't queryable later · 2. A `pauses` table (one row per pause) — supports SC-003's "measured from the subscription log" and any future repeat-pause analysis · 3. Boolean + dates now, with a lightweight audit log added later if the metrics turn out to need it.
**Why it matters**: This is a schema decision made once at build time; picking it after the fact means a migration, and it directly determines whether SC-003 can be measured as written.
