- **No files left in the spec folder** — this report is the only output, placed alongside the

## Clarifications

Each is a decision the PM (or whoever is available before Thursday) can make directly.

### C1 — How does pause interact with non-card payment methods at the cut-off boundary?
*(closes F1)*
- **Option A:** Direct Debit/PayPal customers get the same cut-off as card, but a pause
  requested after the DD lodge point (Thursday) triggers an automatic refund for that week
  instead of a suppressed charge. *Cost: a refund flow (3–5 working days) touches every
  DD pause near the boundary.*
- **Option B:** Move the DD "pause effective from" point earlier than card's, so a pause
  requested before the Thursday lodge always suppresses cleanly, and after it, the pause
  simply starts one week later than a card customer's would. *Cost: two different "effective
  from" rules by payment method, which the account page has to explain.*
- **Impact on users:** without a ruling, ~28% of the customer base (Direct Debit + PayPal)
  either get an unexpected charge the week they pause, or an unexpected refund delay.

### C2 — Should the FR list state the 8-week cap, 6-week warning, and auto-cancel from decision 0004?
*(closes F2)*
- **Option A:** Pull decision 0004's three rules into this spec's FRs verbatim (cap
  validation on the pause form, 6-week warning email, 8-week auto-cancel + slot release) so
  they're in scope for this build.
- **Option B:** Explicitly defer them to a follow-up spec, with the pause form allowing any
  length in the meantime.
- **Impact on users:** Option B means an indefinitely paused subscription holds a delivery
  slot with no cap enforced — exactly what decision 0004 was written to prevent.

### C3 — Which is authoritative: the boolean column, or the Pause record?
*(closes F3)*
- **Option A:** Keep the Pause record (as in Key Entities) as the data model; drop "boolean
  column" from Intent's Constraints — it was a simplification that doesn't hold once resume
  dates and duration tracking are required.
- **Option B:** Keep the boolean, and track dates/duration elsewhere (e.g., on the
  subscription row directly) — in which case Key Entities needs to say so instead of
  introducing a separate Pause entity.
- **Impact on users:** none directly, but this decides how much of C2's cap-tracking work is
  free versus new schema work — worth settling before Thursday's design session, since it
  changes what design has to draw.

### C4 — Is "gift a paused box" real scope for this spec?
*(closes F4)*
- **Option A:** Drop FR-008 — it isn't in any story, contradicts the "nothing delivered while
  paused" premise, and can come back as its own spec if there's real demand.
- **Option B:** Keep it, but then Overview/FR-002/FR-003 need to say a paused customer *can*
  still trigger one delivery via gifting, and a story, key entity (recipient + address), and
  screen need to exist for it.
- **Impact on users:** as written today (Option A's absence), a customer reading FR-008 would
  expect a gifting control that Overview's "nothing arrives while paused" promise says
  shouldn't exist — someone will hit this contradiction first in QA if not resolved now.

### C5 — What is SC-003 measuring against, and is the FEAT-004 relation real?
*(closes F5)*
- **Option A:** Add SC-003 to FEAT-005's verified list (it's clearly a pause outcome metric),
  and drop the "composes-with FEAT-004" relation from derivation.md until referrals is
  actually built — an unrefined feature shouldn't be a dependency surface.
- **Option B:** Keep the relation, but add an FR stating explicitly what "credits keep
  accruing while paused" means operationally, and correct derivation.md's baseline table to
  show FEAT-004 as "proposed (unrefined)," not "delivered."
- **Impact on users:** low direct impact, but the design seat will read derivation.md's
  relations as settled fact; right now one of them describes a feature that doesn't exist.

## Minor findings (log and defer)

- **SC-002** ("Customers feel in control of their subscription") has no measurement method,
  unlike SC-001 and SC-003. Fine to keep as a qualitative goal, but it shouldn't be read as a
  success criterion the team can check off — worth a one-line note on how (survey? support
  sentiment tag?) or reclassifying it out of the SC list.
- **FR-009** ("written in one database transaction") is an implementation instruction, not a
  functional requirement — it's also already covered by Technical notes. Recommend cutting it
  from Functional Requirements and leaving it in Technical notes only, so the FR list stays
  WHAT-not-HOW.
- **Story thinness** (the PM specifically asked for this): US-2 and US-4 are single-scenario
  stories with no failure-path scenario (e.g., US-2 doesn't cover "resume" on a subscription
  that's about to auto-cancel per decision 0004 — does resuming clear that countdown?). Once
  C2 is settled this will need at least one added scenario on US-2.
- Edge Cases section covers the two obvious boundary cases (cut-off timing, early resume) but
  not what happens when a resume date lands during an active single-week skip (FEAT-002) on
  the same subscription — likely rare, worth a one-line ruling rather than a full story.
