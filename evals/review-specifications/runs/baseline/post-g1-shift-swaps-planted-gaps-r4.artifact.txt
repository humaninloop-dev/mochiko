## Clarifications needed

### C1: When does an accepted swap actually change the published rota?   (G1)

**Question**: Should the rota update the moment both staff accept, or only after the venue manager approves?
**Options**: 1. The moment both staff accept — fastest, matches the Overview's "right by the time the doors open," but gives the manager no real veto before staff see the new times. 2. Only after manager approval — matches US-3's own acceptance scenario, protects licensing-sensitive shifts, but adds a wait. 3. Immediate for low-risk roles (usher), manager-gated for licensing-sensitive roles (bar, duty manager).
**Why it matters**: This decides whether US-3's manager review is a real gate or a formality, and it directly resolves the FR-004/FR-006 contradiction.

### C2: Should a swap be checked against the same eligibility flags the rota builder already enforces?   (G2)

**Question**: Should the system block or flag a swap that would put someone on a shift they're not eligible for (untrained, under 18, no alcohol sign-off, no duty-manager flag)?
**Options**: 1. Block it outright, same as the rota builder does for manager-driven placements today. 2. Allow the swap to be requested and accepted, but flag it for the manager to catch at approval (ties to C1/US-3). 3. No system check — rely on staff and managers to notice.
**Why it matters**: Decision 0003 exists because licensing inspections ask who served alcohol and whether they were signed off; a swap is a second path onto a shift that the first path (the rota builder) already guards.

### C3: Is a venue-wide broadcast offer part of shift swaps, or strictly FEAT-005's job?   (G3)

**Question**: Should the "first eligible colleague to claim it" broadcast mechanic live inside shift swaps (FEAT-006), or stay a separate, later capability (FEAT-005, Open shifts)?
**Options**: 1. Keep them strictly separate — shift-swaps is one-for-one only; FEAT-005 remains its own future feature. 2. Fold the broadcast mechanic into shift-swaps now and retire/merge FEAT-005. 3. Keep them separate features with a named relation, since both need the same claim-eligibility logic.
**Why it matters**: As staged, the spec's Intent rules broadcast offers out of scope while the map derivation writes them into FEAT-006 — the map and the spec would disagree the moment either is committed.

### C4: What ships for the UX this round — real screens, or is UX deferred?   (G4)

**Question**: Should the swap-request screen, answer screen, and manager view be mocked as a clickable prototype before this spec proceeds, or is that formally out of this run?
**Options**: 1. Author the SCR/FLOW manifest and prototype now, per the Intent's own UX-bearing ruling. 2. Formally waive UX for this round and re-open the spec once screens exist. 3. Proceed on the "designer + Figma, TBD" path with no manifest or waiver (current state).
**Why it matters**: Without a manifest or a waiver, there's no record of what was actually promised for three screens the Intent itself named — nothing for a reviewer or the prototype-authoring skill to check against.

### C5: What's the fallback when a swap notification can't reach someone by push?   (G5)

**Question**: How should a swap request reach a staff member who has no push notifications enabled?
**Options**: 1. SMS fallback, same as every other staff-notifying feature per decision 0007. 2. In-app only — accept that roughly a third of staff see it late, per staff-devices.md. 3. Escalate to the manager if the request goes unanswered past a threshold.
**Why it matters**: Decision 0007 already settled this for every other notifying feature ("every feature that notifies someone uses these channels and does not choose its own"); shift swaps doing something different is a real inconsistency, not an oversight to wave through.

### C6: Does the CSV swap-history file on the shared drive still stand?   (G6)

**Question**: Is the twelve-month CSV export the intended durable record, or does the swap_requests/rota_change audit trail (FR-007) already cover it?
**Options**: 1. Keep the CSV, and specify who can access the shared drive so staff names stay Confidential. 2. Drop the CSV constraint — the in-app audit trail already persists the same facts. 3. Keep a CSV but strip it to a summary with no staff names.
**Why it matters**: An unscoped CSV of requester/counterpart names on a shared drive risks breaching "staff personal data is Confidential ... visible to managers only" if the drive's access list is broader than the app's.

### C7: How long should an unanswered swap request stay open before it expires?   (G7)

**Question**: What's the "reasonable time" in FR-002 before an unanswered swap request auto-expires?
**Options**: 1. 24 hours, matching SC-001's measurement window exactly. 2. 48 hours, with a reminder notification partway through. 3. A per-venue configurable setting.
**Why it matters**: An expiry shorter than SC-001's window structurally caps the 80% target before it's even measured; too long, and stale requests clutter the swaps list the manager and colleagues both see.
