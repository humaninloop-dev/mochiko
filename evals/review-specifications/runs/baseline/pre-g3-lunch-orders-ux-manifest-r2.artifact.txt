# Stress-test review — spec `lunch-orders`

Reviewer: independent stress-test seat (sole reviewer, run lead unreachable). Scope: `spec.md`,
`stories/US-1..4`, `derivation.md`, `prototype/` (walked directly by opening each HTML file, no
server available). Graded against `tally/CLAUDE.md`, `tally/README.md`, `tally/docs/`,
`tally/FEATURES.md` + `.mochiko/features/*`, and `.mochiko/specs/index.md` at its committed,
run-open baseline.

This is gap-finding input for the lead's judgment, not a clearing PASS/FAIL.

## Clarifications needed before build

**1. How does a funded (free-school-meal) order get placed and charged?** *(blocks F1)*
- (a) FR-003 gets an explicit funded-meal branch: a funded order charges £0 and is placed
  without any wallet-balance check, matching FEAT-003's existing "recorded at zero" language.
- (b) Funded families are given a synthetic top-up or credit so the existing charge path works
  unmodified.
- (c) Something else the schools lead has already decided that just didn't make it into this
  spec.
Why it matters: as written, FR-003 + US-1 scenario 3 give ~59% of pupils at the pilot schools
(docs/free-school-meals.md) no way to complete an order, which defeats the count/safety purpose
FEAT-004 exists for and risks the "wallets never go negative" floor either way it's forced
through.

**2. Should parents ever see a hidden menu item?** *(blocks F2)*
- (a) FR-002 is wrong; parents must never see a hidden item, matching menu-admin's shipped
  FR-002 — hidden stays kitchen-only, always.
- (b) "Hidden" in this spec means something narrower than menu-admin's hidden (e.g., a
  different flag) and the spec needs its own term.
- (c) The menu-admin rule needs to change, and that's a decision for the schools lead + catering
  contractor, not something this spec silently overrides.
Why it matters: hiding exists for recalls and safety; showing a hidden item to parents through
this feature would reopen the exact hazard menu-admin was built to close.

**3. Is the Google Sheet the real menu source, or was that constraint invented?** *(blocks F11)*
- (a) Confirm the Sheet is real and add the ADR that's currently missing from `docs/decisions/`.
- (b) Drop the Sheet constraint; the menu already lives in Postgres per the delivered FEAT-002,
  and FR-006 should describe writing orders to wherever the kitchen already reads counts from.
Why it matters: FR-006 commits to a specific integration (five-minute Sheets-API sync) that
isn't corroborated anywhere else in the product's documented stack.

**4. What should the prototype show for change/cancel and for an underfunded order?**
*(blocks F5, F6, F7)*
- (a) Add SCR-004 and a confirmation screen, plus flows for US-2 and the insufficient-balance
  case, before this goes further.
- (b) These are deliberately deferred/out of scope for the prototype pass and the manifest
  should say so explicitly rather than leaving dead links and silent gaps.
Why it matters: two of the four stories (one of them P1) and the one edge case that touches
money can't currently be walked or verified against the mock at all.

## Feature-layer summary

- FEAT-005 (new, proposed) — traceable to US-1/US-2/US-4 except for the untraced rating bullet
  (F4); over-wide extent (F13); introduces an unprecedented "Relations" section.
- FEAT-006 (new, proposed, deferred) — clean, minimal, traceable to US-3. No issues found.
- FEAT-003 (delta) — illegal status regression from `delivered` to `proposed` (F3); the
  underlying rework (charge-at-order-time) itself is legitimate and correctly flagged as
  touching a delivered capability, just via the wrong mechanism.
- Specs-index draft row is internally consistent with the derived-features table (FEAT-005,
  FEAT-006, FEAT-003) — no drift found there.

## Screens & Flows summary

Two of four manifest screens don't exist as built (SCR-004 missing, plus an unlisted
confirmation screen the flow needs); one built screen (SCR-005) isn't in the manifest; one P1
story (US-2) has zero flow coverage; one flow (FLOW-003) cites a scenario that doesn't exist;
the one flow that does depict the underfunded-wallet case contradicts its own source scenario.
The prototype cannot currently be walked end-to-end for either P1 story.

## Strengths

The allergen-blocking flow (US-4 / SCR-001 / FLOW-003 mechanics, traceability citation aside) is
the one path that's fully thought through end-to-end — disabled radio inputs, per-child
re-filtering, and a supporting allergen-key screen — and it's the story the schools adopted
pre-ordering for in the first place.

## Recommended verdict

**Not ready to build.** Five critical findings (F1–F5, extending to F10) sit on the product's
core safety and money paths (funded meals, hidden-item safety, wallet accounting, a walkable
change/cancel journey) and on the map delta the lead is being asked to ratify. Recommend a
revision pass on spec.md + derivation.md + the prototype manifest before this leaves
stress-test.
