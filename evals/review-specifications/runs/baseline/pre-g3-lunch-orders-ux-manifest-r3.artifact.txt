## Clarifications

**C1 — Funded (free-school-meal) pupils: in or out of this run?** *(blocks F1)*
The spec's charging model has no path for a £0-cost, no-card order, yet ~59% of pupils at the
pilot schools are fully or partially funded and the wallet governance principle names this case
by name.
- **Option A — In scope now:** add a funded-meal branch (FR + story + screen state) where a
  flagged child's order charges £0 and is claimed by the school, matching FEAT-003's existing
  "recorded at zero, claimed by the school" language. Larger for this run, but ships the
  majority-affecting path.
- **Option B — Explicitly deferred:** state in Intent/Out-of-scope that funded meals are out of
  this run, and that funded families cannot order lunches through Tally until a follow-up spec
  — with a named owner/date for that follow-up.
- **Option C — Assumption stands, scoped down:** keep "every family has a card on file" but
  restrict this spec's claimed rollout to schools/cohorts with no funded pupils, and say so
  plainly, so the 95%-by-cutoff SC-001 isn't silently measured against a population it can't
  serve.
Why it matters: as written, the two pilot schools this release targets are the reference
population, and both have large funded cohorts per docs/free-school-meals.md — silence here
ships a blocking bug on day one, not an edge case.

**C2 — Hidden items: visible to parents, or never?** *(blocks F2)*
Two accepted-or-accepting artifacts disagree on the single most safety-relevant rule in the
menu.
- **Option A — menu-admin's rule wins:** drop lunch-orders FR-002's "including items marked
  hidden" clause; parents simply never see hidden items, full stop.
- **Option B — lunch-orders' rule wins:** hidden items should in fact reach parents (e.g., as a
  greyed "unavailable" row) and menu-admin's FR-002/SC-001 need to be revisited/escalated.
- **Option C — Split concept:** "hidden" (kitchen-only, invisible to parents — menu-admin) and
  a separate "sold out today" state (visible-but-unselectable, which is what lunch-orders may
  actually have meant) are two different things and need two different names.
Why it matters: menu-admin's own rationale is a supplier recall — Option B would reintroduce
the exact safety failure that spec was built to close.

**C3 — Cut-off time for order changes: which one?** *(blocks F4)*
- **Option A:** Thursday 17:00 the week before (FR-005, the ratified decision doc) is correct;
  fix US-1 scenario 2's wording.
- **Option B:** there's a second, later soft deadline for in-week tweaks that the decision
  record doesn't capture, and both FR-005 and the decision doc need updating.
Why it matters: the cut-off is the one rule the kitchen's stock order depends on directly
(docs/decisions/0003); an implementation built off the story text alone enforces the wrong
deadline.

**C4 — Is "change or cancel an order" (US-2) actually being built this run?** *(blocks F5)*
It is a P1 story with FRs (FR-004) but zero screens or flows.
- **Option A:** add the missing screen(s)/flow now — it's P1 and money-bearing.
- **Option B:** confirm the change/cancel action is meant to ride on the existing SCR-001 (e.g.,
  re-opening the week menu after confirmation) and add that FLOW row explicitly, rather than
  leaving it unspecified.

## Recommended verdict

**Not ready — send back for revision.** Two findings (F1, F2) are not polish: F1 means the
charging model as specified cannot serve the majority-funded pupil population the pilot
schools represent, and F2 means the spec's own FR contradicts an already-accepted, safety-
motivated sibling spec. F3–F8 compound this with map-legality and prototype-walkability
failures on the run's own P1 flows. None of these are a quick copy-edit; each changes what gets
built (F1, F2) or what gets shown as evidence that it works (F5, F6, F8).

**strengths:** Allergen-blocking (US-4/FLOW-003) is genuinely well specified and the prototype
demonstrates it convincingly — SCR-001's per-child, per-item strike-through with the allergen
name inline is exactly the kind of concrete, walkable evidence this review process is for.
