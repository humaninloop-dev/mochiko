# Spec review — lunch-orders (stress-test pass)

Reviewer: independent gap-finding pass (`mochiko:review-specifications`), author of nothing under
review. Baseline: `tally/FEATURES.md`, `tally/.mochiko/features/*`, and
`tally/.mochiko/specs/index.md` exactly as committed at run open (git state = current state;
nothing committed since). This is gap-finding input for the lead's ruling, not a clearing
PASS/FAIL verdict.

**Prototype walk method:** the prototype is a static, unserved mock (its own `README.md` says to
open `index.html` directly — no server needed, and none could be started from this session
regardless). I opened and traced every `.html` file under `prototype/` and every `href` in it
against the Screens & Flows manifest, link by link, in the adversarial spirit of "click it" — this
surfaces the structural defects below (dead links, missing pages, unreachable P1 scenarios) as
reliably as a browser would; only visual/layout rendering was not observed, and per the
prototype's authority split that layer is advisory only.

## Clarifications (decisions for the stakeholder)

1. **Funded (free-school-meal) orders — how should checkout behave?**
   - **A.** Funded children order through a separate zero-charge path (no card/balance check),
     matching FEAT-003's existing "recorded at zero, claimed by the school" behavior.
   - **B.** All families go through the same wallet-charge path, and schools must pre-load a
     zero-liability wallet for every funded child before ordering opens.
   - **C.** Something else specific to how the pilot schools currently handle this on paper.
   - *Impact:* at 41%+18% of pupils potentially funded, picking wrong blocks a large share of
     families from ordering at all on day one.

2. **Should parents see menu items the kitchen has hidden?**
   - **A.** No — align lunch-orders FR-002 with FEAT-002/menu-admin: hidden items never reach a
     parent, full stop.
   - **B.** Yes, but only in a clearly "unavailable" state (e.g. greyed, not orderable) — a
     narrower requirement than either spec currently states.
   - **C.** Escalate to whoever owns both specs; treat the current state as blocking until then.
   - *Impact:* one of the two in-flight specs must change before either can ship safely.

3. **What happens when the wallet doesn't cover the order?**
   - **A.** Block "Pay" and route to a top-up screen, per US-1 scenario 3, with the order held
     until funded.
   - **B.** Allow partial confirmation (fund what the balance covers, hold the rest for
     follow-up).
   - **C.** Something else — but the prototype's own numbers (£9.10 wallet vs £9.70 order) need
     to route somewhere other than a plain enabled "Pay" button.
   - *Impact:* directly enforces (or violates) the "wallets never go negative" floor principle.

4. **Is "order history" a new capability (FEAT-006) or an extent of ordering (FEAT-005)?**
   - **A.** Keep FEAT-006 separate, as staged — it's a distinct read-only surface.
   - **B.** Fold it into FEAT-005's extent as a viewing capability of the same feature.
   - *Impact:* minor either way, but affects whether the map grows to 6 entries or stays at 5
     for this run; worth a deliberate call rather than a default.

prototype — SCR-001 correctly disables and marks every milk-containing item for the allergic
child and correctly changes marks when switching children — the one flow that fully holds up
under a click-through.
