## Note on the handoff asks

`HANDOFF.md` asked for several things I did not fully accommodate, and I want that visible
rather than silently applied or silently ignored:

- **"Skip the story files"** — I read all four. The feature-layer checks (derivation honesty,
  disposition completeness, SC re-homing) can only be done by reading the stories, and the
  handoff's own ask #4 ("flag anything that reads thin") requires the same thing — the two asks
  are in tension with each other. Reading them surfaced a real finding (derivation.md
  misstates a map-baseline status — see Critical #5) that isn't visible from `spec.md` alone.
- **"Keep severities proportionate... anything engineers can sort out during the build is a
  Minor"** — I classified by the stated rule (Critical = cannot build without the answer)
  rather than by what's convenient for today's approval. Several items below are Critical
  because they concern money movement, an already-ratified decision the spec omits, and a
  requirement with no traceable source — none of that is a during-build cleanup.
- **"Add 'skip a single week' as a missing requirement"** — I did not add it. It's already
  delivered (`FEAT-002`, closed spec `skip-a-week`, 2026-01-26 → 2026-02-16), the spec's own
  derivation correctly rejects US-4 on exactly that basis, and adding it back as a "gap" in
  this spec would be scope creep dressed as a finding, not a real gap in pause-subscription.
  If customers are still asking for it, that's a signal the delivered feature isn't
  discoverable or doesn't match expectations — worth a ticket, but against FEAT-002, not a
  requirement to bolt onto this spec.
- **Wording tightening in `spec.md` / `spec-revised.md`** — I looked for sentences that were
  purely a phrasing problem. I didn't find any: every sentence I flagged below turned out to
  be carrying a substantive gap (a false premise, an undecided cap, an unsourced requirement),
  and tightening the prose would either paper over the gap or require me to make the product
  call myself. I've left `spec.md` and `stories/` untouched rather than pre-empt those calls.
  Once the Critical items are resolved, the Overview's payment sentence, "without losing
  anything," and FR-004's "soon after" will all need a wording pass — noted inline below.
- **"No review files in the spec folder"** — this report lives at `review.md` outside
  `bramble/` entirely, so nothing is added to the spec workspace.

## Clarifications needed

1. **Non-card payment methods during pause (F1)** — Options: (a) block pause requests placed
   between DD lodgment (Thursday) and cut-off (Friday) until the following cycle, showing the
   customer why; (b) allow the pause and issue a refund for any DD/PayPal collection already
   in flight, accepting the 3–5 working day refund lag from docs/payment-methods.md; (c) treat
   DD/PayPal identically to card and accept FR-003 will occasionally be violated by one cycle.
   Why it matters: FR-003 is currently a promise the system can't always keep for 28% of
   customers, and the three options have very different support-load and trust consequences.

2. **Folding in decision 0004 (F2)** — Options: (a) add FRs for the 8-week cap, 6-week
   warning email, and 8-week auto-cancel + slot release directly into this spec; (b) treat
   0004 as already covering the cap and scope this spec to explicitly exclude it, with a
   cross-reference instead of duplicate FRs. Why it matters: without one of these, "how long
   can a pause be" ships as an open question in a spec meant for design on Thursday, and the
   account page can't show a countdown or a cap warning without picking one.

3. **FR-008 gift-while-paused (F4)** — Options: (a) confirm it's in scope and add a story,
   acceptance scenario, and entity fields for it; (b) remove it as an authoring error/no
   accountable source. Why it matters: it's the only requirement in the document with no
   traceable origin, and either answer changes the FR count design will build against.

4. **Screens & Flows waiver (F11)** — Options: (a) keep the waiver as-is, accepting the
   pause/resume states are simple enough to build from the FRs alone; (b) produce a low-fi
   prototype of the account page's paused/active states and the reminder-email landing, since
   three separate stories touch it. Why it matters: this is exactly the kind of "control on an
   existing page" that's cheap to mock and expensive to redesign after build if the states
   don't compose cleanly.

## Recommended verdict

**needs-revision** — not a clearing PASS. Six Critical items (F1–F6) each land in "cannot
build without this answer": one is a functional promise (FR-003) the system cannot keep as
written for non-card customers, one is a ratified decision the spec silently drops, one is an
internal data-model contradiction, one is an untraceable requirement, one is a factual error
in the map-baseline snapshot that props up a cross-feature claim, and one is a success
criterion with no owner. None of these are the kind of thing "engineers can sort out during
the build" — each is a product decision or a correction to a factual claim the spec makes
about the world.

strengths: FR-007's payment-detail requirement is a clean example of a governance-sourced FR done right — sourced, testable, and traced straight to a stated principle.
