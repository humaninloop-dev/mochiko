## Clarifications

1. **When does an accepted swap actually change the published rota?**
   - **A. Immediately on mutual acceptance** (FR-004, matches US-1's acceptance test) —
     fastest for staff, but skips the manager check US-3 exists for, and skips whatever
     eligibility/licensing check F2 raises.
   - **B. Only after manager approval** (FR-006, matches US-3) — matches the "high rigor"
     framing, but US-1 and US-2's acceptance scenarios need rewriting, since they currently
     promise an immediate rota change.
   - **C. Immediate for low-risk swaps (e.g. usher-usher), manager-gated for licensed roles
     (bar, duty manager)** — matches "touches pay and licensing" without slowing every
     swap down, but introduces a role-based branch nothing in the spec currently models.
   - Why it matters: this single decision reshapes the state machine, FEAT-001's delta
     acceptance criteria, and which of US-1/US-2/US-3's acceptance scenarios are correct.

2. **Should a swap request enforce the same eligibility, availability, and time-off checks
   the rota builder already applies?**
   - **A. Yes, reuse the existing checks** — hard-refuse an ineligible or blocked swap the
     way the rota builder refuses an ineligible placement today.
   - **B. No, trust the swap participants and let manager approval (US-3) catch problems**
     — matches the current Assumptions line, but only if F1 resolves to "manager gates
     every swap"; leaves a gap if F1 resolves to "immediate on acceptance."
   - **C. Warn, don't block** — mirror FEAT-002's "it flags, the manager decides" pattern
     for availability, while still hard-refusing on the 0003 eligibility flags (age,
     sign-off, till-training) the way placements already do.
   - Why it matters: decision 0003 already hard-refuses ineligible placements for
     licensing reasons; a swap that routes around it is a live compliance exposure, not a
     hypothetical one.

3. **Is "offer a shift to everyone, first to claim" part of shift-swaps (FEAT-006) or of
   Open shifts (FEAT-005)?**
   - **A. Drop it from FEAT-006** — shift-swaps stays a named-colleague exchange, matching
     every story it actually has; FEAT-005 keeps owning any first-claim mechanic.
   - **B. Fold FEAT-005 into FEAT-006** — but this needs its own stories, since none exist
     in this spec, and a ruling on why one capability should own both shapes.
   - **C. It's a drafting slip** — remove the line from the proposed FEAT-006 entry;
     FEAT-005 stays untouched and unrefined for a later run.
   - Why it matters: FEAT-005 already exists on the map with near-identical wording; the
     derivation's own baseline table doesn't list it, so this overlap wasn't caught by the
     dedup step it should have been caught by.

4. **Where does SC-002 belong, and how should SC-003 be measured?**
   - **A. Home SC-002 to FEAT-006** (manager admin time is a direct effect of the
     request/answer flow); replace SC-003's "intuitive" with a scored post-launch survey
     threshold.
   - **B. Home SC-002 to the FEAT-001 delta** (it's measuring the manager-facing rota
     surface); drop SC-003 or replace it with a support-ticket-volume threshold.
   - **C. Treat SC-002 as a product-level outcome outside any single feature's obligations,
     tracked on `specs/index.md` rather than the Feature Selection table.**
   - Why it matters: an unhomed SC has nothing checking it after launch; an unmeasurable
     SC can never be marked met or missed either way.

5. **What UX artifact ships with this spec, given Intent already says UX-bearing: yes?**
   - **A. Author the SCR/FLOW manifest and a clickable low-fi prototype now**, before the
     spec is called ready, covering the request, answer, and manager-approval screens.
   - **B. Add the explicit waiver line** ("No UX surface — prototype waived at intent") if
     the team has since decided against prototyping — this also means correcting Intent's
     "UX-bearing: yes."
   - **C. Leave "designer mocks it after approval,"** and treat this spec as not yet
     ready for build sign-off until that mock exists.
   - Why it matters: right now the spec is in neither of the two states a UX-bearing spec
     is allowed to be in, so nothing has walked the three screens this feature depends on.

6. **Which notification channel does a swap event actually use?**
   - **A. Follow decision 0007 exactly** (push if enabled, else SMS, else flag to manager)
     for every swap event, and rewrite the Overview's "every staff member has push on"
     claim against the 2026 device survey.
   - **B. Push-only for swaps**, accepting that SC-001's 24-hour answer target will run
     slower than the Overview currently promises.
   - **C. SMS for the initial request (time-critical), push for everything else** —
     matches staff-devices.md's own reading ("anything time-critical goes by SMS as well").
   - Why it matters: the spec's headline claim ("reaches its counterpart within seconds")
     and SC-001's target both depend on a reach rate the team's own survey says isn't real.

## Strengths

The core request/answer/history story set (US-1 through US-4) is well-scoped and each
carries a concrete independent test; the explicit exclusion of cross-venue swaps (US-5) is
a clean, well-justified cut against the Regal-pilot reality.

## Recommended verdict

**needs-revision** — five Critical findings (F1-F5) touch the swap state machine, safety
checks the rest of the product already relies on, feature-map dedup, and the UX gate; none
of these are polish-level and none should be resolved by the implementer's judgment call.
