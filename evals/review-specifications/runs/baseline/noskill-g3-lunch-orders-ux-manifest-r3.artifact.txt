# Stress-test review — spec `lunch-orders`

Scope reviewed: `tally/.mochiko/specs/lunch-orders/{spec.md,derivation.md,stories/,prototype/}`
against `tally/CLAUDE.md`, `tally/README.md`, `tally/docs/**`, `tally/FEATURES.md`,
`tally/.mochiko/features/*`, and `tally/.mochiko/specs/index.md` as committed at run open
(2026-09-03). No code exists yet; this is a paper/prototype review only.

**Verdict: not ready to leave draft.** Two of the findings below are safety- or
money-critical and touch the product's stated non-negotiables (child safety, wallets never
negative). One breaks an already-accepted sibling spec outright. Recommend the run goes back
through requirements/derivation before `lunch-orders` is accepted.

---

## Critical — safety, money, or governance breaking

### C1. The one hard safety rule has no Functional Requirement behind it

US-4 (`stories/US-4.md`) and the prototype (`scr-001-week-menu.html`, disabled radios marked
"not for Ada") both show allergen-containing items **blocked from selection** for a child with
that recorded allergy. `derivation.md`'s proposed FEAT-005 extent says the same: "an item
containing a recorded allergen cannot be ordered for that child."

But `spec.md`'s Functional Requirements list has no such rule. FR-007 only requires that
allergen information be *shown* ("MUST show allergen information for every item before it can
be ordered") — it never requires the system to *refuse* an unsafe selection. Nothing else in
the FR list (FR-001 through FR-010) covers it either.

The FR list is the part of a spec meant to be handed to an implementer as the binding contract.
As written, an implementation that shows every allergen honestly but lets a parent tap "order"
on a milk item for a milk-allergic child would satisfy every FR in the document — and would be
exactly the failure mode US-4's own rationale calls out: *"the kitchen must never receive an
unsafe order."* This is the single most consequential gap in the spec: add an explicit FR
("the system MUST refuse to add an item containing a child's recorded allergen to that child's
order") before this goes anywhere near build.

### C2. FR-002 re-exposes hidden items that a sibling spec just hid

`spec.md` FR-002: *"The parent MUST see the whole published menu for the week, **including
items the kitchen has marked hidden**, so that nothing on offer is missed."*

`menu-admin/spec.md` FR-002 (accepted 2026-08-29, `FEAT-002` row `live`, currently in-flight):
*"A hidden item MUST NOT appear in any parent-facing screen or response, including a week's
menu a parent has already opened."* Its SC-001 is enforced by a contract suite on every deploy,
and `menu-admin`'s Overview states the reason: a hidden item is "a supplier recall, a short
delivery" — i.e. food that may not be available or safe to serve.

These two FRs are direct opposites over the same data. `derivation.md`'s own Relations section
declares `FEAT-005 depends-on FEAT-002`, so this isn't an incidental overlap — the author took
a direct dependency on a capability whose current in-flight delta they contradicted. See D1
below for the likely cause. This must be resolved (almost certainly by deleting the "including
hidden items" clause) before FR-002 goes further.

### C3. The core payment assumption is contradicted by documented school facts

`spec.md`'s Assumptions: *"Every family has a card on file, so every order is charged at
placement."* FR-003 charges the wallet unconditionally at confirmation with no other path.

`docs/free-school-meals.md` — a file `README.md` explicitly flags as a school fact that "keeps
coming up" — says the opposite: 41% of pupils (all Reception/Y1/Y2) get a universally free
lunch, a further 18% of KS2 pupils get means-tested free meals, and *"many of these families
have no card on file and no wallet balance, and some have never topped up."* It also states
plainly: *"A funded child still needs an order placed so the kitchen has a count and the
allergy flag."*

So roughly half the pupils at a pilot school cannot go through the flow this spec describes:
FR-001 requires they be able to place an order, but FR-003's unconditional charge, against a
wallet that governance requires can never go negative ("the order service refuses an order it
cannot fund"), means a funded child with no balance and no card either can't order at all or
breaks the "wallets never go negative" invariant. `FEAT-003`'s own doc already describes the
correct shape — *"A funded child's meals are recorded at zero for the family and claimed by
the school"* — but nothing in `spec.md`'s FRs, Key Entities, or Screens references funded/zero
-charge orders at all. This isn't a missing edge case, it's a missing path for a majority-sized
population the product already special-cases elsewhere. Notably, the prototype's own example
family includes a Reception pupil (Tobi Okafor, `scr-002-child-picker.html`) — exactly the
population this gap affects — and the prototype never demonstrates ordering for him.

### C4. The spec contradicts its own cut-off inside a single acceptance scenario

`stories/US-1.md`, Acceptance Scenario 2: *"the parent changes Tuesday's meal **before Sunday
midnight**."* `spec.md` FR-005 and `docs/decisions/0003-order-cutoff.md` both fix the cut-off
at **17:00 the Thursday of the week before** — i.e. before the order week has even started, let
alone reached Sunday. By the time "Sunday midnight" arrives the week is already three days into
being locked per FR-005, and per governance's "Counts are final at the cut-off" principle the
kitchen has already bought food against those counts. This acceptance scenario describes and
implicitly certifies behaviour the spec's own requirement forbids two sections later. It reads
as leftover text from an earlier (rejected) cut-off design that wasn't swept from the story file
when 0003 was adopted.

## Major — rigor and consistency

### M1. Allergy-safe ordering flow is traced to the wrong story, to a scenario that doesn't exist

`spec.md`'s Flows table: `FLOW-003 | Order for a child with an allergy | ... | US-3 / scenario
3 | —`. The allergy story is **US-4**, not US-3. US-3 ("See what my children are having...")
has only two acceptance scenarios, so "scenario 3" doesn't exist under either reading. This is
the traceability link for the spec's single safety-critical flow, and it points nowhere real.

### M2. The menu's source of truth is asserted two incompatible ways

`spec.md` Intent constraints: *"the kitchen's weekly menu is a Google Sheet the catering
manager edits; orders are written back into a second tab of that sheet."* But `menu-admin/spec.md`
(in-flight, accepted) describes "a toggle on the **existing kitchen menu screen**" and a
parent-facing menu served from a contract-tested API — i.e. the menu already lives in the
product's own database, authored through the app, not a spreadsheet. No file under
`docs/decisions/` records a Google Sheets integration decision. Either the menu is
app-authored (as `menu-admin` and `FEAT-002` clearly assume) or it's spreadsheet-authored (as
this spec's Intent claims) — it cannot be both, and nothing in this spec reconciles them. This
also undermines FR-006 ("orders MUST be written... through the Sheets API") and the Technical
notes' Redis-cached "week's menu," which only makes sense if the menu is already in the app. If
a spreadsheet hand-off is genuinely still in use for kitchen ordering, that needs to be a cited
decision, not an unsupported Intent-section assertion inherited into a P1 functional
requirement.

### M3. The prototype doesn't actually walk the flows it's built to demonstrate

- `index.html` and every screen's nav bar link to `screens/scr-004-order-history.html` — this
  file does not exist in `prototype/screens/`. Every "Order history" link in the mock 404s.
- `scr-003-order-summary.html`'s "Pay £9.70" button links to `scr-006-confirmation.html` —
  also does not exist, and SCR-006 appears nowhere in `spec.md`'s Screens table at all (the
  Screens & Flows section never names a confirmation screen, despite FLOW-001 ending in "→
  confirmation").
- `scr-005-allergens.html` exists and is linked from every page, but SCR-005 is not in
  `spec.md`'s Screens table — an undocumented screen.

Between these, there is no path through the prototype that reaches a working confirmation or
order-history screen. For a spec whose Screens & Flows section exists specifically to be
walked before build, that's the artifact failing at its one job.

### M4. The prototype's own numbers stage an insufficient-funds case and then skip it

`scr-001-week-menu.html`/`index.html` show wallet balance **£9.10**; `scr-003-order-summary.html`
totals the same week at **£9.70**. That's exactly the case US-1's Acceptance Scenario 3 covers
("the wallet holds less than the order total... they are asked to top up and the order is held
until they do") — and exactly the case governance's "wallets never go negative" principle
exists for. But the mock's "Pay £9.70" button goes straight toward a confirmation page (which,
per M3, doesn't exist) with no top-up prompt shown anywhere. Either the numbers were picked
without noticing they under-fund the order, or the mock is silently skipping the one behaviour
this exact scenario is supposed to exercise.

### M5. Derivation's baseline snapshot of the map looks stale, and it explains C2

`derivation.md`'s "Map at baseline" table (read 2026-09-05, run opened 2026-09-03) lists
`FEAT-002 | Menu publishing | delivered`. The live `FEATURES.md`/`.mochiko/specs/index.md` show
FEAT-002 as **in-flight since 2026-08-25** — before this run even opened — with a linked
in-flight spec (`menu-admin`) whose whole point is hiding items from parents. If the author's
derivation genuinely believed FEAT-002 was fully delivered and static, that would explain how
FR-002 ended up flatly contradicting a change that was already underway on the same capability
the new feature declares a dependency on (C2). Worth checking whether the baseline read simply
missed the in-flight row, since the same blind spot could recur on `FEAT-004` (proposed,
unrefined) if a future run assumes it doesn't exist yet either.

### M6. FR-008 is worded as an absolute that contradicts governance's own carve-out

FR-008: *"A child's dietary and allergy details MUST never appear on a screen unless that
child's parent is signed in."* Governance's Confidential-data principle explicitly carves out
a second legitimate viewer: *"the kitchen sees per-day counts and allergy flags by first name
and class."* FR-008 as literally written forbids that. It's almost certainly meant to say
"...on a **parent-facing** screen," but as written it will directly conflict with `FEAT-004`
(Kitchen counts) once that's built. Worth tightening now rather than inheriting the ambiguity.

### M7. Intent's delivery strategy contradicts the Feature Selection

Intent states *"Delivery: whole feature in one run."* Feature Selection then explicitly defers
FEAT-006 (order history, carrying US-3) to a later run. These two statements about the same
spec disagree about whether US-3/SCR-004/FLOW-002 ship with this work or not — and per M3, the
prototype was built as though they do (the order-history link is on every page), while the
Selection table says they don't. Pick one and make the rest of the document agree.

## Minor

- **FR-009** ("Parents MUST be able to rate each meal after it has been eaten") has no source
  story (`Source: —`), no screen, no flow, no Key Entity, and falls outside the Intent's stated
  scope boundary (ordering, changing, paying for lunches). It reads as scope creep that slipped
  past the story-to-requirement discipline the rest of the document follows. Either trace it to
  a real story or drop it.
- **SC-002** ("Parents find ordering easy") has no measurement method, unlike SC-001/003/004
  which all name one. Unmeasurable as written.
- **FR-010** ("The menu MUST load fast") is untestable on its own; the actual number (p95 <
  400 ms) is buried in Technical notes and never linked back to FR-010 or to a success
  criterion.
- The mid-week-leaver edge case ("remaining orders that week are credited to the wallet") isn't
  reconciled with `docs/decisions/0003`'s stated process for leavers (school office phones the
  kitchen). Unclear whether the wallet credit is automatic system behaviour or part of that
  manual call — worth one line to say which.
- `prototype/screens/scr-001-week-menu.html` includes a "Lorem ipsum · £0.00" placeholder row
  for Friday that was left in rather than filled with a real example meal — harmless, but it's
  the row nearest the export/demo path and worth a pass before anyone screenshots it.

---

## What's solid

- FR-004/FR-005 (change/cancel until cut-off, cut-off refusal with reason) correctly mirror
  `docs/decisions/0003` when read on their own.
- US-2's acceptance scenarios (unlike US-1's) get the cut-off right.
- Key Entities and the wallet-delta in `derivation.md` (FEAT-003 dropping back to `proposed`
  while it's reworked to charge at order time) are a sensible, well-justified piece of feature
  bookkeeping given this is the first-ever electronic ordering path replacing paper slips.
- The allergen-key screen (SCR-005, even though undocumented in the table — see M3) correctly
  lists all fourteen UK-regulated allergens, matching the "fourteen allergens" language in
  `FEAT-002`.

---

## Recommendation

Do not carry FR-002, the missing allergen-block FR, or the funded-meal gap forward into
derivation as-is — C1–C3 each touch a stated non-negotiable (safety, wallet invariant) and C2
breaks a spec that's already been accepted and is currently in-flight. Fix C1–C4 and M1 in the
spec text, resolve M2's architecture question with whoever owns the menu-admin/menu-basics
history before committing to FR-006, and rebuild the prototype's broken links (M3) so it can
actually be walked end to end before this spec leaves draft.
