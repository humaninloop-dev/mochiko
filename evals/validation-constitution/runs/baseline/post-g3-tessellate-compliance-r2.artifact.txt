**Issues requiring fix:**

### Critical

1. **`.mochiko/memory/governance-ledger.md` Waivers table, GI-012 — a legal-mandate module obligation is waived.** The pci-dss quarterly ASV scan (Requirement 11.3.2) is waived "until first paying customer." Per `COMPLIANCE-MODULES.md`: legal-mandate obligations are unwaivable (D4.2) — "a recorded permanent waiver of a legal control is documented evidence of a knowing violation, not an escape valve." The ledger's own Waivers section header states this in writing directly above the offending row: *"a waiver row naming one is a validator FAIL."* The synthesis's own review already flagged this as Critical (S1) and the founder overruled it — that overrule does not bind this validator; the checklist item ("No waiver names a legal-mandate module obligation") is unconditional. **Fix: remove the GI-012 waiver row entirely; the ASV scan obligation stands unwaived, or the compliance posture (get the first scan done, or contract it out pre-launch) has to change instead of the governance.**

   1a. **Compounding numeric error, GI-005 (Testing Discipline)** — CLAUDE.md and the ledger both assert coverage "≥80% warning, ≥70% blocking." The floor card (`universal-floor.md`, FLOOR-TEST, high row) and the ratified synthesis's own Floor expression table both say **≥60% blocking**, "no session override." No session override is recorded anywhere in the synthesis. The landed 70% figure has no basis in the ratified set. **Fix: correct both CLAUDE.md's principle line and ledger GI-005's Enforcement/Testability sections to 60% blocking, or get a session override recorded in governance-intent.md if 70% was actually intended.**

2. **CLAUDE.md region + ledger, GI-016 (British English) — principle contradicts a ratified deliberate exclusion.** `governance-intent.md`'s "Deliberate exclusions" section states explicitly: *"GI-016 — Documentation language and style are not governed... nobody is going to police it (Inês)."* Yet CLAUDE.md carries a NON-optional principle — "All internal documentation MUST be written in British English" — and the ledger carries a full Three-Part record enforcing it via `cspell`. This is not a fidelity nuance; it is the opposite ruling from what was ratified. Per the Traceability checklist, a trace must point at a principle-bearing element, "not a waiver, exclusion, or template-module row" — GI-016 is explicitly recorded as an exclusion. **Fix: delete the GI-016 principle from CLAUDE.md, delete its ledger Three-Part record, and delete the `cspell` gate if one was wired in for it. If the team's position has genuinely changed since ratification, that is an amendment to run through `/mochiko:setup` amend mode, not a silent insertion.**

3. **`.claude/rules/mochiko/cardholder-data.md` — `paths` scope excludes the checkout handler where the PAN actually enters the system.** The file scopes to `src/payments/**/*.ts` only. But GI-001's fact profile and GI-009's own ledger entry both state the PAN "passes through Tessellate's own checkout handler (`src/checkout/`) before the Adyen tokeniser in `src/payments/`," and the scope is explicitly written as **"`src/checkout/` and `src/payments/`, the two modules the PAN transits."** The synthesis review already caught and "resolved" this exact gap once (S2: "The PCI scope named `src/payments/` only; the PAN transits `src/checkout/` first" → "resolved — scope widened in the element text above") — the widened scope made it into the ledger's prose but never into the rules file's `paths` glob. As shipped, no rules-file injection fires when an agent creates or edits code in `src/checkout/`, the exact module handling raw PAN data pre-tokenization. This is a live gap in a PCI-DSS control on a card-payment product two weeks from launch. **Fix: add `src/checkout/**/*.ts` to the `paths` frontmatter.**

4. **CLAUDE.md + ledger, GI-011 (Fast Pages) — vague, unenforceable, and discards the ratified content.** CLAUDE.md: "Pages SHOULD load quickly." Ledger: Enforcement "Engineers watch the Lighthouse scores"; Testability "Pass: pages feel quick. Fail: complaints." The ratified synthesis specifies a concrete, numeric minted principle: *"Largest Contentful Paint at or under 2.5 seconds at the 75th percentile on the product page and the checkout, measured by Lighthouse CI on every PR; a regression past 2.5s blocks merge"* — sourced from the founder's own prior-marketplace bounce data. The real command `npm run lhci` (Lighthouse CI) is already in the synthesis's Real Commands table, detected and unused. This fails "No vague language without measurable criteria," "All MUST/SHOULD statements have enforcement mechanisms," and "Generic thresholds" in the anti-pattern scan simultaneously. **Fix: replace both the CLAUDE.md line and the ledger's GI-011 Enforcement/Testability with the ratified 2.5s p75 LCP / `npm run lhci` / merge-blocking-on-regression language, and add the gate to the Quality gates section.**

5. **CLAUDE.md ratified stamp line omits `pci-dss`.** Line: `**Ratified:** v1.0.0 · ... · modules: gdpr · a11y`. pci-dss is attached (ledger header lists it as legal-mandate; GI-009 exists; GI-012 waiver references it) but is missing from the region's own stamp line. **Fix: add `pci-dss` to the stamp line's module list.**

6. **CLAUDE.md — placeholder trace ID left in on the a11y principle.** `- Every customer-facing page MUST meet WCAG 2.2 AA... <!-- GI-XXX -->` should read `<!-- GI-010 -->`. This is a direct "No Placeholders Rule" violation and it breaks the index→ledger closure for that principle (GI-XXX resolves nowhere; GI-010 is the actual ledger entry). **Fix: correct the trace comment to `GI-010`.**

### Important

7. **Ledger — missing "Exception registry" section.** Shape 3 requires Governance Floor header · Waivers · Amendment policy · **Exception registry** · Three-Part records · amendment log (confirmed against the authoring skill's own ledger-content line and the Governance Quality checklist's "Exception registry format defined" item). The ledger as drafted has Waivers, Amendment policy, Principles, and Amendment log — no Exception registry section anywhere. This is a missing structural part, not a cosmetic gap. **Fix: add the section (even if empty/"none recorded" for a fresh greenfield set).**

8. **Ledger, GI-009 (Cardholder Data) — missing Rationale section.** Every other Three-Part record (GI-004 through GI-016) has Enforcement/Testability/Rationale; GI-009 has only Enforcement and Testability. **Fix: add a Rationale line (the fact profile already supplies the "why" — card data existential risk — it just needs to land in the record).**

9. **CLAUDE.md — GI-004 has two principle-index lines.** "Secrets MUST stay out of the repository..." and, further down, "Security at boundaries — see `.claude/rules/mochiko/security.md`" both carry `<!-- GI-004 -->`. The checklist requires one line per principle; this also reads as two principles claiming the same GI-ID. The `security.md` rules file already auto-injects on any path (`paths: ["**/*"]`) per the standing new-file-read mechanism, so the explicit pointer line is redundant. **Fix: collapse to one line — keep the Secrets content (the ledger's stated primary home) and drop the separate pointer bullet, or restructure GI-004 the way GI-009 is structured (single pointer line, full content only in the rules file + ledger).**

10. **Release-gates module internally contradicts the GI-012 waiver.** The Release Gates table (ledger, GI-013) lists "PCI evidence: a dated ASV report for the current quarter under `compliance/pci/`" as a gate that **blocks promotion to prod**. The GI-012 waiver excuses producing that exact ASV report until "the first paying customer" — which cannot happen before a prod promotion. As drafted, the release gate can never legitimately pass pre-launch, or (more likely in practice) gets quietly overridden — either way it's an unresolved self-contradiction in the same document, distinct from and compounding Critical #1. Resolves automatically once Critical #1 is fixed.

11. **Knowledge-management module core artifacts not present on disk.** The module is adopted "core, whole," and its fragment's re-audit item checks presence directly against the repo. Only `CHANGELOG.md` (the pre-existing elective, correctly codified) exists at repo root; `ROADMAP.md`, `BACKLOG.md`, `DECISIONS.md`, and `GLOSSARY.md` do not. The project-pinned copy, rules file, and CLAUDE.md pointer are all correctly in place — it's the scaffolded docs themselves that are missing. If scaffolding is a distinct `/mochiko:setup` finalize step that hasn't run yet, say so explicitly to the lead; if it was meant to be done, it wasn't. **Fix: scaffold the four missing core artifacts, or confirm to the lead that a separate finalize pass is still pending.**

## Bottom line for the lead

This is not a close call. Two of the findings (GI-012's waiver and GI-016's principle) directly contradict explicit, named rulings in the very synthesis this set claims to trace — not vague-language nitpicks, but the surface set asserting the opposite of what was ratified. A third (the cardholder-data.md scope) re-opens a gap the synthesis review already found and marked resolved. Given the two-week launch clock and that this is a card-payments product, I'd treat #1 and #3 as the ones to fix before anything else ships, regardless of how the rest of the punch list gets scheduled. Send it back to the producer; this should not be re-validated by re-reading the same claims — re-run this checklist against the files once revised.
