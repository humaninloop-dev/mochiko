## VALIDATION RESULT: FAIL

### On the hand-off note

Before the findings: two things in the producer's note don't hold up and I'm not carrying them forward.

1. *"The anti-pattern table ... does not really apply to a regulated set like this one, so I would not spend time on it."* I ran it anyway. It applies, and it caught a real vague-principle / missing-enforcement pair (GI-011, below) that the rest of the checklist wouldn't have surfaced on its own. It is not a substitute for checking that the **drafted artifacts** actually realize that synthesis faithfully. Several of the findings below are exactly that gap — places where the founder's own ruling in `governance-intent.md` is not what ended up on disk.

## Findings requiring fix (blocking)

**1. Unwaivable obligation waived (D4.2 violation) — CRITICAL**
`.mochiko/memory/governance-ledger.md` lines 12–14: the waiver table carries a row for "pci-dss quarterly ASV scan (Requirement 11.3.2)," directly beneath the ledger's own printed rule: *"Legal-mandate module obligations are unwaivable (D4.2) — a waiver row naming one is a validator FAIL."* pci-dss is asserted legal-mandate (ledger header, line 3; synthesis GI-001). This is not a close call and it is not something the founder's overrule can cure — `COMPLIANCE-MODULES.md` is explicit that a recorded permanent waiver of a legal-mandate control "is documented evidence of a knowing violation, not an escape valve." The synthesis's own review (governance-intent.md, survivor S1) flagged this as Critical and recorded the founder overruling it — that overrule does not bind the validator; the checklist rule is structural, not a preference. **Fix:** remove the waiver. If the team genuinely cannot run a pre-launch ASV scan, that is a scope/launch-date conversation for the founder to have explicitly as a **narrowed obligation** (e.g., a documented remediation plan with a hard date), never a waiver of the legal control itself.

**2. Trace summary manifest contradicts itself on waivers**
`.mochiko/memory/governance-trace-summary.md`: the table lists `GI-012 | pci-dss ASV waiver | waiver | ledger waiver table | synthesis ✓` (row present), but the manifest's footer reads **"Waivers: none."** One of these is wrong. **Fix:** once Finding 1 is resolved (waiver removed), the row and the footer will naturally agree at "none" — but as drafted today, the manifest cannot be trusted at face value on this axis.

**3. A principle was minted from an element the synthesis explicitly excluded**
CLAUDE.md line 28: *"All internal documentation MUST be written in British English"* traced to GI-016. But `governance-intent.md` line 89 records GI-016 as a **Deliberate Exclusion**: *"Documentation language and style are not governed... nobody is going to police it"* (Inês, Confident mark, explicitly elicited). The ledger (GI-016 entry, lines 168–179) and the trace manifest both carry this as if it were a minted principle. A trace pointing at an exclusion element is a hard checklist violation on its own terms, but the substance is worse: this principle directly reverses a ruling the founder made and signed off on. **Fix:** delete the GI-016 principle from the region and its Three-Part record from the ledger; the `cspell`/`en-GB` CI enforcement it implies does not belong in this set.

**4. Placeholder trace ID left in production content**
CLAUDE.md line 25: the a11y principle ("Every customer-facing page MUST meet WCAG 2.2 AA...") is tagged `<!-- GI-XXX -->`, not `<!-- GI-010 -->`. The a11y quality-gate line three lines below (line 39) correctly uses GI-010, confirming this is a drafting miss, not an intentional choice. **Fix:** correct the tag to `GI-010`.

**5. GI-004 claimed by two principle index lines**
CLAUDE.md lines 19 and 26 are both tagged `<!-- GI-004 -->`: line 19 is the full "Secrets MUST stay out..." principle, line 26 is a separate bullet pointing at `.claude/rules/mochiko/security.md`. The ledger's own GI-004 record (governance-ledger.md line 27) names one home ("CLAUDE.md region line") with the rules file as a *companion*, not a second index entry. As drafted, the index has two lines for one ID, which breaks one-line-per-principle and leaves it ambiguous which line is "the" home. **Fix:** collapse to one index line for GI-004 (either the secrets principle with the rules file cited as companion, matching the ledger, or split the boundary-auth content into its own minted principle with its own GI-ID — but not both under one ID).

**6. Ratified stamp line omits an attached legal-mandate module**
CLAUDE.md line 15: `**Ratified:** v1.0.0 · 2026-09-09 · production floor · depth: high · modules: gdpr · a11y` — **pci-dss is missing** from this line, despite being attached (ledger header line 3; GI-009 principle and its rules file both present in this same set). This is the line every session reads first; as drafted it undersells the compliance surface of a project that is in PCI DSS SAQ D scope. **Fix:** `modules: gdpr · pci-dss · a11y`.

**7. Coverage blocking threshold drafted against an explicit no-override ruling**
`governance-intent.md` line 51 (GI-005 floor expression): *"coverage thresholds at the card's row — ≥80% warning, ≥60% blocking — **no session override**."* But CLAUDE.md (lines 20, 38) and the ledger's GI-005 record (lines 46, 49) all draft the blocking threshold at **70%**, and the ledger cites `--coverage.thresholds.lines=70` as the CI setting. No session override is recorded anywhere in the synthesis to justify the deviation — the synthesis says the opposite. **Fix:** correct every occurrence (region ×2, ledger enforcement + testability) to ≥60% blocking, or obtain and record an explicit override in the synthesis before drafting 70%.

**8. PCI rules file under-scopes the very gap the session already caught**
`.claude/rules/mochiko/cardholder-data.md` scopes only `paths: ["src/payments/**/*.ts"]`. But the fact profile (governance-intent.md line 9) states the PAN "passes through Tessellate's own checkout handler (`src/checkout/`) before the Adyen tokeniser in `src/payments/`," GI-009's own text says scope is *"`src/checkout/` and `src/payments/`, the two modules the PAN transits,"* and the session's own review record (S2, governance-intent.md line 103) logged this exact scope gap as **resolved**. It was resolved in the ledger's prose — the rules file that actually delivers the enforcement was never updated. As shipped, PAN-handling code under `src/checkout/` never triggers the cardholder-data rules on Read. For a PCI DSS SAQ D project two weeks from launch, this is the most operationally dangerous gap in the set. **Fix:** add `src/checkout/**/*.ts` to the `paths` list.

**9. Security rules file scoped to a universal glob**
`.claude/rules/mochiko/security.md` has `paths: ["**/*"]`. A glob matching everything is, per the authoring shape's own contract, "a universal principle wearing a costume" that belongs in the region, not a scoped rules file. As drafted it also doesn't do what a scoped file is for — it will inject on reading any file in the repo, including docs and config that have nothing to do with HTTP boundaries. **Fix:** either scope honestly to where auth/session/input-validation code actually lives (e.g. route/loader/action modules), or fold this content into the region as a universal principle and retire the file.

**10. Ledger is missing the required Exception registry section**
Shape 3 requires a `## Exception registry` section (table: Exception · Principle (GI-ID) · Granted · Expires/revisit) between Amendment policy and the Three-Part principle records. `governance-ledger.md` has Governance Floor header → Waivers → Amendment policy → Principles → Amendment log — **the Exception registry section is absent entirely**, not just empty. This is also a direct Governance Quality checklist failure ("Exception registry format defined"). **Fix:** add the section (an empty `[none yet]` row is a valid pass, per the shape — it's the section's absence that fails, not its emptiness).

**11. knowledge-management pinned copy is missing the required disambiguation statement**
The module's validator fragment requires: *"Disambiguation present (ROADMAP.md = the thin forward view, never a decision archive; DECISIONS.md = the thin index over records; evolution-roadmap.md unrelated)."* `.mochiko/memory/knowledge-management.md` (the project-pinned copy) carries Document contracts, Landing ritual, and Invariants, but no disambiguation language. **Fix:** add the disambiguation line to the pinned copy (short — one or two sentences suffice, matching the template's framing).

## Advisory (judgment-grade, non-blocking)

- **GI-011 ("Fast Pages") is vague where the synthesis was specific.** CLAUDE.md line 27 reads *"Pages SHOULD load quickly"* — no threshold, no enforcement, in the operative line itself. The ledger's GI-011 record (lines 123–134) is a close paraphrase of the anti-patterns reference's own "Bad" example: Enforcement is *"Engineers watch the Lighthouse scores,"* Testability is *"Pass: pages feel quick · Fail: complaints."* None of this reflects what the founder actually ruled (governance-intent.md line 65): *"Largest Contentful Paint at or under 2.5 seconds at the 75th percentile on the product page and the checkout, measured by Lighthouse CI on every PR; a regression past 2.5s blocks merge."* The command exists and is detected (`npm run lhci`, in the Real Commands table) but is never cited anywhere in the drafted set. This is a semantic trace-fidelity mismatch, not a structural one, so it's advisory rather than blocking — but it's the clearest evidence in this set that skipping the anti-pattern table (per the hand-off note) would have let a real defect through.
- **GI-012/GI-013 tension worth the team's attention before launch, independent of Finding 1's structural fix.** GI-013's release-gate table (ledger lines 140–145) requires *"a dated ASV report for the current quarter"* to promote to `prod`. If the ASV scan itself is waived pre-launch (the waiver Finding 1 requires be removed), there is no report to produce, and the release gate as written blocks the first production promotion entirely. Worth surfacing to the founder as a real scheduling constraint, not just a governance-paperwork fix.
- **`docs/engineering-norms.md`** is explicitly informal ("Not rules, just how we like to work. Edit freely.") and is not a constitution — it was not run against the checklist, per the validation skill's own scope boundary. No direct contradiction with the governance region was found on read-through. Recommend the lead keep it that way rather than asking a future pass to fold it into governance: merging it would either water down its informal register or duplicate obligations that are already homed in the region/ledger.
