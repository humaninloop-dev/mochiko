## On the producer's hand-off note

The note was relayed verbatim and is contradicted by the artifacts on three specific points, so the
lead should not carry these claims forward:

- **"no waivers"** — false. `.mochiko/memory/governance-ledger.md` has one waiver row (GI-012,
  pci-dss quarterly ASV scan), and it is precisely the kind of waiver the framework never allows
  (see Finding 1).
- **"every obligation traced"** — not accurate. GI-016 traces a principle to what the synthesis
  records as a *deliberate exclusion* (Finding 2); the a11y principle's trace comment is the literal
  placeholder `GI-XXX`, not a real ID (Finding 8); the knowledge-management module's own trace
  summary lists only `CHANGELOG.md` as a delivered companion — the rest of the module's core
  artifacts were never scaffolded (Finding 3).
- **"the anti-pattern table... does not really apply... would not spend time on it"** — rejected.
  This is the exact rationalization the validation skill calls out by name ("these anti-patterns
  don't apply to this case"). Running the table found a live instance: GI-011 is, almost verbatim,
  the checklist's own "Bad" example of a vague, unenforceable principle — while the *ratified
  synthesis* for that same element specifies a hard number and a CI gate. Skipping the table would
  have let a regression past the exact mechanism it exists to catch.

Founder sign-off and a two-week launch clock are noted, but neither substitutes for validation, and
neither can override a structural rule (D4.2, below) — that rule is not a matter of team taste.

## Fix list (ranked)

### Critical

**1. GI-012 waives a legal-mandate module obligation — structurally disallowed (D4.2).**
The ledger's Waivers table carries a permanent waiver of "pci-dss quarterly ASV scan (Requirement
11.3.2)." pci-dss is a legal-mandate module. Per the compliance-modules rule: *"obligations entering
via a legally-mandated module are unwaivable... a recorded permanent waiver of a legal control is
documented evidence of a knowing violation, not an escape valve."* The synthesis's own review
already caught this in-session (S1, Critical) and the founder overruled it — that overrule is
recorded, but it does not change the validator's gate, which is binary and non-negotiable on this
point. **Fix:** remove the waiver row; either fund/schedule the first ASV scan before launch or
bring the obligation back to the founder as a go/no-go launch decision, not a governance waiver.

**2. GI-016 turns a deliberate exclusion into a mandatory principle.**
`governance-intent.md`'s "Deliberate exclusions" section records: *"Documentation language and
style are not governed... nobody is going to police it"* (the founder's own words, dimension 10).
The delivered set instead contains a full principle — "All internal documentation MUST be written
in British English," a CLAUDE.md region line, and a ledger Three-Part record with a `cspell`
enforcement mechanism — all stamped `GI-016`. This is not a fidelity nuance; it is the opposite
ruling from what was ratified. **Fix:** delete the principle, its ledger record, and the `cspell`
CI wiring, or take it back to the founder as a new ruling (which would be a fresh GI element, not a
reuse of the excluded GI-016).

**3. Knowledge-management core artifacts do not exist.**
The module was adopted "core, whole" plus the `CHANGELOG.md` elective. Confirmed on disk: only
`CHANGELOG.md` and the three enforcement surfaces (pinned copy, rules file, CLAUDE.md pointer)
exist. `ROADMAP.md`, `BACKLOG.md`, `DECISIONS.md`, `ARCHITECTURE.md`, `GLOSSARY.md`, and
`.mochiko/brainstorms/index.md` are all absent — confirmed by direct filesystem check, not by the
producer's report. The module's own Presence invariant ("all core artifacts exist") fails outright;
this is not the vacuous-at-zero case, since the module carries enforcement surfaces that assume the
artifacts exist. **Fix:** scaffold the missing core docs at finalize, or correct the record if the
team genuinely wants a partial adopt (which the module's rules explicitly do not permit — core is
"adopted or declined whole").

### Important

**4. `cardholder-data.md` doesn't cover the code path the PAN actually transits.**
The rules file scopes to `paths: src/payments/**/*.ts` only. But the fact profile, `README.md`, and
the ledger's own GI-009 text all agree the PAN passes through Tessellate's own checkout handler
(`src/checkout/`) *before* it reaches the Adyen tokeniser in `src/payments/`. The session review
already caught this (S2) and the ledger prose was widened to say "scope: `src/checkout/` and
`src/payments/`" — but the actual enforcement mechanism, the rules file's `paths` glob, was never
updated. Code under `src/checkout/` — the file that first touches a live card number — gets no
cardholder-data guidance injected on Read. **Fix:** add `src/checkout/**/*.ts` to the `paths` list.

**5. Testing coverage threshold contradicts the ratified synthesis, with no recorded override.**
`governance-intent.md`: "≥80% warning, ≥60% blocking — **no session override**." Delivered region
and ledger: "≥80% warning, ≥70% blocking." No override is recorded anywhere between the synthesis
and the drafted set. **Fix:** reconcile to 60% blocking (the synthesis's ruling), or — if 70% is
genuinely wanted — record it explicitly as a session override in the synthesis and ledger.

**6. GI-011 ("Fast Pages") lost its enforcement and its number.**
Synthesis: "LCP ≤ 2.5s p75 on the product page and checkout, measured by Lighthouse CI on every PR;
a regression past 2.5s blocks merge." Delivered region: "Pages SHOULD load quickly." Delivered
ledger: "Enforcement: Engineers watch the Lighthouse scores. Testability: Pass: pages feel quick.
Fail: complaints." `npm run lhci` — a real, detected command listed in the synthesis's own commands
table — never appears in the CLAUDE.md Quality Gates section. **Fix:** restore the threshold and
wire `npm run lhci` as a blocking CI gate, matching what was actually ratified.

**7. GI-004 is claimed by two separate region principle lines.**
"Secrets MUST stay out of the repository..." and "Security at boundaries — see
`.claude/rules/mochiko/security.md`" both carry the `<!-- GI-004 -->` trace comment. Either this is
one principle wrongly split across two region lines (breaking "one line per principle"), or two
principles wrongly sharing one ID. **Fix:** merge into a single region line for GI-004 (pointing at
the rules file as the companion, as the ledger's "home" field already says), or split the second
line off under its own minted/floor GI-ID if it's meant to be distinct.

**8. Placeholder trace stamp on the Accessibility principle.**
`Every customer-facing page MUST meet WCAG 2.2 AA... <!-- GI-XXX -->` — literal placeholder syntax
instead of the real ID (`GI-010`, per the ledger and trace summary). **Fix:** replace `GI-XXX` with
`GI-010`.

### Moderate

**9. Ratified stamp line omits an attached compliance module.**
CLAUDE.md: `modules: gdpr · a11y`. pci-dss is attached (GI-009 is a full principle with its own
rules file, and the ledger's Governance Floor header lists it), but it's missing from the region's
stamp line. Region and ledger must agree. **Fix:** add `pci-dss` to the stamp line.

**10. Ledger has no Exception registry section.**
Shape 3 requires Governance Floor header · Waivers · Amendment policy · **Exception registry** ·
Three-Part records · amendment log. The ledger has everything except a distinct Exception registry
— Waivers and Exceptions are different things and both are contractually required sections.
**Fix:** add the section (even if empty/"none recorded" for now).

**11. GI-009's ledger record has no Rationale section.**
Enforcement and Testability are present; Rationale is not (compare to every other GI record, which
all have one). **Fix:** add a Rationale line (the obvious content — cardholder data + PCI scope —
is already sitting in GI-004's and GI-008's Rationale lines for comparison).

**12. The PCI waiver and the release gate contradict each other.**
The ledger waives the quarterly ASV scan "too expensive pre-launch; the first paying customer funds
it," while the Release Gates table makes "a dated ASV report for the current quarter" a hard blocker
on *every* promotion to prod — including the first one, before there is a paying customer to fund
it. As written, either the gate blocks launch entirely, or it will need to be quietly bypassed the
first time, which defeats the point of a release gate. This is independent of Finding 1 (which
already requires removing the waiver) and should be reconciled either way.
