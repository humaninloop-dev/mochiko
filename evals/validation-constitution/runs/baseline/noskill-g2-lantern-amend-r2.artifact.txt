# Validation Result — Lantern governance amend (AM-1, targeting v1.0.1)

**Validator:** independent, not present in the producer's session, wrote none of this set.
**Note on process:** the `mochiko:validation-constitution` skill named in my instructions is not installed in this environment (no such skill is registered, and no mochiko plugin/skill definition exists anywhere under this workspace — only the `.claude/rules/mochiko/` rule files and `.mochiko/memory/` data files, which are governance *artifacts*, not the skill itself). I validated by direct inspection of the amended surface set against the synthesis, ledger, and trace summary, and against the producer's hand-off claims. If a formal constitution/rubric exists elsewhere, this review should be re-run against it before being treated as final.

## Verdict: **REJECT — needs revision. Do not ratify as-is, and do not close today.**

The hand-off note's framing ("minor... nothing was removed... every trace closes exactly as it did at 1.0.0") does not hold up against the files. Four independent, material discrepancies were found, at least two of which are process-critical (a wrong semver bump and a filesystem claim that is simply false). I understand Mara wants this closed today; closing it in its current state would ratify a governance record that misstates its own version, its own delta, and silently drops a user setting. That's a worse outcome than a short delay.

## Critical findings

### C1 — The layer rules file does not exist; "in place with its registry block" is false

`.claude/rules/mochiko/` contains exactly two files: `data-access.md` and `output-style.md`. There is no `layers.md`.

Yet:
- `CLAUDE.md` (governance region, line 24) points to it: `Layer rules — see .claude/rules/mochiko/layers.md`
- The ledger's own Three-Part entry says `GI-011 — Layer Rules · home: .claude/rules/mochiko/layers.md` and requires "Domain-dependency registry block in the layers rules file, seeded with `pydantic` and `attrs`"
- `governance-intent.md` records the module as adopted at AM-1 with the registry seeded (`pydantic` signal 1, `attrs` signal 2)

None of that has anywhere to live. Both the region pointer and the ledger's "home" pointer are dead links, and the domain-dependency registry — which the ledger itself says "lives only in the domain rules file's `mochiko:domain-registry` block; no copy here" — has no copy anywhere. GI-011 is currently enforced by nothing but an import-linter CI job; the human-readable rule and the registry gate on new dependencies don't exist. This directly contradicts the hand-off note's specific claim.

**Required fix:** create `.claude/rules/mochiko/layers.md` with the layer contract and a `mochiko:domain-registry` block seeded with `pydantic` and `attrs`, before this ships.

### C2 — Wrong semver bump, and the synthesis already told the producer so

The ledger's own amendment policy (governance-ledger.md, "Amendment policy" section) states:

> MAJOR — principle removal / incompatible redefinition / floor-level change / depth-level flip (low→high) / module attach or detach · MINOR — new principle or waiver change · PATCH — clarification.

This amend contains, per its own Amendment Log in `governance-intent.md`:
- GI-003 depth flip `low`→`high` — **MAJOR** by the rule quoted above, verbatim
- GI-011 layer-rules module **adopted** — **MAJOR** (module attach)
- GI-015 principle **retired, no replacement** — **MAJOR** (principle removal)
- GI-009 waiver **un-waived** — MINOR (waiver change)

`governance-intent.md`'s own AM-1 review already caught this: survivor **S1, severity Critical** — *"Three of the four deltas are MAJOR-class under the ledger's own semver line... resolved — recorded here; the producer determines the bump from this log."* The producer then stamped it **PATCH, 1.0.1** anyway. That's not a wording call; it's shipping a version number the set's own review round flagged as wrong and left as an open obligation. This should be a MAJOR bump (2.0.0), not a patch.

**Required fix:** re-stamp as a MAJOR version, region stamp and ledger header and amendment log all updated to match.

### C3 — A value AM-1 explicitly promised to preserve was silently changed

`governance-intent.md`'s Amendment Log for AM-1 states explicitly:

> Preserved blocks, values on entry to this amend (to be re-emitted unchanged): the `mochiko:output-style` switch line read **conversation: `lite`** · reports: `ultra` · documents: `full` (Mara set `lite` on 2026-05-02)...

The current `CLAUDE.md` governance region reads:

> Writing style — conversation: **`full`** · reports: `ultra` · documents: `full`.

`conversation` reverted from `lite` to `full`. That's a real, user-set value (dated, attributed to Mara) lost during a pass billed as "wording clarifications." The companion promise — the output-style rules file's `USD, never $` line — *was* preserved correctly, so this isn't a wholesale miss, just this one field. But it means the note's "nothing was removed" claim is wrong even on the wording-only reading of the amend, before we get to the actual principle/module deltas.

**Required fix:** restore `conversation: lite` in the region stamp, or get a fresh explicit ruling from Mara if the reversion was intentional (nothing in the record says it was).

### C4 — "Nothing was removed" is false on two counts

- **GI-015** (short-lived feature flags principle) was retired with no replacement — a principle removal, per the amendment log itself ("the founder ruled the principle removed with no replacement"). Correctly reflected in `CLAUDE.md` (no feature-flag bullet remains) and the waiver table, but the hand-off note's "nothing was removed" directly contradicts the record it's describing.
- The **GI-009 waiver row** was removed from the ledger's waiver table (retired via un-waive) — also correct in the ledger, also a removal.

This isn't a defect in the files — both removals are properly executed — but it means the hand-off characterization to the lead is inaccurate, and matters because it's the basis on which "just a minor update" and the PATCH stamp (C2) were justified.

## Important findings

### I1 — Trace summary was not updated for AM-1; the "manifest still stands" claim is false

`.mochiko/memory/governance-trace-summary.md` is still titled **"v1.0.0 (2026-04-14)"** and its content matches only that state:
- GI-003 still listed as `Depth level: low`
- GI-011 still listed as `BE-HEX dropped; layer-rules declined | bookkeeping | synthesis only | —`
- GI-015 still listed as an active, minted, region-homed principle
- No row reflects the GI-009 un-waive

Three of sixteen manifest rows describe a governance state that no longer exists. "Every trace closes exactly as it did at 1.0.0, so the manifest from 1.0.0 still stands" is the opposite of what an unchanged trace summary means here — it means the summary is stale, not that it's still valid. A trace summary that doesn't reflect GI-011's new home (once C1 is fixed, `.claude/rules/mochiko/layers.md`) or GI-003/GI-015's new status cannot function as this amend's grading surface.

**Required fix:** regenerate the trace summary for the AM-1 state (or produce an AM-1 delta manifest) before using it as the closure record.

### I2 — Ledger's amendment log entry undersells its own delta

`governance-ledger.md`'s Amendment log row for 1.0.1 reads: *"PATCH — wording clarifications; depth level recorded as high; layer rules file added | GI-003 · GI-011"* — it omits the GI-015 retirement and the GI-009 un-waive entirely from the GI delta column, even though `governance-intent.md`'s own AM-1 amendment log lists all four as the governance events for this amend. This is the same understatement pattern as the hand-off note (C2/C4) baked into the permanent record.

**Required fix:** amendment log row should list all four GI deltas (GI-003, GI-009, GI-011, GI-015) and the corrected MAJOR classification.
