## Issues requiring fix

1. **Region stamp omits an attached legal-mandate module.** `CLAUDE.md:15` reads `modules: gdpr
   · a11y`. The ledger header and `governance-intent.md` GI-001 both carry pci-dss as a third,
   mechanically-triggered, legal-mandate module, and GI-009 (Cardholder Data) is in fact landed
   in the region and in `cardholder-data.md`. The stamp must list all three.

2. **`cardholder-data.md` is scoped to the wrong paths.** Its frontmatter reads
   `paths: ["src/payments/**/*.ts"]`. GI-009's own element text (ledger and synthesis) states
   the scope is "`src/checkout/` and `src/payments/`, the two modules the PAN transits" — this
   exact gap was raised and marked **resolved** in the synthesis review (S2, Important). The fix
   was made to the element text but never to the rules file's actual `paths:` list, so the
   PCI rule will not inject on Read/Write in `src/checkout/`, the module where the PAN first
   lands. Add `"src/checkout/**/*.ts"` to `paths:`.

3. **GI-012 waives a legal-mandate obligation, which the ledger itself defines as a FAIL.**
   `governance-ledger.md`'s Waivers section states, immediately above the table: "Legal-mandate
   module obligations are unwaivable (D4.2) — a waiver row naming one is a validator FAIL." The
   very next row waives the pci-dss quarterly ASV scan (Requirement 11.3.2). The synthesis
   records that this exact conflict was raised at review (S1, Critical) and the founder
   overruled it — but D4.2 is a floor invariant of the governance mechanism, not a session-level
   choice the founder's ruling can waive, and founder sign-off does not verify this at
   validation time. This must be removed or the module's unwaivable-obligation status revisited,
   not carried forward as "Contested."

4. **GI-016 contradicts the ratified synthesis outright.** `CLAUDE.md:28` and the ledger's GI-016
   entry assert and enforce a British-English documentation principle (`cspell`, en-GB, CI-
   blocking). `governance-intent.md`'s own GI-016 is filed under **Deliberate exclusions** and
   states the opposite was ruled: "the team writes in whatever English it has; no principle
   governs spelling, register, or the language of internal documents" — elicited verbatim from
   the founder ("we have Portuguese, Scottish, and Bristol English on the team and nobody is
   going to police it"). Remove the principle, the ledger entry, and the `cspell` gate.

5. **GI-005's blocking coverage threshold drifted from the ratified value.** `CLAUDE.md:20` and
   the ledger both assert `≥ 70%` blocking coverage on new code. `governance-intent.md`'s
   floor-expression table fixes FLOOR-TEST's high-row value at "≥80% warning, ≥60% blocking —
   **no session override**." Correct the region line and the ledger's Enforcement/Testability
   text (and the CI threshold flag, `--coverage.thresholds.lines`) to 60%, or take the
   discrepancy back through `/mochiko:setup` amend if the team actually wants 70% — it cannot
   just appear in the draft.

6. **GI-011's ratified criterion never reached enforcement.** See anti-patterns 1–2 above. Fix:
   restate the region principle with the actual number (LCP ≤ 2.5s p75, Lighthouse CI, blocks on
   regression), rewrite the ledger's Enforcement/Testability to the same, and add `npm run lhci`
   to the CLAUDE.md Quality gates list — the command is already detected and declared for this
   exact purpose in `governance-intent.md`'s Real commands table.

7. **The producer's own trace manifest contradicts itself.** `governance-trace-summary.md`'s
   GI-012 row correctly lists it as a waiver, but the closing line reads "**Waivers:** none." This
   matches the hand-off note's false claim of "no waivers" — both undercount the one waiver that
   is actually the most serious defect in the set (Issue 3). Regenerate the trace summary from
   the actual ledger content, not from the running assumption that the waiver was resolved.
