`scripts/check-artifacts.py` live outside this session's permitted read/exec paths and could not

## 2. Adopt-first disclosure (BLOCKING)

`design-disclosure.md`'s `adopt_first` block:

```
- {decision: D-004, category: locking, shelf_named: no, note: "small enough to own"}
- {decision: D-005, category: scheduling, shelf_named: "Redis TTL", custom_beats_shelf: "n/a — shelf chosen"}
```

- **D-004 (offer-issue serialisation, category: locking) fails the disclosure gate outright.**
  `shelf_named: no` is neither a real shelf candidate nor an assertion that "no shelf candidate
  exists" — it's "we didn't look." PostgreSQL advisory locks / `SELECT ... FOR UPDATE` are a
  real, in-stack shelf candidate for exactly this problem (serialise-per-berth-row), and
  `constraints-and-decisions.md`'s D-004 alternatives table lists **one option only** — no
  comparison happened. G-03 explicitly asked the design phase to weigh the existing D-001
  (pg-boss/singletonKey) shelf here; that weighing is not on the record.
  **Severity: Critical (blocking).**

- **D-005 (hold expiry, category: scheduling) names a shelf ("Redis TTL") — disclosure presence
  is satisfied — but the choice itself contradicts the product's blocking datastore constraint,
  and the stated rationale is false.** See §4 for the detail; noting it here because it means
  the one decision that *did* clear the adopt-first bar did so by picking the option the
  baseline forbids.

- **Fix:** re-run D-004 with ≥2 real alternatives (at minimum: Postgres advisory lock /
  `SELECT FOR UPDATE`, vs. the `offer_locks` table), and re-run D-005 against the already-adopted
  D-001 shelf (pg-boss delayed job) with an honest comparison, per the sufficiency report's own
  instruction.

## 3. Rung-claim honesty (advisory)

`design-disclosure.md`'s ladder is directionally reasonable (WaitlistEntry/Offer at rung 1,
Booking.offerId at rung 3) with two exceptions worth flagging to the lead even though this lane
is advisory:

- **D-005 "rung 3 already exists" is not honest.** The claim is "Redis is already in the stack
  for sessions" — but the product baseline's session mechanism (D-002, AX-001) is
  **server-side sessions in PostgreSQL**, not Redis. Redis is not in the stack anywhere in the
  product baseline. This rung claim is factually wrong, and it's the load-bearing justification
  for a constraint-violating decision (§4).
- **"tasks.md Cycle 2 task list, rung 5 builder's room, claim: file paths listed to save the
  builder the lookup"** — rung-5 self-disclosure doesn't cure this. The cycle-card format itself
  forbids pre-written task lists and file paths regardless of rung (the builder decomposes at
  build time). This is a hard format violation, not a minimalism-rung question — see §5.

## 4. Cross-artifact consistency: design vs. decided (Critical)

**D-005 (Redis key TTL for hold expiry) contradicts C-003, a blocking product constraint, and
invalidates the sufficiency report's no-delta claim.**

- `.mochiko/product/constraints-and-decisions.md:28-31` — C-003, blocking: *"PostgreSQL is the
  only datastore... a second datastore needs a platform sign-off recorded on AX-002 before any
  code."*
- `.mochiko/product/architecture/concerns.md:15` — AX-002 *"Sign-offs recorded: none."*
- `.mochiko/features/FEAT-031/constraints-and-decisions.md:58-62` — D-005 chooses "Redis key TTL"
  and adds `IP-003: Redis instance in lhr` (line 70-77) as a MUST infrastructure item — with no
  AX-002 sign-off recorded anywhere in this package.
- The stated rationale ("Redis is already in the stack for sessions") is false (§3), and the
  one real alternative in D-005's own table — **pg-boss delayed job, already the adopted
  mechanism (D-001)** — is rejected for "job table grows with open offers (small)," which the
  table itself concedes is not a real cost at this scale.
- `sufficiency-report.md:14` records the store consult's `no_delta_claim`: *"No structural
  change: the waitlist rides the existing api, worker, and db containers; no new container,
  boundary, or flow."* Introducing a managed Redis instance **is** a new container/boundary.
  Nothing in `design-disclosure.md` acknowledges that this decision invalidates the no-delta
  claim, and no architecture-store delta or AX-002 consult accompanies it.

This is a design-vs-decided contradiction, which per this skill's scope is graded here (not
handed to `review-feasibility`, which owns requirement-vs-requirement contradictions).

- **Severity: Critical.**
- **Fix:** either produce the AX-002 sign-off before this decision stands, or replace D-005 with
  the pg-boss delayed-job option already on its own alternatives table, and update or withdraw
  the no-delta claim accordingly.

**Two decisions declare required follow-on work that never appears in `tasks.md`:**

- D-004's consequence: *"a sweeper job for stale lock rows"* (`constraints-and-decisions.md:50`).
- D-005's consequence: *"expiry notifications are at-most-once, so a missed notification needs a
  sweep"* (`constraints-and-decisions.md:62`).

Neither sweeper appears in any of the four cycles. If these are load-bearing for correctness
(a stuck lock row or a missed Redis expiry notification both mean a berth never releases), they
need a cycle or at least a named task — currently there is none.

- **Severity: Critical** (declared-necessary correctness work with zero build traceability).

## 5. Cycle-card / tasks.md completeness

- **US-4 (P2, "homed") has zero cycle coverage.** `tasks.md:11` states *"Stories covered: US-1,
  US-2, US-3"* — openly omitting US-4. This tracks with the missing queue-view endpoint (§1):
  there's nothing to test because nothing was designed. Per the checklist, every P1/P2 story
  needs ≥1 card. **Severity: Critical.**

- **FR-002 (leave the waitlist) has zero test coverage anywhere in tasks.md**, despite
  `DELETE /waitlist/{entryId}` existing in the contract. No cycle exercises leaving, position
  renumbering (US-1 scenario 2), or the "entrant leaves while holding an open offer → offer
  withdrawn" edge case. **Severity: Critical.**

- **The vessel-length skip edge case is untested.** Spec edge case: *"The first entrant's vessel
  no longer fits the freed berth... skip to the next entrant... the skipped entrant keeps their
  position."* No cycle in `tasks.md` exercises this — Cycle 2's offer-issue test only covers the
  case where the first entrant's vessel fits. **Severity: Important.**

- **Cycle 2 embeds a pre-written task list with file paths** (`tasks.md:54-58`: `offer.service.ts`,
  `accept.controller.ts`, a migration path, `templates.ts`). The cycle-card grammar explicitly
  forbids this — decomposition is build-time, not design-time — regardless of the rung-5
  self-disclosure in `design-disclosure.md:14`. **Severity: Critical** (explicit format
  violation, not a minimalism judgment call).

- **Cycle 3's Assert inverts the requirement it's meant to verify.** `tasks.md:91`: *"The second
  entrant's offer `issuedAt` is T + 24 h, after the declined offer's hold elapses."* But
  `stories/US-3.md:6` and `spec.md`'s FR-005 both require the next offer **immediately** on
  decline, *"not after the original hold would have ended."* As written, this assert would pass
  only if the system does the wrong thing (waits out the full 24h hold before offering the
  decliner's berth to the next entrant) and would fail correct behaviour (an immediate re-offer).
  This is an oracle-semantics defect that inverts pass/fail. **Severity: Critical.**

- **Cycle 4 is entirely out-of-scope material** (US-5/FR-009 don't exist — §1) and should be
  dropped or re-grounded, not graded on its own merits until re-traced.

## 6. Data-model completeness

- **`WaitlistEntry.contactEmail` is left unclassified in its own attribute row**
  (`data-model.md:41`: the Sensitivity column is blank), yet the same document declares it
  Confidential via **DS-002** three lines later in a separate section (`constraints-and-decisions.md:87-90`,
  *"WaitlistEntry.contactEmail (Confidential)"*), and the top-of-file **Data Sensitivity
  Summary — "the coverage index"** (`data-model.md:8-10`) omits this attribute entirely, listing
  only `Offer.stripePaymentIntentId`. A PII field (an e-mail address, the same class as
  `Owner.email`, Confidential in the baseline) is inconsistently and incompletely annotated
  within a single document. **Severity: Critical** (sensitivity-annotation presence is an
  explicit completeness check, and this is a live PII field).
  **Fix:** classify `contactEmail` Confidential in its attribute row and add it to the coverage
  index table.

- **No Payment entity linkage is modeled for the accept-offer charge.** The product baseline's
  governance floor (CLAUDE.md: *"Money moves only on someone's authority... `authorisedBy` is
  non-null on every payment row; the API rejects a null"*) implies every charge produces a
  `Payment` row. `data-model.md`'s `Offer` entity carries its own `stripePaymentIntentId`
  (line 65) but nothing shows a `Payment` row being created or linked on accept, and the
  contract's `HoldReceipt` response (`contracts/api.yaml:110-117`) has no `authorisedBy` or
  `paymentId` field. It's unclear from this package how (or whether) the accept flow satisfies
  the baseline's payment-authority principle. **Severity: Important.**

## Informational — gaps noticed in the spec itself (out-of-band; not part of the plan-artifact verdict above)

Requested by the requirements analyst while reviewing the design package against `spec.md` and
`stories/`. These are observations on the **specification**, not findings against the design
package, and carry no verdict weight above.

1. **No FR backs the "notified" clause in US-2.** `stories/US-2.md:6` requires the entrant be
   "notified" when an offer issues, but `spec.md`'s FR list (FR-001..FR-006) has no requirement
   covering the notification itself — channel, timing, or content. This gap is plausibly *why*
   the design phase felt licensed to invent a `Notification` entity and an FR-007 that doesn't
   exist in the spec (see §1 above) — worth closing at the source so design doesn't need to
   improvise a requirement number.

2. **No FR or edge case addresses a missing/expired saved payment method at accept time.** The
   spec's only payment-failure path is "the saved method is declined" (edge case, FR-004). It's
   silent on an owner who has *no* saved method at all when their offer issues — a real state
   for any owner who joins a waitlist without ever completing a booking-and-pay flow before.

3. **Marketing-consent vs. transactional status of the offer notice is undecided at the spec
   layer**, and surfaced downstream as a blocking `[NEEDS CLARIFICATION]` in the design's C-006
   (see §7). This reads as a requirements gap that should have been resolved before design, not
   discovered during it.

4. **FR-004 doesn't state which dates the resulting booking uses.** "accepting... MUST... create
   the booking" doesn't say the booking's `startsOn`/`endsOn` are the waitlist entry's
   `fromDate`/`toDate` verbatim — reasonable to infer, but not stated, and the freed berth's own
   available window could in principle differ from the entry's requested range.

5. **No requirement covers what happens to a vessel's fit-check if the vessel is edited (e.g.
   `lengthM` changed) while the owner is queued.** The design's `WaitlistEntry.vesselId` is a
   live reference, so a length edit after joining silently changes fit eligibility for an entry
   already in position — the spec doesn't say whether that's intended, disallowed, or needs
   re-validation.

6. **US-4 has no "offer open" or "notify" detail beyond "whether an offer is open"** — FR-006
   doesn't say whether marina staff can *act* on that (e.g., see who to call), which may be fine
   as a read-only view, but the spec doesn't explicitly rule out an action surface, leaving the
   P2 story's real scope a little underdetermined for design.
