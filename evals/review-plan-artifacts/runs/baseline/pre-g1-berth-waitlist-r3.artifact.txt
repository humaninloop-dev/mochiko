## Clarifications needed

### C1: Does the offer notice require marketing consent, or is it transactional? (I1)

**Question**: C-006 leaves this open with a [NEEDS CLARIFICATION] marker. An offer e-mail is
time-critical (24 h hold) — treating it as marketing-gated risks an owner missing their hold
window because they opted out of marketing mail.
**Options**: 1. Transactional (sends regardless of marketing opt-out) · 2. Gated by marketing
consent · 3. A new consent category ("service alerts") distinct from marketing
**Why it matters**: Determines whether Postmark suppression lists can block an offer notice,
which directly risks SC-001/SC-002 if an owner never learns their hold started.

### C2: What actually frees a berth for a waitlisted date range? (G8)

**Question**: The product baseline's Booking state machine has no cancellation path
(FEAT-034 pending), yet FR-003's whole trigger is "a berth of the class frees." Is FEAT-034
a hard dependency this feature must wait on, or is there an interim release mechanism
(e.g. marina staff manually reassign/cancel) that should be modeled now?
**Options**: 1. Block FEAT-031 on FEAT-034 landing first · 2. Design an interim
release/cancel transition scoped to this feature · 3. Restrict "frees" to non-renewal at
endsOn only (no early release) and say so explicitly in the spec
**Why it matters**: Without this, Cycle 2's core TEST has no real trigger to test against,
and the feature's central mechanic is unbuildable as specified.

## Spec gaps (flagged for requirements-analyst, not part of this review's verdict)

- **Release trigger undefined**: spec.md never states what "a berth of the class frees"
  means operationally — cancellation, non-renewal, or both — and the baseline has no
  cancellation path yet (see C2 above). This ambiguity is what let the design phase leave
  G8 unresolved.
- **Notification requirement missing**: US-2/US-3 acceptance scenarios say "the owner is
  notified" but no FR requires it or names a channel/content constraint, which let the
  design phase invent an orphan FR-007 for the Notification entity (G3). Consider adding an
  FR sourced from C-004 (Postmark-only) covering what an offer/decline/lapse notice must
  and must not contain (feeds directly into C-006/I1's consent question too).
- **Concurrent entries per owner unstated**: spec.md doesn't say whether an owner may hold
  waitlist entries at multiple marinas, or multiple berth classes at one marina,
  simultaneously — the design phase had to invent this via a validation rule
  (one entry per ownerId+marinaId+berthClass+range) without a spec anchor.
- **Expiry notice unspecified**: the edge case "the entry expires ... and the owner is told"
  has no FR requiring a notification on expiry, leaving it to design/build discretion.
