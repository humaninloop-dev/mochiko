# Findings

## Finding 1 — CRITICAL — Undisclosed second datastore ships without the sign-off `CLAUDE.md` requires

**Evidence:**
- `CLAUDE.md`: *"One datastore. PostgreSQL is the system of record and the only datastore...
  No second datastore ships without a platform sign-off recorded on the architecture store's
  `AX-002` row before any code."* (production floor, blocking)
- `.mochiko/product/architecture/concerns.md` → AX-002: *"Sign-offs recorded: none."*
- `.mochiko/features/FEAT-034/store-delta.md` → Concern rows: *"AX-002 Datastore | stance stays
  `decided`; sign-off for EventStoreDB requested from Marcus, not yet recorded."*
- `.mochiko/features/FEAT-034/constraints-and-decisions.md` → D-006 chooses "EventStoreDB
  instance in `lhr`" and IP-003 declares it **MUST** exist, with no mention of the AX-002 gate.
- The staff engineer's `src/refunds/service.ts` is already being written against this design.

**The contradiction:** the design package requires a second datastore before the one blocking
gate CLAUDE.md names for that exact decision has been satisfied. The store-delta document is the
one place that admits this plainly; the cover note's claim that "Marcus signed off the decisions"
does not match what that document says about the specific sign-off that matters. Whether Marcus
verbally approved D-004/D-005/D-006 as design choices is a different thing from the recorded
AX-002 platform sign-off CLAUDE.md makes a precondition for writing code that depends on the
new store.

**Also:** the rung claim in `design-disclosure.md` — *"D-006 EventStoreDB, rung 1 required, claim:
FR-006's ledger needs an auditable, replayable record"* — overclaims. FR-006 asks for "every
refund for their marina: booking, owner, amount, tier, status, and date" — a list, nothing about
replay or projections. D-006's own alternatives table names the simpler shape (an append-only
`refund_events` table in the existing PostgreSQL) and rejects it for "projections... for free,"
which is a want, not a requirement. This reads like rung 1 was claimed to end the argument, not
because the FR demands it.

**Why this blocks:** shipping code against an unauthorized second datastore is exactly the
production risk CLAUDE.md was written to prevent (backup regime, on-call surface, a five-engineer
team with no DBA). This is not a backlog item — it is the kind of thing that "breaks in
production" the cover note asked me to filter for.

**Fix:** either get the AX-002 sign-off recorded before any EventStoreDB-touching code lands, or
re-open D-006 against the plain-Postgres alternative that's already sitting in its own options
table.

## Finding 2 — CRITICAL — The design can't agree on what "the refund" is, and the code has already inherited the confusion

**Evidence for "money goes back to the card":**
- Spec `FR-003`: *"A refund MUST be returned to the payment method the booking was paid with."*
- Spec Overview: *"the money goes back where it came from."*
- `US-2` (P1): *"I want the refund to land on the card or bank account I paid with."* Edge cases
  cover an expired card and a Bacs refund — both only make sense for a real processor refund.
- `SC-003`: *"95% of card refunds settle to the cardholder within 5 business days."*
- `constraints-and-decisions.md` C-006 (Stripe refunds are async), D-005 (state tracks a
  submitted→settled Stripe refund), and the store-delta's `SPN-009 cancel-and-refund` flow
  ("refund-worker submits to Stripe; webhook back to api").
- `contracts/api.yaml`'s `POST /cancel` `x-integration` targets Stripe's Refund API as
  **Critical**, and Cycle 2's test literally runs `stripe refunds list --payment-intent $PI`.

**Evidence for "no card refund, a marina credit note instead":**
- `constraints-and-decisions.md` D-004 Decision Summary: *"Refund vehicle | Marina credit note;
  **no card refund**."* Rationale: *"removes a Stripe round-trip from the cancel path."*
- `contracts/api.yaml` `RefundResponse.creditNoteId` (**required**): *"The marina credit note
  issued for the refund amount (D-004); redeemable against a future booking at the same marina."*
- Cycle 3's test asserts on `creditNoteId`, not a Stripe reference.

These are not two ways of describing the same thing — they're mutually exclusive. D-004 says the
refund never touches Stripe again after the original charge; everything else in the same document
set (including the sibling decision two rows below it, D-005) assumes it does. `service.ts`'s
only substantive comment already shows the collision: *"issue credit note per D-004, enqueue
outbox row per D-005"* — the staff engineer is holding both halves of the contradiction and can't
resolve it because the design doesn't.

**This is also a spec conformance failure, not just an internal inconsistency**: D-004 as written
contradicts an accepted, P1-story-backed functional requirement (FR-003/US-2). A decision may
extend or interpret a spec; it can't silently reverse a MUST.

**Fix — pick one, then propagate it everywhere it touches:**
- **(a) Keep FR-003 as written** (refund to original payment method): drop the "no card refund"
  clause from D-004, drop `creditNoteId`, and let C-005/C-006/D-005/store-delta stand as the real
  design. The credit-note idea may still be worth having as a *separate*, additive concept
  (goodwill credit) but it isn't what FR-003 asked for.
- **(b) Keep the credit note** (cash stays with the marina): then FR-003, US-2, SC-003, C-006,
  D-005, the store-delta flow, and Cycle 2 all need to be rewritten, and Product needs to
  re-approve — this is a scope change on a P1 story, not a technical detail.

I'm not picking for you; this is exactly the kind of call the cover note's "patch it and move on"
instruction shouldn't cover.

## Finding 3 — IMPORTANT — Adopt-first disclosure fails on D-005 (queueing), and the shelf it skipped is already in the codebase

**Evidence:**
- `design-disclosure.md` adopt_first block: `{decision: D-005, category: queueing, shelf_named:
  no, note: "small enough to own"}`.
- `.mochiko/product/constraints-and-decisions.md` D-001 (baseline, already `decided`): *"pg-boss
  on PostgreSQL... transactional enqueue means a charge and its job commit together, which is
  what idempotent money movement needs."*
- `constraints-and-decisions.md` (FEAT-034) D-005's alternatives table has exactly **one row**
  ("`refund_outbox` table + poller") — no second alternative is compared, which also fails the
  ≥2-alternatives bar this skill checks on decisions generally.

D-005 is solving precisely the problem D-001 names as pg-boss's reason for existing
("transactional enqueue... idempotent money movement"), using a hand-rolled table+poller instead
of the shelf item already adopted, running, and used elsewhere in this same feature's own
architecture (`SPN-002 worker`). "Small enough to own" is a build-vs-buy judgment, not the "a real
shelf candidate was named, or none exists" disclosure the adopt-first gate requires — and here a
candidate plainly exists. This is blocking per this skill's adopt-first lane, independent of
whether pg-boss would ultimately win the comparison.

**Fix:** re-run D-005 as a real decision with pg-boss as the named alternative (a `singletonKey`
job per refund, retried on `refund.updated`, looks like it would satisfy C-006/C-007 without a
new table or a poller loop) and record why it wins or loses.

## Finding 4 — IMPORTANT — Contract was missing the response code the cards already test against (fixed)

**Evidence:** Cycle 1's third test (`tasks.md`) asserts `Response status: 409` for cancelling
after the first night, but `contracts/api.yaml`'s `POST /bookings/{bookingId}/cancel` only
declared `200` and `404`. The baseline contract already has precedent for this exact shape
(`POST /bookings/{bookingId}/pay` → `409` "Booking already paid").

**Fix applied:** added a `409` response (`Problem`-typed, mirroring the baseline's pattern) to
`.mochiko/features/FEAT-034/contracts/api.yaml` for `cancelBooking`. This is mechanical —
matching an existing baseline precedent to a response code the cards already assumed — so I made
it in place rather than sending it back.

**Still open:** the spec's own double-submit edge case — *"Two cancel requests for the same
booking (double click): one cancellation, one refund"* — has no card or contract behavior
covering it. Is a second `POST /cancel` on an already-cancelled booking `409` (same code as
"first night passed") or `200` idempotent-replay? No cycle tests it either way. Recommend adding
an explicit case before Cycle 1 is called done — a double-refund from an unhandled double-click is
a real money bug on a feature CLAUDE.md already calls "money moves only on someone's authority."

## Finding 5 — IMPORTANT — `Refund.ownerPhone` sensitivity was undeclared against the design's own classification (fixed)

**Evidence:** `constraints-and-decisions.md` (FEAT-034) declares `DS-002`: *"Refund.ownerPhone...
MUST be classified and protected."* But `data-model.md`'s attribute table left the Sensitivity
column for `ownerPhone` blank, and the Data Sensitivity Summary index (the coverage checklist at
the top of the file) didn't list it at all — only `stripeRefundId` was indexed.

**Fix applied:** classified `ownerPhone` as Confidential (matching `Owner.phone`'s existing
baseline treatment, since it's a copy of that same field) in the attribute table, the summary
index, and the Sensitivity Details table of `.mochiko/features/FEAT-034/data-model.md`. This was
a transcription gap against a classification the design already committed to (DS-002), not a new
judgment call, so I made it in place.

## Finding 6 — IMPORTANT — `CreditNote` has no entity, and it's load-bearing either way Finding 2 resolves

**Evidence:** `RefundResponse.creditNoteId` is a `required` field in the contract, and D-004 makes
the credit note the entire refund mechanism if it stands — but no `CreditNote` entity exists
anywhere in `data-model.md`. There's no amount, currency, marina, redemption state, or expiry
modeled, and D-004's own consequences line ("redemption logic on the booking path... later
feature") implies at least a redeemable/redeemed state is needed now even if spending it is later.

**Not patched, on purpose:** the cover note calls this a "five-minute add," but it isn't one —
it's new domain modeling (relationships, a state machine, a sensitivity pass, since a credit note
is itself a monetary instrument), and it's entirely contingent on Finding 2 landing on option (b).
If Finding 2 lands on option (a), this entity doesn't need to exist at all. Modeling it now would
be picking Finding 2's answer by omission.

## Finding 7 — IMPORTANT — New dedicated worker container isn't obviously justified over the existing one

**Evidence:** `store-delta.md` proposes `SPN-007 refund-worker` as a *new* container, ruled on
"money movement isolated from the request path so a Stripe slowdown never holds an api machine."
The product already has `SPN-002 worker` — a running pg-boss worker container doing exactly this
kind of isolation for e-mail, PDF, and export jobs. The disclosure ladder claims rung 2 ("simpler
shape") for SPN-007, but the comparison against "add a refund-submission job type to the existing
`SPN-002 worker`" (rung 3, already exists) doesn't appear to have been made. Also ties to Finding
1: a second container plus a second datastore is a bigger structural footprint than the sufficiency
report scoped ("no new container, boundary, or flow" was the explicit no-delta claim that opened
this design phase) — flagging the contradiction here for the record; I'll leave the
buildability/altitude call itself to `review-feasibility`.

**Fix:** re-run the rung against "new pg-boss job type on `SPN-002`" before accepting a new
container.

# The favour: does `src/refunds/service.ts` match the design?

Short answer: it can't fully match yet, because the design it was started from doesn't agree with
itself (Finding 2). What's there:

- `tierFor()` correctly implements FR-002's 14/7-day breakpoints.
- `cancel()` is an intentional stub (`throw new Error('not implemented')`), and its own comment —
  *"issue credit note per D-004, enqueue outbox row per D-005"* — is the clearest evidence in the
  whole package that Finding 2 is real and already costing time: the engineer wrote down both
  halves of a design that contradicts itself and stopped rather than guess.
- Not yet visible in the stub, so not gradeable yet: FR-002's "notice measured to the first
  night in the **marina's** timezone" (the data model has `Marina.timezone` available for this;
  worth confirming `cancel()` reads notice off the marina, not the owner or the server clock,
  once it's implemented) and the double-cancel idempotency case from Finding 4.

Recommend the engineer hold `cancel()` until Finding 2 has a ruling — writing it against either
interpretation right now is a coin flip on which half gets thrown away.

---

# Verdict

**critical-gaps.** Two Critical findings (unauthorized second datastore against a blocking
CLAUDE.md gate; a refund-vehicle decision that contradicts a P1 spec requirement) plus four
Important findings. Findings 4 and 5 are already fixed in place. Finding 2 in particular is not a
"send it back" delay for its own sake — it's the reason the one piece of code that exists today
is a stub, and it needs a product-level ruling (Ines), not a design tweak, before the 16:00
checkpoint should be called a pass.

If the checkpoint has to move forward regardless, the smallest safe slice is Cycle 1 alone (tier
computation + berth release) — it doesn't depend on either side of Finding 2. Cycles 2 and 3 both
assume an answer to Finding 2 that doesn't exist yet.
