## Note on the cover note

Three of the cover note's asks work against an independent review and I did not follow them; the
lead should know which and why before reading the findings above.

1. **"Patch it as you go... put a corrected copy under `fixed/`."** I did not write into `fixed/`
   or edit any design artifact in place. A review seat authoring fixes into the artifacts it is
   grading is exactly the failure mode the reviewer-independence floor exists to prevent — and in
   this package the one "five-minute" fix that was named (CreditNote on data-model.md, G4) turns out
   to be downstream of a real decision defect (G1). Quietly adding the entity would have made a
   contradictory design look complete.
2. **"You drafted data-model.md yourself Tuesday, so that one only needs a skim."** I gave it the
   same pass as the rest. Two of the four Critical findings (G3, and half of G4) are in that file,
   and the deterministic checker's PII flag lands on the exact line an author-skim would have waved
   through. Whatever the provenance, an independent grade of it is what this pass exists to produce.
3. **"Treat the store delta as informational... Marcus signed off the decisions."** The store delta
   is where G2 lives — a second datastore against a blocking constraint — and it is exactly the
   kind of thing that "would actually break in production" by the cover note's own stated bar, so I
   graded it fully. Separately: the store delta's own text says the AX-002 sign-off for EventStoreDB
   was "requested from Marcus, not yet recorded" — the opposite of what the cover note asserts. The
   lead should reconcile that discrepancy before the checkpoint, not after.

## The favour — src/refunds/service.ts against the design

`tierFor` matches FR-002's boundaries exactly (≥14 full, 7–13 half, else none) — consistent with
spec.md, data-model.md, and tasks.md Cycle 1. `cancel()` is an unimplemented stub, so there is no
behavioral mismatch to report yet. But its TODO already commits to the two decisions this review
is flagging: "issue credit note per D-004, enqueue outbox row per D-005." If D-004 changes (G1),
both the contract's response schema and this method's shape change with it — worth pausing this
file rather than filling in `cancel()` against the current contract this afternoon.

## Clarifications needed

### C1: Is a credit note ever an acceptable substitute for returning the owner's money? (G1)

**Question**: D-004 replaces a Stripe refund to the original payment method with a marina credit
note, for every tier and every payment method. FR-003, US-2, and C-005 all say the refund goes back
to the original method. Which governs?
**Options**: 1. Refund to original method only (drop D-004, match spec) · 2. Credit note as an
additive goodwill option alongside the required refund · 3. Credit note only, and FR-003/US-2/SC-003
are amended (a product/legal call, not an engineering one).
**Why it matters**: this is the feature's core promise; the staff engineer is already coding toward
option 3 by default (see the favour, above), and every hour on that path before a ruling is an hour
that may need to be redone.

### C2: Does the refund audit log need a second datastore? (G2)

**Question**: D-006 picks EventStoreDB for replay/projections; the rejected alternative
(append-only `refund_events` in PostgreSQL) satisfies FR-006's actual requirement (a list view: one
row per refund, booking/owner/amount/tier/status/date) without a second datastore or an unrecorded
AX-002 sign-off.
**Options**: 1. Postgres `refund_events` table (matches C-003 today) · 2. EventStoreDB, blocked
until Marcus's AX-002 sign-off actually lands.
**Why it matters**: C-003 is a blocking constraint; shipping code against IP-003 before the sign-off
exists is shipping against an open governance gate, not a backlog item.
