## Critical (blocking)

### 1. Architecture store delta is out of scope and contradicts the sufficiency report's own no-delta claim
`sufficiency-report.md`'s `store_consult.no_delta_claim` states plainly: *"No structural
change: cancellation and refunds ride the existing api, worker, db and the standing Stripe
boundary; no new container, boundary, or flow."* Neither gap (G-01 contract-exposure, G-02
data-exposure) named an architecture delta at all.

`store-delta.md` nonetheless introduces **two new elements and a new flow**: SPN-007
(`refund-worker`, new container), SPN-008 (`EventStoreDB`, new boundary), SPN-009
(`cancel-and-refund`, new flow) — none of it something a named gap authorized.

**Fix:** per `material-divergence-autofail`, this alone is enough to fail the package back to
the architect. The delta needs to be re-justified against the no-delta claim it contradicts,
or withdrawn — the existing `SPN-002 worker` container already exists for exactly "timed
work" (see finding #5); it isn't obvious SPN-007 earns its keep.

### 2. New datastore (EventStoreDB) ships without the sign-off CLAUDE.md requires before any code
CLAUDE.md's governing principle: *"One datastore... No second datastore ships without a
platform sign-off recorded on the architecture store's `AX-002` row before any code."*
`constraints-and-decisions.md` (product baseline) restates this as C-003, **blocking**
severity.

`store-delta.md` itself: *"sign-off for EventStoreDB requested from Marcus, not yet
recorded."* D-006 chooses EventStoreDB over the Postgres-native alternative its own
alternatives table lists (*"Append-only `refund_events` table in PostgreSQL — One datastore;
trivially queryable"*) to satisfy FR-006, which only asks for a list view (booking, owner,
amount, tier, status, date) — not replay/projections.

**Fix:** this blocks code today regardless of anything else in this review. Either get the
AX-002 sign-off recorded first, or take D-006 back to the Postgres-table option that was
already on the table and already satisfies FR-006.

### 3. D-004 (marina credit note, no card refund) contradicts FR-003, US-2, SC-003, and the constraint it claims to be shaped by
- FR-003: *"A refund MUST be returned to the payment method the booking was paid with."*
- US-2 (P1): *"the refund reaches the payment method I paid with"*; independent test: *"a
  refund against the original PaymentIntent appears in Stripe within 60 s."*
- SC-003: *"95% of card refunds settle to the cardholder within 5 business days, measured from
  the processor's refund events."*
- C-005, cited in `constraints-and-decisions.md` (FEAT-034 delta) as the thing D-004 is
  *"shaped by"*: *"a card refund returns to the original card; a refund to any other
  instrument is a scheme violation."*

D-004 chooses *"marina credit note; no card refund"* — the opposite of what C-005, FR-003,
US-2, and SC-003 all specify. This isn't a simplification trade-off, it's building a different
feature than the one accepted in `spec.md`. This is a contradiction/buildability call that
belongs to `mochiko:review-feasibility` to classify formally — I'm flagging it here because it
also makes the rest of the package materially diverge from what any gap authorized, and it's
the root cause of findings #4 and #7 below.

**Fix:** D-004 needs to go back to "Stripe refund to the original payment" (the option already
listed in its own alternatives table) unless someone is deliberately re-scoping US-2 out of
the feature — which is a product call, not a design-phase one to make silently.

### 4. Contract requires a `CreditNote` entity that exists nowhere in the data model
`contracts/api.yaml`'s `RefundResponse.creditNoteId` (required) is described as *"The marina
credit note issued for the refund amount (D-004)"* — but no `CreditNote` entity appears in
`data-model.md`, gap G-02 named only `Refund` (new) and `Booking`'s new state, and there is no
sensitivity classification, state machine, or relationship for whatever this entity is meant
to be.

The cover note calls this *"a five-minute add to `data-model.md`"* — it understates the
problem. `CreditNote` only exists because of D-004 (finding #3); modeling it faithfully means
modeling a feature the spec doesn't describe. Adding the entity without revisiting D-004 papers
over the real gap rather than closing it, which is why I didn't make the edit myself.

**Fix:** resolve #3 first; model `CreditNote` only if the product decision is to actually ship
credit notes instead of cash refunds.

### 5. False "no shelf candidate" disclosure on D-005 (adopt-first, blocking)
`design-disclosure.md`'s adopt-first block: `{decision: D-005, category: queueing,
shelf_named: no, note: "small enough to own"}`.

But a queueing shelf is already standing and already adopted for this exact need: D-001
(product baseline) chose pg-boss specifically because *"transactional enqueue means a charge
and its job commit together, which is what idempotent money movement needs"* — refund
submission is a charge-adjacent, idempotent money-movement job by the constraints document's
own description (C-006, C-007). D-005 hand-rolls a parallel `refund_outbox` table + poller +
state machine instead of a pg-boss job, without ever mentioning pg-boss.

Per `review-plan-artifacts.adopt-first-lens`, a commodity-category decision must name a real
candidate or truthfully state none exists; asserting "no candidate" when the product's own
standing decision is squarely on point is not a true "none exists" — it fails the check in
substance even though the disclosure field is technically filled in.

**Fix:** either explain in writing why pg-boss can't carry refund submission (and let that
survive scrutiny), or fold D-005 into a pg-boss job and drop the bespoke outbox/poller.

### 6. Marina refund ledger contract omits two fields FR-006 explicitly requires
FR-006: *"Marina staff MUST be able to see every refund for their marina: booking, owner,
amount, tier, status, and date."*

`RefundResponse` (used by `GET /marinas/{marinaId}/refunds`) has `id, bookingId, amountMinor,
currency, tier, status, creditNoteId, expectedBy` — **no owner and no date/createdAt.** The
data exists (`Refund.authorisedBy`, `Refund.createdAt`) but isn't exposed through the contract
the ledger endpoint returns. Cycle 3's TEST card inherits the gap — its asserts check only
`creditNoteId` presence and ordering, never owner or date, so it would pass against a
non-conforming implementation.

**Fix:** add `ownerId` (or a display name) and `createdAt`/`date` to `RefundResponse`, and add
an assert for both to Cycle 3's TEST card.

## Important (blocking)

### 7. Cycle 2's first TEST has no `**Assert**` at all
```
**TEST:** Cancelling a card-paid booking submits a refund
- Setup: ...
- Action: curl ... /cancel
- Action: sleep 60 && stripe refunds list --payment-intent $PI
- Capture: console
```
No assert line — the card can't mechanically pass or fail. It's also written against the
pre-D-004 world (a Stripe refund against the original PaymentIntent), which D-004 as written
no longer produces — see finding #3.

**Fix:** add an explicit assert once #3 is resolved, matching whatever the corrected refund
vehicle actually returns.

### 8. Cycle 3 cites a requirement that doesn't exist
`**Covers**: US-3 / FR-006, FR-011` — `spec.md` defines FR-001 through FR-006 only; there is
no FR-011. Broken traceability reference.

**Fix:** drop `FR-011` or correct it to whatever was intended.

### 9. Cycle 3 is tagged `[P]` while declaring a dependency
`### - [ ] Cycle 3: Marina refund ledger [P]` also states `**Depends on:** C2`. Per the
dependency-minimality checklist, `[P]` is reserved for cards that are truly independent — this
card contradicts its own tag.

**Fix:** drop the `[P]` tag (or drop the stated dependency, if it's actually independent).

### 10. D-005's poller interval is an unresolved `[TBD]`
*"Consequences: poller every [TBD] seconds..."* — SC-001 requires a refund initiated within 60
seconds p95, and Cycle 2's test hardcodes a 60-second sleep before checking Stripe. An
undefined poller interval means neither the requirement nor the test has a designed basis for
passing.

**Fix:** pick and record an interval before this goes to a builder (or resolve via #5, which
may make the interval moot).

### 11. `Refund.ownerPhone` is an undocumented Confidential-PII copy with no traced requirement
`data-model.md` (FEAT-034) adds `ownerPhone` to `Refund` — *"Number to call about the refund;
copied from Owner at cancellation"* — but:
- No FR or US in `spec.md` mentions calling the owner about a refund.
- Its Sensitivity cell in the entity's own attribute table is **blank**.
- It's absent from the Data Sensitivity Summary index at the top of the same document.
- `constraints-and-decisions.md` (FEAT-034 delta) separately declares `DS-002: Refund
  contact number ... Refund.ownerPhone (Confidential)` — so the classification exists, just
  not where the data-modeling checklist requires it to be recorded.

This is a Confidential PII duplication (Owner.phone is already Confidential in the baseline)
introduced without a named requirement, and its handling isn't documented where governance
requires (CLAUDE.md: *"Counterparty data is confidential ... masking, audit logging"*).

**Fix:** either trace it to a real requirement and complete its Sensitivity Details row and
summary-index entry, or drop the field.

### 12. `RefundResponse.expectedBy` is optional, but FR-004 makes it mandatory
FR-004: *"On cancellation the owner MUST see the refund amount, the tier applied, and when to
expect the money."* `expectedBy` is not in `RefundResponse`'s `required` list, so a
schema-valid response can omit the one field FR-004 says must always be there.

**Fix:** add `expectedBy` to `required` (or document why it's legitimately absent for some
tier, e.g. tier `none`).

- **D-006** claims rung `1 required` on *"FR-006's ledger needs an auditable, replayable

## The favour: `src/refunds/service.ts` against the design

- `tierFor()` is correct against FR-002: `>=14` → full, `>=7` → half, else none — boundaries
  match the 14-day/7-day cutoffs exactly.
- `cancel()` is an explicit `TODO`/stub (`throw new Error('not implemented')`), started "from
  the contract before the review" per its header comment — there's nothing to fault in a stub,
  but flagging loudly so the afternoon isn't lost to it: **don't implement `cancel()`'s
  credit-note/outbox path yet.** As written, the contract and D-004/D-005 it would be built
  against are the subject of findings #2–#5 above; building against them now means reworking
  `cancel()` once those are resolved, which is the exact mismatch-losing-the-afternoon scenario
  the cover note asked me to watch for.

## Verdict: critical-gaps

Finding #1 alone triggers `material-divergence-autofail` (an architecture delta no gap named,
contradicting the sufficiency report's own no-delta claim). Independently, finding #2 is a
blocking-constraint violation (second datastore, no recorded sign-off) and finding #3 is a
P1-story-breaking contradiction. Any one of these blocks; together they put this well past
`needs-revision`.

**Recommended path to close, in order:** resolve #3 (D-004 refund vehicle) first — it's
upstream of #4 and #7. Then #1/#2 (architecture delta and the EventStoreDB sign-off/necessity)
and #5 (pg-boss vs. hand-rolled outbox) together, since they're the same "does this need new
infrastructure" question. Then #6, #10, #11, #12 are each independent and fast. #8/#9 are
one-line tasks-file corrections.
