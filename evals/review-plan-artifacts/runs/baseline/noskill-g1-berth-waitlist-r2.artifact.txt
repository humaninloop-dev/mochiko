## Blocking

### B-1. D-005 justifies a second datastore with a claim the product baseline contradicts, and skips the required sign-off

`FEAT-031/constraints-and-decisions.md` D-005 chooses "Redis key TTL with keyspace
notifications" for hold expiry, rationale: *"Redis is already in the stack for sessions, so this
adds no new infrastructure."* That is false. The product baseline `constraints-and-decisions.md`
D-002 states sessions are **server-side, in a PostgreSQL session table** — "Consequences: session
table in PostgreSQL." There is no Redis anywhere in the built system (`architecture/spine.md`'s
container diagram has five elements: api, worker, db, Stripe, Postmark — no cache/KV boundary).

This isn't a stylistic quibble: `C-003` (blocking) says *"a second datastore needs a platform
sign-off recorded on \[AX-002\] before any code."* `concerns.md` AX-002 currently shows
**"Sign-offs recorded: none."** D-005 introduces IP-003 (a new managed Redis instance in `lhr`)
without that sign-off, and the false "already in the stack" premise is exactly the kind of
reasoning that would let it slip through review unnoticed. `design-disclosure.md`'s ladder
compounds it: the D-005 row claims rung "3 already exists" with the same false note, which is the
rung that normally lets a checkpoint wave something through without scrutiny.

D-001 already gives this feature a same-datastore option (pg-boss delayed job) that D-005's own
comparison table lists and rejects only on "job table grows with open offers (small)" — a cost the
table itself calls small. There is no stated reason C-003's bar was worth clearing here.

**This should stop the checkpoint.** Either get the AX-002 sign-off on the record before build, or
switch D-005 to the pg-boss option already on the table and drop IP-003.

### B-2. US-4/FR-006 (marina staff queue view) has no contract endpoint and no task — while an out-of-spec forecast feature got a full build-out in its place

`spec.md` FR-006 (MUST): marina staff must see the waitlist per berth class with position, date
range, vessel length. US-4 is homed, P2, in scope.

- `contracts/api.yaml`: no GET endpoint for the queue exists anywhere in the delta. `POST
  /marinas/{marinaId}/waitlist` and `DELETE /waitlist/{entryId}` are the only waitlist paths.
- `tasks.md`: the Overview table states outright — **"Stories covered | US-1, US-2, US-3."** US-4
  is absent from every cycle card.

Meanwhile, `contracts/api.yaml` (lines 57–65), `data-model.md`'s implied schema, and
`design-disclosure.md` (row: `GET /berths/{berthId}/availability-forecast`, rung "4 minimum now")
all build out a **`GET /berths/{berthId}/availability-forecast`** endpoint with a full
`AvailabilityForecast` schema, and `tasks.md` Cycle 4 gives it a dedicated test cycle. Its
justification cites **"US-5"** and **"FR-009"** — neither exists anywhere in `spec.md` or
`stories/`. The spec's own scope boundary explicitly lists what's in: "waitlisting... offers,
holds, accept/decline; the marina's view of its queue" — a forecast digest is not in that list,
and "cross-marina waitlists; waitlist priority tiers; SMS" are the only stated exclusions, so this
isn't even a named out-of-scope item, just an invented one.

Net effect: a MUST requirement with a real story has zero design surface, while a requirement that
doesn't exist in any approved spec artifact has a contract, a schema, a disclosure entry, and a
test cycle. This is scope substitution, not just an omission, and it should be corrected before the
checkpoint closes — not carried forward as a follow-up.

### B-3. Offer has no "lapsed" state, so FR-005 and SC-001 aren't representable

`data-model.md` Offer.status is `Enum(open, accepted, declined)`, and the documented state machine
only lists `open → accepted` and `open → declined`. But FR-005 and US-3 both require a third
outcome — the offer **lapsing** after 24h with no response, distinct from an active decline (US-3:
*"24 hours pass without a response, then the offer lapses and the next eligible entrant is issued
an offer immediately"*). With only `declined` to record both cases, the two are indistinguishable
in the data.

This directly breaks measurability of `SC-001` ("90% of offers are accepted or declined within the
hold, measured monthly from the offers table") — the offers table as designed cannot tell a
timely decline from a timeout, so the metric can't be computed as specified. Needs a `lapsed`
status value and a transition (`open → lapsed`) added before this ships.

## Significant

### S-1. WaitlistEntry.contactEmail is Confidential PII but skips the baseline's own sensitivity documentation pattern

The product baseline's data-model convention (see `.mochiko/product/data-model.md`'s "Data
Sensitivity Summary" plus a per-entity "Sensitivity Details" table for every Confidential/
Restricted attribute) is not followed for `contactEmail`:
- It's missing from FEAT-031's Data Sensitivity Summary index (only `Offer.stripePaymentIntentId`
  is listed there), despite `DS-002` declaring it Confidential.
- Its Sensitivity column in the WaitlistEntry attribute table is **blank**, not "Confidential."
- There's no Sensitivity Details subsection (retention, access, masking deviation) for it at all,
  unlike Owner.email/phone and Offer.stripePaymentIntentId which each get one.

Separately: it's a *copy* of `Owner.email` taken at join time, which can go stale (owner changes
address; entry sits on the waitlist for weeks) and creates a second location that must observe
Owner's "delete ≤ 30 days after account closure" erasure rule — the design doesn't say whether
`contactEmail` is erased/nulled on account closure independent of the WaitlistEntry's own
lifecycle. Worth resolving before build, since this is exactly the class of gap DS-001/DS-002 exist
to catch.

### S-2. No stated trigger for `issueOffer(berthId)`, and its placement risks the request-thread/idempotent-job principles

`tasks.md` Cycle 2 puts `issueOffer(berthId)` and the `offer_locks` polling loop in
`src/waitlist/offer.service.ts` (api-side, per the brownfield note "extends `src/bookings/`"), but
nothing in `constraints-and-decisions.md` or `data-model.md` states *what calls it* when a berth
actually frees. Berths free either via `Booking` reaching `completed` (a scheduled, non-request-
triggered transition) or eventually via cancellation (FEAT-034, not yet built) — neither is an
inbound HTTP request. If `issueOffer`'s 500ms-polling lock loop runs synchronously inside an API
request handler, that conflicts with the architecture spine's "one transaction per request"
responsibility for `SPN-001 api` and with D-001's own rationale for pushing anything that outlives
a request onto the worker. The design package should say which process calls this and when —
right now the only place the trigger is implied is the manual `psql update bookings set
status='completed'` in the Cycle 2 test setup, which is a test fixture standing in for a mechanism
that isn't otherwise specified.

Related: the `offer_locks` sweeper (for stale lock rows, mentioned as a D-004 consequence) and the
Redis-expiry-miss sweeper (mentioned as a D-005 consequence) both lack an owning task, a job name,
or a `singletonKey` in `tasks.md` — CLAUDE.md's idempotency principle requires every background job
to have one.

### S-3. G-04 from the sufficiency report (SC-002 latency target) is still open

The sufficiency report explicitly required the design phase to "state the target on its row (in
the no-delta amendment) so the build has a number to meet" for SC-002 (offer-issue latency ≤60s).
Neither `constraints-and-decisions.md` nor any other file in the package amends `concerns.md` or
adds an NFR row for this. `tasks.md` Cycle 2's test asserts the 60s behavior operationally, but
there's no recorded target/measurement mechanism analogous to AX-004/NFR-002 or AX-007/NFR-003. As
flagged, this gap survived the design phase unresolved.

### S-4. Money-moves-on-authority path for offer-accept isn't spelled out

CLAUDE.md's blocking principle requires `authorisedBy` non-null on every `Payment` row, and the
baseline's `Booking–Payment` relationship implies a real `Payment` row per charged booking. The
FEAT-031 delta puts `stripePaymentIntentId` directly on `Offer` rather than describing whether/how
an accept creates a `Payment` row (with `authorisedBy` set to the accepting owner) once the booking
is confirmed. `contracts/api.yaml`'s `HoldReceipt` response (receiptId, bookingId, chargedMinor,
currency) doesn't reference a `Payment` id either. Not necessarily wrong, but the package doesn't
show the seam, and this is exactly the kind of money-flow detail the baseline treats as
non-negotiable.

## Minor / consistency

- `data-model.md`'s `Notification` entity cites **"Traceability: FR-007"** — `spec.md` only
  defines FR-001–FR-006. This is a dangling reference (see spec-gap note below for the likely root
  cause).
- `entry–offer` relationship is `Cascade` and `offer–booking` is `Restrict`. Since `WaitlistEntry`
  appears to be soft-deleted via its `status` enum (`left`, `expired`) rather than hard-deleted,
  the cascade behavior may never fire — worth confirming entries are never hard-deleted, otherwise
  an accepted offer with a live booking would make the cascade fail against the Restrict on
  `offer–booking`.
- `design-disclosure.md`'s ladder doesn't include a row for the availability-forecast's data
  model or for `Notification`, despite both being `[NEW]` — the disclosure looks like it undercounts
  what actually shipped in the package relative to what B-2 found in the contract/tasks files.

## Gaps in the spec itself (for the requirements analyst)

- **No umbrella FR for notifications.** The word "notified" / "told" appears three times across
  US-2 and the edge cases (offer issued, charge declined, entry expired) but there's no FR
  covering owner notification as a requirement in its own right. That's very likely why the design
  phase had to invent an untraceable `FR-007` for the `Notification` entity (see minor note above)
  — the spec gives it nothing to point at.
- **"A berth frees" is never operationally defined.** SC-002 measures latency "from the booking
  release commit," but the spec doesn't say what event constitutes a release given `FEAT-034`
  (cancellation) doesn't exist yet — today the only path is `Booking active → completed` on
  `endsOn`, which is a scheduled transition, not something instantaneous. Worth spelling out
  whether the waitlist is expected to react to *any* berth-freeing event or only the
  season-end transition, since that materially affects whether a 60s p95 target is even reachable
  and shapes what the design phase should have specified for the trigger (see S-2).
- **C-006's `[NEEDS CLARIFICATION]` (does marketing consent gate the offer e-mail, or is it
  transactional?) is a spec-level question**, not a design one — it turns on what the owner agreed
  to at signup, which the design phase can't resolve on its own. Flagging so it doesn't sit
  unresolved into build.
- **No stated cap or re-evaluation on "skipped entrant keeps their position."** If an entrant's
  vessel is oversized for the berth class's mix of berths, the edge case as written could leave
  them parked ahead of everyone else indefinitely with no berth ever fitting them. Not clearly a
  bug, but the spec doesn't say whether that's accepted behavior or worth a bound.
