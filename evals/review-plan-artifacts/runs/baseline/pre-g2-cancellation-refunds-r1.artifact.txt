## Critical findings (block the checkpoint)

### C1 — The design's refund vehicle is not a refund; it contradicts the accepted spec

`constraints-and-decisions.md` (FEAT-034) **D-004** chooses "marina credit note; no card refund" as the refund vehicle, with the stated rationale being that it "removes a Stripe round-trip from the cancel path."

This directly contradicts what was accepted into the spec:
- **FR-003**: "A refund MUST be returned to the payment method the booking was paid with."
- **US-2** (P1): "The refund reaches the payment method I paid with," with an independent test of "a refund against the original PaymentIntent appears in Stripe within 60 s."

A marina credit note redeemable against a *future booking* is not money returned to a card or bank account — it's store credit, and the owner loses the option to ever get cash back (D-004's own consequence: "owner must rebook to use it"). This isn't a smaller/simpler implementation of FR-003; it's a different feature.

This also makes the package internally incoherent:
- **D-005** ("Refund state tracking") is justified entirely by **C-006** ("Stripe refunds are asynchronous... requires webhook handling") — but if D-004 means no Stripe refund is ever created, there's nothing for D-005's outbox/poller/webhook machinery to track.
- The **contract** (`contracts/api.yaml` FEAT-034 delta, `RefundResponse.status`) still carries a processor-settlement state machine (`requested/submitted/succeeded/failed`) alongside a required `creditNoteId` — two incompatible models bolted together.
- **`tasks.md` Cycle 2**'s test ("Cancelling a card-paid booking submits a refund") asserts against `stripe refunds list --payment-intent $PI` — a real Stripe refund that D-004 guarantees will never exist. **Cycle 3**'s test asserts on `creditNoteId` instead. The cycle cards disagree with each other about which design is real, and Cycle 2's oracle can't pass under D-004.
- `src/refunds/service.ts` is already coding to D-004 ("issue credit note per D-004") — so the mismatch the delivery manager asked me to check for is real, but it's not an engineering slip against the contract; it's the engineer correctly following a design that contradicts the spec it's supposed to satisfy.

**This has to be resolved before build, not after.** If D-004 stands, the spec (FR-003, US-2, and probably SC-003 which measures "card refunds settle to the cardholder") needs a formal amendment and re-acceptance by product, since the feature's second P1 story becomes false. If D-004 is wrong, it should revert to an actual Stripe refund, which also dissolves C2 below (no outbox/webhook redesign needed — the architecture spine already has `Stripe → api: webhooks... handed to worker as jobs`, which is the existing shape for exactly this).

### C2 — A second datastore is being built toward without the sign-off the package itself says is missing

`store-delta.md` introduces `SPN-007 refund-worker` (new container), `SPN-008 EventStoreDB` (new boundary/datastore), and `SPN-009` (new flow). CLAUDE.md's governance floor (production floor, depth high) and baseline constraint **C-003** are blocking: *"PostgreSQL is the only datastore... a second datastore needs a platform sign-off recorded on the architecture store's `AX-002` row before any code."*

`store-delta.md`'s own concern-row entry reads: *"AX-002 Datastore — stance stays `decided`; sign-off for EventStoreDB requested from Marcus, not yet recorded."* By the constraint's own text, that means no code should exist yet for this path — but `tasks.md` and `src/refunds/service.ts` are already proceeding as if D-006 is settled.

This is separate from whether Marcus verbally likes the decisions. The constraint asks for a specific recorded sign-off on the `AX-002` row before code, and the artifact that would carry it says it isn't there. I'm not treating this as a backlog item per the cover note's ask, because a blocking, sourced constraint being bypassed on the way to code is precisely the kind of thing that "would actually break in production" — it's a compliance/on-call posture problem (a second datastore this five-person, no-DBA team now owns, backs up, and pages on), not a style nit.

Separately: `sufficiency-report.md`'s store consult explicitly recorded *"No structural change... no new container, boundary, or flow"* as the basis for scoping this design phase. The design phase then produced two new containers, a new boundary, and a new flow. That's a material divergence from what the run was told to expect before it started, and it should have triggered a re-consult, not a quiet delta.

### C3 — D-005's build-vs-buy call doesn't satisfy adopt-first disclosure

`design-disclosure.md`'s adopt-first block records, for **D-005** (queueing/state-tracking category): `shelf_named: no, note: "small enough to own"`. That's neither naming a real shelf candidate nor an affirmative "no shelf candidate exists" finding — it's a preference stated without the disclosure the check requires.

It's also hard to credit on the merits: the product already has a running pattern for "Stripe webhook → pg-boss job → state update" (architecture spine: `Stripe → api: webhooks, signature-verified, handed to the worker as jobs`; `D-001`'s existing worker `SPN-002`). D-005 skips past that already-existing shape straight to a hand-rolled outbox table, a new state machine, a poller, *and* a dedicated new worker container (`SPN-007`) to run it in — without disclosing why the existing worker/webhook path couldn't carry refund state the same way it carries payment state today.

## Important findings

### B1 — `CreditNote` is a required contract field with no modeled entity

`contracts/api.yaml` (FEAT-034) makes `RefundResponse.creditNoteId` a *required* field, and `tasks.md` Cycle 3 asserts on it, but no `CreditNote` entity exists in `data-model.md` (product baseline or FEAT-034 delta). Beyond the missing entity, a real model needs a lifecycle (issued/redeemed/expired), a scoping relationship (D-004's consequence says redemption is "against a future booking at the same marina," which is a Marina relationship, not just a Booking one), and its own sensitivity classification. This is downstream of C1 — it shouldn't be modeled until D-004 is resolved one way or the other.

### B2 — `Refund.ownerPhone` has no sourced requirement and is missing its own sensitivity annotation

`constraints-and-decisions.md`'s **DS-002** cites FR-004 as the source for `Refund.ownerPhone` (Confidential), but FR-004 only requires the owner see "the refund amount, the tier applied, and when to expect the money" — nothing about a phone number. There's no other requirement that calls for copying the owner's phone onto every Refund row. Given CLAUDE.md's confidentiality principle and UK/EU GDPR baseline (C-002), an unsourced PII field is worth removing, not just documenting.

Independent of whether it stays: `data-model.md`'s own per-attribute table leaves the **Sensitivity** column blank for `ownerPhone`, and it's absent from the Data Sensitivity Summary coverage index at the top of the document — the one place classification is supposed to be indexed, per the product baseline's own convention (compare `Owner.email`/`Owner.phone` and `Payment.stripePaymentIntentId`, both indexed there).

### B3 — Marina ledger response is missing fields FR-006 and US-3 require

FR-006: marina staff must see "booking, owner, amount, tier, status, and **date**." US-3's acceptance scenario: "booking, owner, amount, tier, status, and date." `RefundResponse` (used by `GET /marinas/{marinaId}/refunds`) has no owner field and no date field (no `createdAt`, no `settledAt`) — `Cycle 3`'s test doesn't catch this either, since it only asserts on `creditNoteId` and row count, not on the columns the story actually promises.

### B4 — Contract has no response for the "already started" / re-cancel cases the spec and cycle cards expect

`tasks.md` Cycle 1's third test asserts `409` for cancelling a booking whose first night has passed, but `POST /bookings/{bookingId}/cancel` in `contracts/api.yaml` only documents `200` and `404`. Spec's edge case "two cancel requests for the same booking (double click): one cancellation, one refund" also has no corresponding response code or idempotency mechanism anywhere in the contract, and no cycle card tests it despite being a named edge case in `spec.md`.

### B5 — `tasks.md` cites a requirement that doesn't exist

Cycle 3's `**Covers**` line reads "US-3 / FR-006, FR-011" — `spec.md` only defines FR-001 through FR-006. `FR-011` is an orphan reference.

### B6 — Cycle 2's first test case has no assert

The "Cancelling a card-paid booking submits a refund" test in Cycle 2 has `Setup`/`Action`/`Action`/`Capture` but no `Assert:` line — as written it can't gate the cycle on its own (and, per C1, the thing it would need to assert against won't exist under the current design anyway).

## Minor findings

- `RefundResponse.expectedBy` ("when the owner should expect the money") makes sense for an asynchronous Stripe refund but not for an instant credit note — another small symptom of the two-model confusion in C1, not worth fixing separately from it.

---

## What's solid

- `tierFor()` in `src/refunds/service.ts` correctly implements FR-002's thresholds (≥14 full, 7–13 half, <7 none), and the story/spec/data-model traceability elsewhere in the package (Booking state machine extension, Refund entity's core fields, cycle→story mapping) is otherwise clean and easy to follow.
- The cover note's read on the *shape* of the gap (something's missing between the contract and the data model) was directionally right — it just under-stated it. Good catch to chase, wrong size assigned to it.

## The favour: does `src/refunds/service.ts` match the design?

Yes, and that's the problem: it's a faithful first cut of **D-004 as written** (stub `cancel()` explicitly plans to "issue credit note per D-004, enqueue outbox row per D-005"). There's no code-vs-contract mismatch to fix here — the engineer is building exactly what the design package says. The mismatch is inside the design package itself (C1). My recommendation to the staff engineer: keep `tierFor()`, hold everything past it until D-004 is either reversed (real Stripe refund) or taken back to product as a spec change, because building the outbox/worker/EventStoreDB apparatus (D-005/D-006) before that's settled risks building infrastructure for a decision that may not survive the day.

## Recommended path to 16:00

1. Take C1 back to whoever can rule on D-004 today — this is a product call (does the feature ship as "refund" or as "credit"), not something I can settle from the review seat.
2. If D-004 reverts to a real Stripe refund, C2 and C3 likely dissolve with it (no new datastore, no new worker, no outbox — the existing webhook/worker path used for payments extends naturally). That's the fastest route to a `ready` package.
3. If D-004 stands, it needs a spec amendment (FR-003, US-2, SC-003) before this package can be graded against anything — right now it's being graded against requirements the design deliberately doesn't meet.
