## Critical findings

### C1. D-004 replaces the promised cash refund with a marina credit note — contradicts the spec

`constraints-and-decisions.md` D-004 chooses "marina credit note; no card refund" as the refund
vehicle. This directly contradicts:
- **FR-003**: "A refund MUST be returned to the payment method the booking was paid with."
- **US-2** (P1): "the refund reaches the payment method I paid with."
- The spec's own edge cases: an expired card still gets a Stripe refund via the scheme; a Bacs
  payment refunds to the same bank account. Neither is possible if there is no card/Bacs refund at
  all.
- **SC-003**: "95% of card refunds settle to the cardholder within 5 business days" — meaningless if
  no card refund is ever created.

This isn't a documentation lag: `tasks.md` Cycle 2's first `**TEST:**` still asserts against a real
Stripe refund (`stripe refunds list --payment-intent $PI`), which will find nothing once D-004 ships,
because D-004 removes the Stripe refund call entirely. The design package contradicts itself, not just
the spec. `src/refunds/service.ts`'s TODO ("issue credit note per D-004") shows the staff engineer is
already coding toward this — worth stopping before more code lands on it.

**This should go back to the technical analyst**, not forward. Either the spec's FR-003/US-2/SC-003
were wrong to promise cash-back (a product call, not a technical one), or D-004 needs to be a real
Stripe refund with the credit-note idea dropped or rescoped as an *additional* option, not a
replacement.

### C2. D-006 / SPN-008 introduces a second datastore without the required sign-off

`CLAUDE.md`'s governance floor: "PostgreSQL is the system of record and the only datastore... No
second datastore ships without a platform sign-off recorded on the architecture store's `AX-002` row
before any code." `store-delta.md`'s own Concern rows table says: "sign-off for EventStoreDB requested
from Marcus, not yet recorded." The package proceeds to `tasks.md` cycle cards anyway.

This is a blocking, production-floor principle, not a style preference, and the note explicitly
requires the sign-off to be *recorded on the AX-002 row* before code — not merely requested. The
architecture spine (`.mochiko/product/architecture/concerns.md` AX-002) confirms: "Sign-offs recorded:
none."

Worth adding: `constraints-and-decisions.md`'s own D-006 table lists a one-datastore alternative
("Append-only `refund_events` table in PostgreSQL... One datastore; trivially queryable") that
satisfies FR-006 (a projection/read model over an append-only table is a normal pattern). The
disclosed rung for D-006 is "1 required" (`design-disclosure.md`), but a same-store option that meets
the requirement exists on the same page — "required" is not an honest rung claim for a second
datastore when Postgres can do the job.

**This should not proceed past the checkpoint without Marcus's sign-off recorded on AX-002**, or a
swap to the Postgres-native option already evaluated and rejected only for projection convenience.

### C3. The sufficiency report's "no structural change" claim is false against the package it gated

`sufficiency-report.md`: *"No structural change: cancellation and refunds ride the existing api,
worker, db and the standing Stripe boundary; no new container, boundary, or flow."* `store-delta.md`
then adds SPN-007 (new container, refund-worker), SPN-008 (new boundary, EventStoreDB), and SPN-009
(new flow). That's two new containers/boundaries and a new flow — the opposite of "no structural
change."

This matters beyond bookkeeping: the no-delta claim is what determined how light a design pass this
feature got (no sequence-diagram obligation flagged, no architecture-desk walk recorded beyond the one
AX-002 row). If the claim had been accurate about the structural footprint, the design phase would
likely have been scoped differently from the start.

## Important findings

### I1. `CreditNote` is a required contract field with no backing entity

`contracts/api.yaml`'s `RefundResponse` requires `creditNoteId`, but no `CreditNote` entity exists
anywhere in `data-model.md` — no attributes, no relationships, no redemption/expiry rules, no
sensitivity classification. The cover note calls this "a five-minute add to `data-model.md`." It
isn't: `CreditNote` is downstream of C1. Modeling it now would quietly ratify the credit-note-replaces-
cash-refund decision before that decision has actually been settled. I've left it unmodeled pending C1.

### I2. `Refund.ownerPhone` sensitivity classification is declared but not applied

`constraints-and-decisions.md` DS-002 declares "Refund.ownerPhone (Confidential)." In
`data-model.md`'s Refund entity table, the `ownerPhone` row's Sensitivity column is **blank**, and
`ownerPhone` does not appear in the entity's Sensitivity Details section at all (no retention, no
access rule, no masking note) — unlike `stripeRefundId`, which gets a full row. `CLAUDE.md`'s
governance floor is explicit that owner contact details are Confidential/Restricted and must never
appear in logs, exports, or error bodies; an unclassified phone-number field is exactly the kind of
gap that skips the redaction list.

### I3. `tasks.md` Cycle 3 cites a functional requirement that doesn't exist

Cycle 3's TEST covers "US-3 / FR-006, **FR-011**." The spec (`spec.md`) only defines FR-001 through
FR-006. FR-011 is not defined anywhere in the feature. Broken traceability — either a typo for another
ID or a requirement that was never authored.

### I4. `tasks.md` Cycle 2's first TEST case has no assertions

"Cancelling a card-paid booking submits a refund" has two `**Action**` lines and a `**Capture**`, but
no `**Assert**` at all. As written this card can never fail — there's no oracle. (It also can't
meaningfully be fixed until C1 is resolved, since the action it's built around — checking Stripe for a
refund — won't apply if D-004 stands.)

### I5. The spec's double-cancel edge case has no corresponding test

Spec edge case: "Two cancel requests for the same booking (double click): one cancellation, one
refund." No cycle card in `tasks.md` exercises concurrent/duplicate cancel calls. Given the project's
"every background job is idempotent" governance principle and that refund submission is meant to run
through a `singletonKey`'d job, this is a real, explicitly-scoped gap, not an edge case that fell out
naturally — it's named in the spec and not covered anywhere in the plan.

### I6. SPN-009's sequence diagram is missing, not just pending

`store-delta.md`: "Sequence diagram for SPN-009 to follow." SPN-009 crosses into a new boundary
(EventStoreDB) and a new container (refund-worker) and touches the standing Stripe boundary — this
qualifies for a sequence diagram under the architecture-delta discipline, and it isn't in the package.

### I7. SC-001's latency target has no concern-row landing

`sufficiency-report.md` flagged `AX-004/NFR-002` and `AX-007/NFR-003` as the applicable NFR targets
for this feature. Neither `store-delta.md` nor `constraints-and-decisions.md` says how SC-001 ("refund
initiated within 60s of cancellation, p95") is measured or which concern row (existing or new) owns
it. Flagged in advance, not answered in the package that followed.

## Minor / advisory (rung-claim honesty, adopt-first)

- **D-005** (`refund_outbox` hand-rolled table + poller) is disclosed at rung "2 simpler shape," with
  adopt-first recorded as "no shelf candidate, small enough to own." The product already runs pg-boss
  for exactly this kind of durable, transactional, at-least-once job dispatch (`D-001`, and it's the
  literal arrow from `api` to `refund-worker` in this same delta diagram). The disclosure doesn't
  explain why the outbox-plus-poller pattern isn't just a pg-boss job with retry/backoff, which is the
  standing, already-adopted mechanism for "something needs to happen reliably later." Not blocking —
  a real "no" was recorded — but the justification is thin given the obvious candidate sitting in the
  same diagram.
- (Folds into C2 above) D-006's rung-1 "required" claim is optimistic given the Postgres-native
  alternative on the same decision table.

  this further: don't build the credit-note path or the EventStoreDB projection until C1 and C2 are
  resolved, since both are live candidates for reversal.
