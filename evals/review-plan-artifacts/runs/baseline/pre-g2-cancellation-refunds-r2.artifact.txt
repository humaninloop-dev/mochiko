## Clarifications needed

### C1: Refund vehicle — cash back to the original method, or a marina credit note? (G1)

**Question**: FR-003, US-2, both spec edge cases, and SC-003 all describe money returning to the card or bank account the owner paid with. D-004 chose a marina credit note specifically to avoid a Stripe refund call. Which is the actual product intent?
**Options**: 1. Follow the spec as written — real Stripe refund to the original method; drop D-004 and creditNoteId. 2. Follow D-004 — credit note only; formally amend spec.md (FR-003, US-2, the expired-card and Bacs edge cases, SC-003) to match, since as written they promise cash back. 3. Hybrid (credit note as the default, cash refund as an owner-facing option) — not specified anywhere today and would need its own FR.
**Why it matters**: this shapes data-model.md, contracts/api.yaml, and Cycles 1-3 of tasks.md. Shipping the current mixed package means half the built surface expects a Stripe refund event that D-004 says will never be created.

### C2: Is the EventStoreDB sign-off actually landing before code starts? (G2)

**Question**: store-delta.md records the AX-002 sign-off for a second datastore as requested but not recorded. C-003 is blocking: no second datastore ships without it.
**Options**: 1. Get Marcus's sign-off recorded on AX-002 before the checkpoint clears this package. 2. Swap D-006 to the Postgres append-only table already named in its own alternatives table — no sign-off needed, and it satisfies FR-006 as specified. 3. Ship the first cut without EventStoreDB/SPN-007/SPN-008 and revisit post-checkpoint as a separate proposal.
**Why it matters**: proceeding past this checkpoint with the sign-off still absent means the build starts against a floor-asserted constraint that hasn't been cleared, not a paperwork gap to backfill later.
