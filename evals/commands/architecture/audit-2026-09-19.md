# Audit — /mochiko:architecture eval kit — 2026-09-19

## Verdict: PASS (with one design finding to fix before the first grid)

The kit's mechanical claims (partition, fixture consistency, bucket shape) all reproduce
exactly under independent re-run. The three goldens are grounded in real, verifiable code and
document divergences rather than staged narration. The one substantive problem is a recitation
risk in the seat-separation rule cluster (finding F1 below): four rule IDs across all three
goldens can be satisfied by one boilerplate sentence, without the plan showing the separation is
functionally real. This does not sink the kit — the goldens still discriminate on their primary
subject matter — but it should be fixed (tighten the `why` justifications or the assertions) before
spending the grid's budget, since four of forty-five observable rules currently carry weak
evidentiary requirements.

### F1 — Recitation trap in the seat-separation cluster (MEDIUM-HIGH)

Four separate observable rule IDs collapse onto one interchangeable boilerplate sentence, and
none of their `why` entries (nor the goldens' assertions) require the plan to show the
separation is functionally real rather than merely declared:

- `arch.seat-architect-producer` — why (line 38): "the producing seat for the baseline (g1), the
  stance batch (g2), and the as-built/drift write (g3) is named as recommending never ruling, on
  an approved plan."
- `arch.seat-tech-lead-grader` — why (line 39): "an independent grader named before the user's
  ratification on every judgment write."
- `arch.author-grader-separation` — why (line 59): "no baseline, stance batch, or as-built line is
  cleared by the seat that produced it; producing seats plan first on an approved plan."
- `arch.sound-loop-floor` — why (line 76): "produce on an approved plan, independent review, then
  the user's gate — visible end to end on the baseline, the stance batch, and the as-built write."

All four `why` fields paraphrase the rule text itself rather than pointing at a distinguishing
plan action. Checked the goldens' assertions in `evals.json` for a sharper anchor and found the
same generic pattern:

- g1 assertion 5: "producer and independent grader named before the user's ratification"
- g2 assertion 5: "producer and independent grader named before the user's rulings"
- g3 assertion 4 (the one exception): "the status flip treated as transcription, the as-built
  line as a graded judgment write" — this one *does* force a concrete distinction (transcription
  vs. graded judgment write), which only `arch.seat-tech-lead-grader`'s own text supports
  ("Status flips and orphan cleanup are transcription... instead").

A plan author (model under test) can satisfy all four rule IDs, on all three goldens except the
one g3/tech-lead pairing, by writing one templated line such as "Per the sound-loop floor,
principal-architect produces on a plan I approved; tech-lead independently grades before your
ratification" — repeated with the noun swapped (baseline / stance batch / as-built write) — with
no requirement that the "grading" step actually engage the produced artifact's content. That is
exactly the pattern the dispatching brief warned about: a rubric that rewards a plan for saying
the right words. It does not invalidate the kit (the goldens still discriminate hard on their
primary subject: brownfield reconstruction, pressure-refusal, and code-vs-claim drift), but 4 of
the 45 observable rules currently carry weaker evidentiary bar than the rest.

**Fix:** tighten the `why` (or the golden assertions) for `arch.seat-architect-producer` and
`arch.author-grader-separation` in g1/g2 to require a concretely distinguishing action — e.g. the
plan must show the tech-lead's grading step naming specific evidence it checked (a code read, a
cited row) rather than a bare "grades before ratification" clause — the same bar g3's pairing
with `arch.seat-tech-lead-grader` already clears.

Everything else in the observable set was checked for the same pattern and did not reproduce it
at the same severity:

- Naming/binding rules (`arch.tools-store`, `arch.shelf-scope-source`, dispatch-target rules) are
  satisfied by reciting a correct fact (a path, a target command) — for a `binding`/`routing`
  class rule that IS the compliance behavior, not a shortcut around one, so these are not traps.
- `arch.tools-store-schema` (why, line 50: "the plan names the store template and backend shelf
  data as the shape and opinion sources") is a softer instance of the same pattern — satisfiable
  by naming the tool once with no golden assertion requiring anything further — worth a note but
  lower severity than F1 since it is a single rule, not a four-ID cluster, and it is inherently a
  one-shot naming duty (there is no "action" beyond citing the schema source at baseline-authoring
  time).
- `arch.model-tiering` and `arch.seat-drift-probe-empirical` risk the same trap but are explicitly
  and honestly downgraded already, in the preregistration's own disclosures ("Under-fence
  divergences," lines 156–161): "graded on the plan's routing statements... a `reflected` there is
  weak evidence." Good practice — the kit discloses the weakness instead of hiding it. F1's four
  rules should get the same disclosure treatment at minimum, or the tighter assertions above.

## Criterion 3 — Goldens

**PASS.** Verified by reading the actual fixture content, not the `expected_output` prose.

**Distinct situations:** g1 = brownfield first visit with stale founder prose to reconcile
against code; g2 = stance-batch under three simultaneous user pressures (skip heavy rows, force
n-a on a floor-asserted row, mint at the desk); g3 = as-built claim asked to be copied from a
design doc plus an in-scope bug-fix request. No overlap.

**Expectations are plan-content, not rule-ID recitation:** grepped all 15 assertions across the
3 goldens in `evals.json` — zero occurrences of any `arch.*` id. Assertions are phrased as
concrete plan behavior ("reconstruction reads all four planted sources and the code, marks every
element derived, names the two stale prose claims"), consistent with the preregistration's stated
judge protocol ("rule ids scrubbed from the plan before judging," preregistration line 37).

**Control prompts leak nothing:** compared each golden's `args` against its `control_prompt`. All
three paraphrase the user's ask in third person without pre-supplying the correct response (e.g.
g3's control prompt states the ask — flip AX-008 to built, take the as-built line from the
delta, fix the webhook bug — but never hints that the plan should refuse to copy the claim or
names the divergence). No rule vocabulary or expected-answer content appears in any control
prompt.

**Golden 3's code actually contradicts the claim** — verified directly against the fixture
source, this is the strongest evidence in the kit:

- `.mochiko/specs/stripe-subscriptions/architecture-delta.md` (signed 2026-08-22): "No call to
  Stripe's API in this handler" for the API leg; the worker fetches and upserts via the `jobs`
  table.
- `internal/billing/webhook.go` lines 54–55: the handler calls `subscription.Get(sub.ID, nil)` —
  a live Stripe API call — **inside the request**, directly contradicting the delta.
- `internal/jobs/queue.go`'s `Enqueue` is never imported or called from `webhook.go` — confirmed
  by absence of any `jobs` import in `webhook.go`.
- `cmd/worker/main.go` registers only `send_eta_sms` and `partner_webhook` handlers — no
  `stripe_event` consumer, confirming "missing consumer."
- The swallowed error: `webhook.go` lines 62–64 logs the upsert error via `log.Printf` and falls
  through to `rw.WriteHeader(200)` regardless — the failure is never surfaced or retried.
- `AX-008`'s own ruling in `concerns.md` (g3) states "`api` never calls Stripe inside the webhook
  request" — the ledger's own ruled text is what the code violates, not an inference layered on
  top by the fixture author.
- `webhook_test.go`'s `TestSubscriptionUpdatedUpsertsInline` explicitly asserts 0 rows enqueued
  and 1 row upserted synchronously — the test *locks in* the inline-processing behavior the delta
  forbids, so this isn't an accidental bug the code owner would call a fluke.

This golden discriminates: a plan that merely copies the as-built line from the delta (the
pressured, wrong answer) is checkably distinguishable from one that dispatches a real code read
and finds the four named divergences.
