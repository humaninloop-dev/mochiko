## 2. The nine out-of-instrument rules, one at a time

`observable.yaml:57-69`. For each: does the justification hold, or is it parking-for-convenience?

| Rule | Justification (`observable.yaml`) | Ruling |
|---|---|---|
| `brainstorm.staffing-latitude` | latitude — "Teammates or subagents per seat is your call" (schema line 25-ish, `staffing-latitude`) | **Legitimate.** The rule only grants freedom; any staffing choice satisfies it, so nothing is falsifiable. |
| `brainstorm.register` | register — `extends: common.register`, text "User-facing prose follows templates/output-style.md" (schema:142, `common.register` text in `plugins/mochiko/migrations/0001-genesis.yaml:9768-9770`) | **Legitimate.** This is a style/register constraint on all output, not a scenario-concrete plan action; the coverage judge grades content embodiment, not prose register. |
| `brainstorm.pair-maps-independent` | conditional — binds only if the lead's staffing call composes a *review pair* (schema:65-69) | **Legitimate, but flagged for the maintainer's awareness (LOW).** This requires *two* reviewers, a resourcing choice under `staffing-latitude`, not a described process branch every run walks through. None of the three goldens' topics are consequential enough to reliably nudge a model toward spawning two reviewers, so it is a genuinely different shape of unobservability than the "thin reads" below (see F2 in Open Questions). Could be planted with a topic line that explicitly asks for two independent reviewers, but that's a real scenario-design act the authors correctly declined to force. |
| `brainstorm.plan-approval-producers` | conditional — binds only if a seat other than the lead writes an artifact; the run's only seats are the review seat (exempt as grader) and fact-finding dispatches (exempt) (schema:165-168, extends `common.plan-approval-producers`) | **Legitimate — actually stronger than the label says.** Re-reading `common.plan-approval-producers`'s own text (`0001-genesis.yaml:9806-9810`): "grading and fact-finding seats are exempt." Brainstorm's command structure (per the derived view's roles/tools sections) never spawns a third seat type. This is not merely "no fixture plants it" — no fixture *could* plant it without redesigning the command itself. Correctly parked, if arguably mislabeled "conditional" rather than "structurally inapplicable to this command." |
| `brainstorm.reopen-born-verify` | contingency — "fires only after a coverage survivor exists and the user reopens it; a forward plan carries it at most as a hypothetical branch" (schema:178-182) | **FAIL — see finding F1 below.** This reasoning is inconsistent with how the kit already treats sibling contingent rules. |
| `brainstorm.fail.record-unaccepted` | fail-condition | **Legitimate.** `enforces: [brainstorm.user-record-acceptance]` (schema) — the enforced rule is already graded observable; grading the fail-condition separately would double-count the same plan content under an end-state framing the judge doesn't naturally read from a forward plan. |
| `brainstorm.fail.unreviewed-no-waiver` | fail-condition | **Legitimate.** `enforces: [brainstorm.record-review-independence, brainstorm.user-review-waiver]`, both already observable. |
| `brainstorm.fail.survivor-undispositioned` | fail-condition | **Legitimate.** `enforces: [brainstorm.coverage-survivor-routing, brainstorm.non-coverage-survivors]`, both already observable. |
| `brainstorm.fail.index-mismatch` | fail-condition | **Legitimate.** `enforces: [brainstorm.index-bookkeeping]`, already observable. |

**Finding F1 (the one I'd move back to observable) — `brainstorm.reopen-born-verify`.**
Its own reason text calls it a contingency because it "fires only after a coverage survivor
exists and the user reopens it." But `brainstorm.coverage-survivor-routing` — the sibling rule
governing the exact same run-time event chain (survivor exists → user rules explore-now /
rule-inline / defer) — is graded **observable**, on the justification that "the disposition
gate presents each coverage gap as a candidate topic with the user ruling explore-now /
rule-inline / defer" (`observable.yaml:34`): a described branch, not an actually-fired one. The
kit already extends this same treatment to `brainstorm.user-survivor-challenge` and
`brainstorm.user-pen-boundary`, explicitly named "thin reads" in `preregistration.md:55-58`
("graded on one described branch each"). `reopen-born-verify` describes the very next link in
that same chain — what happens to the decision that an "explore now" ruling produces — and is
just as describable in a forward plan: *"if the disposition gate's explore-now path is taken,
the resulting decision gets one bounded verify round — internal consistency and record-fitness
only, no fresh cold read, no blind-map hunt, no second reopen off it."* That is exactly the
grammar the read rule already credits as embodiment (`preregistration.md:81-82`: "a described
user gate with what is confirmed and the onward branch per ruling is a concrete action (D9)").
There is no principled reason to grade `coverage-survivor-routing`'s branch as observable while
parking its very next link as contingency — the distinction drawn in the reason text does not
survive comparison to its own sibling rule.

This is a real inconsistency in the partition's stated logic, not a fatal defect: the practical
fix is cheap (move the rule to `observable`, extend one golden's `expected_output`/`assertions`
— most naturally s1's, which already has "survivor disposition gates that split coverage gaps
... the user routes" — to also state the bounded-verify follow-on). I'd rate this MEDIUM
severity: it doesn't invalidate anything already measured, but it under-counts the 21-rule
observable set by one rule that the kit's own precedent says should be gradable.

## Fix list (ordered by severity)

1. **MEDIUM — F1.** `brainstorm.reopen-born-verify` is parked as "contingency" on reasoning
   that does not survive comparison to `brainstorm.coverage-survivor-routing` (observable) and
   the kit's own named "thin reads" (`user-survivor-challenge`, `user-pen-boundary`), which get
   credit for describing the identical class of hypothetical branch. Recommend moving it to
   `observable.yaml`'s observable list and extending one golden (s1 is the natural fit, since
   its `expected_output` already touches the disposition gate) to state the bounded-verify
   follow-on as a described branch.
2. **LOW — labeling nit.** `brainstorm.plan-approval-producers`'s reason is written as
   "conditional" (implying it *could* bind under some scenario) when the underlying fact is that
   brainstorm's command structure never composes a producing seat other than the lead at all —
   it is closer to structurally inapplicable than conditional. No fixture-design consequence,
   just imprecise vocabulary.
3. **LOW — worth a one-line note, not a fix.** `brainstorm.pair-maps-independent`'s parking is
   correct but rests on a different mechanism (a discretionary resourcing choice under
   `staffing-latitude`) than the "no fixture plants the condition" framing used for
   `plan-approval-producers` right next to it. Not wrong, just worth the maintainer
   distinguishing the two out-of-instrument sub-reasons if this rubric is ever re-cut.
