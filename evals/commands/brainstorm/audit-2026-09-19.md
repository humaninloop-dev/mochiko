`observable.yaml:57-69`. For each: does the justification hold, or is it parking-for-convenience?

**Finding F1 (the one I'd move back to observable) — `brainstorm.reopen-born-verify`.**
Its own reason text calls it a contingency because it "fires only after a coverage survivor
exists and the user reopens it." But `brainstorm.coverage-survivor-routing` — the sibling rule
governing the exact same run-time event chain (survivor exists → user rules explore-now /
rule-inline / defer) — is graded **observable**, on the justification that "the disposition
gate presents each coverage gap as a candidate topic with the user ruling explore-now /
rule-inline / defer" (`observable.yaml:34`): a described branch, not an actually-fired one. The
kit already extends this same treatment to `brainstorm.user-survivor-challenge` and
`brainstorm.user-pen-boundary`, explicitly named "thin reads" in `preregistration.md:55-58`
("graded on one described branch each"). `reopen-born-verify` describes the very next link in
that same chain — what happens to the decision that an "explore now" ruling produces — and is
just as describable in a forward plan: *"if the disposition gate's explore-now path is taken,
the resulting decision gets one bounded verify round — internal consistency and record-fitness
only, no fresh cold read, no blind-map hunt, no second reopen off it."* That is exactly the
grammar the read rule already credits as embodiment (`preregistration.md:81-82`: "a described
user gate with what is confirmed and the onward branch per ruling is a concrete action (D9)").
There is no principled reason to grade `coverage-survivor-routing`'s branch as observable while
parking its very next link as contingency — the distinction drawn in the reason text does not
survive comparison to its own sibling rule.

This is a real inconsistency in the partition's stated logic, not a fatal defect: the practical
fix is cheap (move the rule to `observable`, extend one golden's `expected_output`/`assertions`
— most naturally s1's, which already has "survivor disposition gates that split coverage gaps
... the user routes" — to also state the bounded-verify follow-on). I'd rate this MEDIUM
severity: it doesn't invalidate anything already measured, but it under-counts the 21-rule
observable set by one rule that the kit's own precedent says should be gradable.

### Ruling 1 — is a branch-only, no-scenario-forces read worth its place in the denominator?

Keep it in. It will not read absent across the board — `coverage-survivor-routing` describes
the same event chain's outer shell and is already a normal (non-thin) observable rule the
goldens' own `expected_output` text engages with directly (e.g. `evals.json:7`'s "survivor
disposition gates that split coverage gaps... the user routes"), so a plan that engages with
the disposition gate at all has a real, non-zero chance of also stating the bound on what
comes out of the explore-now branch, especially since the rendered rule text
(`brainstorm.reopen-born-verify`'s full text) is always in the model's context regardless of
golden — delivery doesn't gate on `when:` resolution, only applicability does.

That said, I'd expect it to run flakier than `user-survivor-challenge` and
`user-pen-boundary`, not equally stable — it's nested one hypothetical layer deeper (survivor
exists → user picks explore-now → *then* the reopened decision's own bound) where its two
siblings are nested only one layer (survivor exists → it happens to challenge a ruling /
amend one). A plan is more likely to spontaneously state "the user rules on any survivor that
challenges a prior decision" than to also spontaneously append "...and if they pick explore
now, the resulting decision gets exactly one bounded verify round, no fresh cold read, no
second reopen" — that's a more specific, more easily-dropped clause. So: legitimate signal,
worth the denominator seat, but likely the flakiest of the three thin reads rather than a
peer to them. This is exactly why it belongs in the "Thin reads, named now" disclosure
(gap 2 above) — so a low or split read on it is pre-classified as expected noise rather than
investigated as a surprise regression. Recommend adding it there and to the fill-log line
before the first grid, and watching in the fill log whether it in fact reads lower than its
two siblings — if it reads absent on literally every replicate across all three goldens,
*that* would be worth re-opening as a dead-rule finding, but one described branch with no
scenario forcing it is not the same claim as zero possible embodiment.

### Ruling 2 — should `brainstorm.plan-approval-producers`'s label change, and to what?

Yes, relabel it. The kit's own vocabulary legend (`observable.yaml:12-13`) defines
`conditional` as "observable only under a condition no current scenario plants (activating it
= planting the condition, **a scenario-design act**)" — i.e., plantable, just not planted.
That is true of `pair-maps-independent` (a topic line could ask for two reviewers) but not of
`plan-approval-producers`: per `common.plan-approval-producers`'s own text
(`plugins/mochiko/migrations/0001-genesis.yaml:9806-9810`, "grading and fact-finding seats are
exempt") and brainstorm's schema (roles/tools sections spawn only a review seat and
Explore-tier fact-finding dispatches), **no scenario, however designed, can plant a producing
seat in this command as currently specified** — doing so would require redesigning
`/mochiko:brainstorm` itself to add a third seat type, which is a command-design act, not a
scenario-design act. Calling it "conditional" invites a future reader to go looking for a
fixture or topic line that plants it, and no such fixture can exist without the command
changing first — that's wasted effort the mislabel specifically causes.

Recommend a new vocabulary term distinct from `conditional`, e.g. **`structural`**: "the
command's own seat wiring never composes the binding condition in any run — not a scenario
absence but an architecture fact; replant only if the command's role wiring changes." Add it
to the legend at the top of `observable.yaml` alongside the existing five terms, and re-tag
`brainstorm.plan-approval-producers` with it. `pair-maps-independent` stays `conditional` —
that one is genuinely plantable, just not planted.
