## 3. The missing positive control — FAIL (kit-failing per your framing)

**Claim verified.** Ran the partition myself against the authoring pin:

```
$ git merge-base --is-ancestor 49acf05 HEAD && echo yes-ancestor
yes-ancestor
$ uv run --with pyyaml python evals/commands/run.py partition feature --old-ref 49acf05
{ "unchanged": [...all 50 ids...], "changed": [], "removed": [], "added": [] }
```

All 50 rules land in `unchanged`; `changed`/`removed`/`added` are empty. `HEAD` at
`f1a662b` ("Add the feature command eval kit...") only adds the eval kit itself — no edit
to the `/mochiko:feature` pair exists between `49acf05` and `HEAD`. The author's claim is
correct: pre and post are text-identical at the baseline ref.

**Ruling: a kit with no positive control cannot, by construction, detect its own instrument
failure at this baseline run — and this specific kit does not compensate for that with
anything else that would.**

The project's own governing design record states the general principle plainly
(`.mochiko/brainstorms/primitive-eval-harness-v2/record.md:109`, D11): *"a positive control
is the only thing that separates 'no regression' from 'no signal'"* and explicitly
*"Rejected: no positive control (a null diff and a broken instrument look identical)."*
That ruling is written for the persona target — `evals/README.md:21`'s vocabulary table
scopes "positive control" as an addition required only for **personas**, not commands — so
this kit is not in violation of an explicit house rule. But the underlying epistemic problem
D11 names applies with equal force here, and the team's own risk framing ("if it cannot, that
is a FAIL-level finding regardless of how the rest reads") is asking about the epistemic
problem, not rule-compliance.

At this baseline run, pre and post run the *same command pair* rendering the *same rules*.
No rule can ever land in the regression bucket by construction — a "0 regressed rules"
reading is tautological, not evidence the judge/partition/scrub pipeline would catch a real
regression if one existed. Concretely, three failure modes this baseline read cannot rule
out:
- A judge that marks nearly everything `reflected` regardless of actual plan content
  (sycophancy, or a broken rule-id scrub letting lexical match through).
- `mochiko-cli` silently failing to render feature-specific rule content, so `post` plans
  degrade toward generic bare-model output.
- A judge with a systematic false-negative bias (under-detection), which looks identical to
  "the command genuinely doesn't reflect much."

The kit does carry two pieces of *circumstantial* mitigation, both real but neither designed
as a control:
- The `nocmd` dead-zone reading (`preregistration.md:24-28`) would surface gross judge
  leniency, since a lenient judge marks bare-model plans `reflected` too.
- Ship bar (a) and (c) (`preregistration.md:190-198`) implicitly test for gross
  non-differentiation — the 47 rules are idiosyncratic enough (e.g. `feat.epic-dispatch`,
  `feat.grooming-door-ceiling`) that a silently-broken render pipeline would likely fail many
  of them, and (c) explicitly calls out identical cross-golden profiles as a red flag.

Neither is pre-registered as a decision procedure with a "halt and re-key" trigger the way
the noise band or the stopping rule are (`preregistration.md:68-74`); both are read *after
the fact*, advisory, "informs, never gates" (`preregistration.md:188`). Nothing in this kit
validates, before or at the baseline grid, that the changed/removed/added bucket-computation
path (the actual regression-detection code in `run.py`'s `cmd_report`) has ever correctly
flagged a real, known change in this command's rubric.

The author's own framing — "the pair's next edit gets a pre/post read on day one" — defers
the real test to whenever the command is next edited, which is a legitimate, disclosed choice
(this is exactly how `setup`'s and `implement`'s kits got a positive control "for free," just
timed the other way round — they were built alongside a real edit). But as written, nothing
commits the kit to actually treating that first real edit as a validation gate on the
instrument itself, separate from grading the command. If that first edit fails to move any
rule from `unchanged`'s `reflected`-in-pre to `absent`-in-post even on a rule the edit plainly
touches, there's no stated rule that says "re-key the instrument, don't grade the command" —
only the stopping rule for *repeated* instrument re-keys (`preregistration.md:72-74`), which
presupposes a re-key has already been triggered by something.

## Fix list, by severity

1. **(HIGH — blocks "ready")** Add a synthetic positive-control probe before declaring the
   kit ready. Take one rule with clearly falsifiable text (e.g. `feat.dm-health-first` or
   `feat.epic-dispatch`), make a throwaway local edit to the command `.md`/migration source
   that removes or visibly weakens that one obligation, run a single low-replicate `plan-run`
   against the mutated copy as an ad-hoc `pre` against the real `post`, and confirm the
   targeted rule id — and only that id — flips state while the rest of the unchanged bucket
   holds. This validates the render→invoke→scrub→judge→partition pipeline end-to-end without
   waiting for a real command edit, at the cost of a couple of extra sessions inside (or
   just past) the existing budget. Revert the mutation immediately after.
2. **(HIGH — blocks "ready")** Remove "the product's capability map stays truthful" (and any
   equivalent rubric-specific phrasing) from all three `control_prompt` fields
   (`evals.json:6,20,34`). Replace with wording that states only the business-facing ask (what
   `args` already gives the real command), so the `nocmd` arm measures what a bare model does
   with the raw request, not with the command's own vocabulary pre-loaded. Re-extend the
   "Fixture-echo caveat" section to explicitly cover control-prompt wording, not just fixture
   files, so this class of leak is checked on sight for future kits.
3. **(MEDIUM)** Before the baseline grid, explicitly state what happens if the eventual first
   real edit fails to register on any rule it plainly touches — i.e., extend the stopping rule
   so a single failed detection on a known real edit is itself treated as a "re-key,"  not
   silently read as "no regression."
4. **(LOW, cross-kit, not blocking this kit)** `load_rubric()` in `evals/commands/run.py:180-181`
   dedupes `observable`/`out_of_instrument` via dict comprehension before the dupe-check runs,
   so a same-list duplicate id would pass `check-rubric` silently. Not triggered in this kit
   (verified directly), but worth a follow-up fix in the shared runner since every command kit
   depends on the same check.

**Ruling on your question 1 — is a git-backed one-rule delta as good a detection gate as the
mutation probe, or does the probe test something the delta doesn't:** Not fully equivalent, and
the difference is real, not academic. `feat.artifact-home` only exercises the **added-bucket**
code path in `run.py`'s `cmd_report` (`adoptions.append((rid, passk(post, rid)))`, `run.py:568-569`
— checked directly), which asks only "does post reflect it." It never exercises the
**unchanged-bucket regression** path (`if rid in part["unchanged"] and pre: if passk(pre, rid)
and not passk(post, rid): regressions.append(rid)`, `run.py:562-564`) — the actual mechanism the
"0 regressed rules" tolerance band and the noise-band stopping rule gate on, and the one a real
future command edit will almost always exercise (weakening or dropping an existing obligation,
not just adding a new one). These are asymmetric failure modes: detecting new, distinctive text
appearing is the easy direction for a judge (more information to match against); detecting an
existing obligation quietly disappearing is the hard direction, and it's the specific failure
mode a lenient/sycophantic judge is most likely to miss — mark it `reflected` on generic
competence even though the text that used to earn that verdict is gone. The synthetic mutation
probe I proposed was aimed exactly at that gap, and it remains open: nothing in this kit has
ever validated the regression-detection path against real or synthetic ground truth. This
doesn't reopen the FAIL — you now have a real, verified, pre-registered control where there was
none, which is the finding closed — but I'm recording the residual as a follow-up (see fix list
below), not silently declaring the instrument fully proven.

One small, related gap in the runner itself, not this kit: `cmd_report` never prints
`passk(pre, rid)` for an added-bucket rule, so "absent under `pre`" — half of the pre-registered
expected outcome at `preregistration.md` — isn't actually surfaced by the report; a reader has
to dig into `summary.json` by hand to confirm it. Worth a small runner fix so the control's pass
condition is fully report-visible, not partially manual.

**Ruling on your question 2 — wrong ref by preferring the tighter gap over the two-control
option:** No. `9cdac97` costs three unrelated plugin versions of intervening change (v0.105→
v0.108, 66 commits) between the ref and the point you actually want to compare against, which
is real attribution risk for what this control needs to prove cleanly — and it would have
bought you a changed-bucket data point on `feat.delta-cards`, one you didn't ask for and would
still need to check wasn't itself confounded by unrelated changes in that gap. Given the
explicit goal (an unconfounded control that matches the pattern the `architecture` and
`brainstorm` kits already use), `794cea8` is the right call. This doesn't replace the need for
regression-path coverage (question 1) — it just means that coverage should come from a
purpose-built synthetic probe or the next real edit, not from re-opening this ref choice.
