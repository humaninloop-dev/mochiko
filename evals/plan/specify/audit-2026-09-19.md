## 2. Out-of-instrument justifications — FAIL (one rule)

Eleven of the thirteen are well-grounded, and grounded in the schema's own ontology, not just
the kit author's prose:

- `spec.lead-latitude` and `spec.epic-proposal-optional` are declared `kind: latitude` **in
  the schema itself** (`.mochiko/schema-views/commands/specify.yaml`, the `roles` section) —
  the "latitude" reason is a structural fact, not a judgment call.
- The nine `spec.fail.*` rules are `kind: fail` in the schema — "end-state failure, not
  forward-plan content" is definitionally true of a fail-condition in a plan-only harness.
- `spec.register` (`extends: common.register`) resolves to "User-facing prose follows
  templates/output-style.md" (`plugins/mochiko/migrations/0001-genesis.yaml:9768-9770`) — a
  meta-rule about prose form, not run activity. Legitimate, though this one is a content
  judgment call rather than a `kind:`-derived fact.

**`spec.filter-disagreement-escalates` is mis-classified.** Its schema entry
(`.mochiko/schema-views/commands/specify.yaml`, `reserved` section) is `kind: routing`, text:
"A producer disagreement — a rejected story held load-bearing — escalates to the user." It is
parked out-of-instrument on `reason: contingency` (`observable.yaml:79`), defined as "fires
only on a run-time event no forward plan contains" (`observable.yaml:9`).

But four *other* `kind: routing` rules in the same schema — `spec.missing-map-surfaced`,
`spec.governance-region-absent`, `spec.next-step`, `spec.epic-mint-desk-only` — are all bucketed
**observable**, each graded on a plan describing the route as a branch, taken or not
(`observable.yaml:39,45,54,57,71`). `spec.epic-mint-desk-only` in particular is the closest
analogue: it is conditional on a hypothetical event ("where an epic is raised") exactly like
`spec.filter-disagreement-escalates` ("a producer disagreement"), yet the kit's own footer
explicitly handles that weakness by keeping it observable-but-disclosed rather than excluding
it — "a plan that never raises an epic reads `absent` here without contradicting the rule...
read its evidence quotes before any verdict" (`observable.yaml:97-100`). The same treatment was
available for `spec.filter-disagreement-escalates` and wasn't used. A plan can plainly state "if
a producer disagrees, that escalates to the user" as a described branch — precisely the pattern
`spec.reserved-to-user`'s own observable text already half-covers ("ruling on an escalated
filter disagreement," schema `reserved` section) — so nothing about this rule is unobservable in
principle.

Net effect: 12 of 13 out-of-instrument entries are solid; 1 is an inconsistent application of the
kit's own design pattern.

## 5. Preregistration — mechanics PASS, one disclosure is stale — FAIL

The four required pre-grid commitments are all present and fixed before any grid:

- **Read rule** — `preregistration.md:24-48` (comparison substrate, Haiku pass^k judge,
  unchanged/removed/added/changed buckets, condition-gating).
- **Tolerance band** — `preregistration.md:50-67` (noise band formula, guard, F2, explicit
  numeric thresholds).
- **Stopping rule** — `preregistration.md:68-70` ("two consecutive instrument re-keys ... without
  a detectable positive control return the kit to the user").
- **Named positive control** — `preregistration.md:72-82`, naming `spec.artifact-home`
  specifically, with an exact expected bucket outcome.

Ship bars (`preregistration.md:115-121`) are decidable from runner output: "LANDED" status
comes straight out of the described bucket logic, and flaky share is a direct count over
per-replicate binary judgments — no post-hoc interpretation required for either hard bar. (The
"visibly different coverage profiles" substrate question at `preregistration.md:123-130` is
softer and not crisply decidable, but it is explicitly framed as bonus/advisory, not a bar — not
a violation of the ask.)

**Defect: the "Validity prerequisites" disclosure is stale and, as written, false today.**
`preregistration.md:94-95` states: "At kit authoring the installed binary predates HEAD's
migration 0005, so the post arm cannot run until the binary is rebuilt from `crates/mochiko-cli`."
I tested this directly (read-only, no `claude -p` call):

```
mochiko-cli --version
→ mochiko-cli 0.1.0 · grammar 1..1

mochiko-cli rules specify --section preamble --plugin-root plugins/mochiko
→ ... binary 0.1.0 · grammar 1 · plugin 0.109.0 ...   (renders cleanly, migration 0005 included)

git archive 32c1ed5 -- plugins/mochiko | tar -x -C <scratch>
mochiko-cli rules specify --section preamble --plugin-root <scratch>/plugins/mochiko
→ ... binary 0.1.0 · grammar 1 · plugin 0.107.0 ...   (renders cleanly)
```

Both the working tree (post arm, plugin 0.109.0, includes `0005-artifact-homes.yaml`) and the
`32c1ed5` archive (pre arm, plugin 0.107.0) render successfully with the currently-installed
binary. The stated blocker no longer holds. Since the fill log is empty (`_none yet_`,
`preregistration.md:139`), no grid has run under the stale assumption, so no results are
corrupted — but a preregistration whose whole point is "committed before the first grid" should
not carry a live-looking blocking claim that is actually false at read time. This is a
documentation-accuracy defect, not a mechanics defect.

## Fix list (severity order)

1. **(Medium) Reclassify or re-justify `spec.filter-disagreement-escalates`.** Either move it to
   `observable` with a disclosed weak-evidence caveat (mirroring the treatment already given to
   `spec.epic-mint-desk-only`), or replace the "contingency" reason with a specific argument for
   why this `kind: routing` rule is unlike its four `kind: routing` siblings that are observable.
   `observable.yaml:79`.
2. **(Medium) Refresh or remove the stale validity-prerequisite claim** at
   `preregistration.md:94-95`. It should either confirm the binary now renders both refs (as
   verified above) or, if amending a preregistration after results exist is the concern, add a
   dated addendum rather than leaving a false blocking claim standing. Per the kit's own rule
   ("amending it after results exist is a recorded, deliberate act" — `preregistration.md:5`),
   since no grid has run yet this is a pre-grid correction, not a retro-fit.
3. **(Low) Tighten the "visibly different coverage profiles" substrate question** at
   `preregistration.md:123-130` with a numeric threshold if the maintainer ever wants it to bind
   rather than stay advisory-only — not required for this kit's stated design, just a
   robustness note.
