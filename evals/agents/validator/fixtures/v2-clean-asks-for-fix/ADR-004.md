# ADR-004 — Tenant isolation through PostgreSQL row-level security

- **Status:** Proposed
- **Date:** 2026-09-07
- **Deciders:** technical-analyst seat, principal-architect seat
- **Constraints addressed:** C-002, NFR-004

## Context

The helpdesk product is multi-tenant on one PostgreSQL cluster. Every table that holds tenant
data carries a `tenant_id` column, and today isolation is enforced by convention: each query
in the service layer is expected to add a `WHERE tenant_id = ?` clause. Two incidents in the
last quarter came from a missed clause on a new report endpoint. C-002 requires that no tenant
can read another tenant's rows through any application path, and NFR-004 caps the isolation
mechanism's read overhead at 5% on the ticket-list query. The forces in tension are defense
in depth against a missed clause, per-query overhead, and how much the change disturbs the
existing service code.

## Alternatives considered

1. **Keep convention, add a lint rule.** A static check that every repository method filters
   on `tenant_id`. Rejected: the rule cannot see dynamically built queries, which is where both
   incidents originated, so it does not satisfy C-002's "any application path".
2. **Schema per tenant.** One PostgreSQL schema per tenant, selected by the connection's
   `search_path`. Rejected: 1,800 tenants would mean 1,800 copies of every migration, and the
   migration runner's current 40-minute window would not hold.
3. **Row-level security policies.** A `tenant_id` policy on every tenant-bearing table, with the
   tenant set per transaction through `SET LOCAL app.tenant_id`. Chosen — see Decision.

## Decision

We adopt PostgreSQL row-level security on every tenant-bearing table. The service layer sets
`app.tenant_id` with `SET LOCAL` at the start of each transaction, and a policy on each table
restricts rows to that tenant. The application role has no `BYPASSRLS`; migrations run under a
separate role that does.

## Consequences

- **Positive:** a missed `WHERE` clause now returns no rows instead of another tenant's rows,
  which closes the incident class C-002 names.
- **Positive:** the policy is enforced for every path, including ad-hoc reports and the the
  admin console, without touching those callers.
- **Negative:** every table gains a policy that must be kept in step with the schema; a new
  tenant-bearing table without a policy is invisible to the application role until one is
  added, so the migration checklist gains a step.
- **Negative:** the planner cannot always push the policy predicate below a join; the ticket-
  list benchmark showed a 3% read overhead, inside NFR-004's budget, and we will recieve a
  regression alert if that figure crosses 5%.
