### F1 — Critical — GI-001: fact profile contradicted by detected reality

The amend's GI-001 text says: *"No new data classes — cardholder data never touches Tidewell."*
`codebase-analysis.md` says otherwise, twice: a new `payment-instrument metadata` class
(`card_brand`, `last4`, `exp_month/year`, `fingerprint` on `payment_methods`), and a new
`raw Stripe event payloads` class — `payment_events.payload` stores the full Stripe event
JSON indefinitely ("kept for replay and support debugging" per `src/payments/README.md`),
and the sampled fixtures show it carries `billing_details` (cardholder name, email, postal
address). The synthesis's own "brownfield cross-check: consistent" only checks that `stripe`
is the one new dependency — it doesn't check the data classes the same analysis lists as new.

No floor row, principle, or module treatment governs retention, access, or minimization for
that JSONB blob, despite `gdpr` being an asserted module. GI-007's redaction list covers log
lines, not a persisted table column.

Failure scenario: authoring proceeds on "no new data classes," `payment_events.payload` ships
ungoverned, and Tidewell is holding indefinite, unminimized billing PII with no principle
requiring retention limits or access control — discoverable only after a DSAR or an incident.

Resolution: amend GI-001 to acknowledge the two new data classes, and add a retention/access
principle for `payment_events.payload` (or an explicit, reasoned waiver) before ratification.
