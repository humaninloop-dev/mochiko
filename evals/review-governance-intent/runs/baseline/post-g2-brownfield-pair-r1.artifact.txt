Coherence lens, Halyard governance-intent — 6 findings raised, 6 survived (no cross-exam yet; counterpart's draft has no overlap, see bottom). My read: **not clear yet — recommend critical-gaps.** Three of these are the frozen synthesis stating something as already-true that the codebase analysis (or the repo files themselves) directly contradicts, which is exactly the "contradicted by detected reality" trigger for that status, not a polish issue.

**1. GI-007 / GI-011 — the PHI redaction filter it's all built on doesn't exist. (Critical)**
GI-007 says "the PHI redaction filter in `halyard/logging.py` keeps intake fields out of log lines," and GI-011 mints "PHI never in logs or error reports" on top of it. There is no `halyard/logging.py` anywhere in the repo — I checked — and `codebase-analysis.md` says so explicitly ("no PHI redaction filter found"). Failure scenario: a clinician note lands in a Sentry breadcrumb or a stdout log line next week, and nobody catches it because both the floor row and the minted principle already claim this is handled. Resolution: either the filter gets built before this floor goes live, or GI-007/GI-011 get re-marked as a build task, not a standing fact.

**2. FLOOR-TEST / Real Commands — synthesis contradicts itself on whether tests run in CI. (Critical)**
The Real Commands table says `pytest` is "detected (runs on every PR in CI)," and GI-005 marks the coverage thresholds Confident. But `ci.yml` has exactly one job — `ruff check .` — no test step at all, which matches what `codebase-analysis.md` says outright, and matches Marcus's own quoted words at GI-003: "CI does not even run the tests yet." The synthesis disagrees with itself here, not just with the analysis. Failure scenario: the authored floor enforces an "already-enforced" coverage gate that has literally never run once. Resolution: fix the Real Commands table and have FLOOR-TEST describe what will be wired up, not what's already running.

**3. GI-004 vs GI-014 — pip-audit is simultaneously enforced and waived. (Critical)**
GI-004 (Confident) says "pip-audit blocks merge at high/critical." GI-014 waives "dependency vulnerability scanning runs" as "not now," Contested. `codebase-analysis.md` confirms reality sides with the waiver: "no vulnerability scanning." So GI-004's own sentence is false as written today. Separately, GI-014's rationale is just "not now" with no revisit trigger — compare to GI-010, which is also Contested but carries real reasoning and a concrete trigger; GI-014 is a bare shield. Resolution: pick one story — ship pip-audit and drop GI-014, or drop the claim from GI-004 — and give GI-014 an actual trigger if it stands.

**4. GI-004 — the Heroku Shield/BAA claim doesn't match `app.json`. (High)**
GI-004 says Shield tier "signs a BAA, so the hosting side of the BAA obligation is covered." `app.json` shows plain `standard-1x` dynos on `heroku-24` — no Private Space, no Shield config — which is exactly what `codebase-analysis.md` flags. Failure scenario: this is a live BAA with Cascade and Sound Rehab, not a hypothetical — if hosting isn't actually on Shield, telling either clinic group it's "covered" is a real exposure. Resolution: confirm with Marcus whether Shield is provisioned somewhere outside the repo (billing console), or strike the "covered" language and open a real action item.

**5. GI-013 (Storybook mandate) — no fact traces to it; over-governance. (Medium)**
Elicited from a lead suggestion, met with "sure, if it's not much work" — that's a hedge, not the basis for a Confident mark. Nothing in the fact profile (two engineers, mutual PR review, `low` depth chosen specifically to avoid new process before CI/tests are solid) supports a standing Storybook + visual-regression-in-CI obligation. This is a minted intent, not floor/compliance-derived, so it's fair game for the over-governance hunt. Resolution: re-confirm as a real commitment with Marcus, or fold it into a deliberate exclusion like GI-018 until the frontend shelf actually needs it.

**6. GI-015 — the audit-logging waiver's justification doesn't cover what it waives. (Medium)**
"Heroku router logs already record every request" is offered to satisfy "audit logging of authentication events." Router-level access logs are path/status/timing — they don't capture who authenticated or whether it succeeded or failed. That's a different artifact from an authentication audit log. It's marked Confident and "permanent" despite this gap. Resolution: check whether Django actually emits a login-event log line anywhere; if not, this isn't a satisfied waiver, it's an open gap and shouldn't be marked permanent.
