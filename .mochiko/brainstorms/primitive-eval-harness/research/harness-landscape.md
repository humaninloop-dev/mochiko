# Eval harness landscape for regression-testing Claude Code artifacts (August 2026)

Method note: WebSearch was blocked for me by an org policy on this model, so everything below comes from direct doc fetches, the GitHub search API, and raw README/SKILL.md reads — no blog-survey layer. HN search returned nothing relevant.

**Bottom line:** build a thin runner on `claude -p` yourself, modeled on Anthropic's own `skill-creator` eval loop. Anthropic ships the closest thing to a reference design and deliberately stops short of CI; promptfoo is the best framework fallback and has a working Claude Code reference implementation; Inspect AI is the right answer only if this grows into a serious agentic benchmark. Two facts do most of the work: `claude -p --bare --plugin-dir <path>` gives you a hermetic session with exactly the artifacts under test loaded, and the `system/init` event reports `plugin_errors`, so a zero-LLM CI gate is available on day one.

## 1. promptfoo

Promptfoo can drive `claude -p` and is built for the CI shape you want. The `exec:` provider runs any shell command as a provider — the contract is argv-based, not stdin: your executable receives the rendered prompt as argument one, a JSON options string as argument two, and a JSON context string (test vars, metadata) as argument three, and returns its result on stdout. For anything beyond a one-liner the docs steer you to the native Python provider or a JS `ApiProvider` implementation, which is what the Claude Code reference implementation below actually does.

The CI story is the strongest of any candidate. `promptfoo/promptfoo-action@v1` runs a before/after comparison on every PR that touches the prompt glob and posts results as a PR comment with a link to an interactive diff viewer; it needs `pull-requests: write` and caches LLM responses through `actions/cache` on `~/.cache/promptfoo`. On the CLI, `--repeat <n>` runs each test n times, `-j` sets concurrency, `PROMPTFOO_PASS_RATE_THRESHOLD` sets a minimum pass rate (default 100), and the eval exits with code 100 when a test fails or the threshold is missed. Output formats include `junit.xml` and `json`.

Judge-model flexibility is good. Model-graded assertions include `llm-rubric`, `g-eval`, `factuality`, `select-best`, `max-score`, plus agent-oriented ones — `agent-rubric`, `conversation-relevance`, and `trajectory:goal-success` (which requires trace data). The grading provider is settable at three levels — `promptfoo eval --grader <provider>`, `defaultTest.options.provider`, or per-assertion — and Anthropic credentials in the environment select a Claude grader by default. It is open source and runs entirely locally; the SaaS is optional sharing.

**Fit verdict:** the strongest off-the-shelf option, and the only one whose CI ergonomics (PR comment, threshold exit code, `--repeat`) match what you'd otherwise hand-roll. The costs are a Node toolchain in a Rust-and-markdown repo and a config layer between you and the thing you actually care about. Threshold control is coarse — one global pass-rate floor, no per-test hysteresis.

## 2. Inspect AI (UK AI Security Institute)

Inspect is an open-source eval framework from the UK AISI and Meridian Labs, with 200+ benchmark implementations. A Task is a dataset plus a solver plus a scorer; solvers range from a single `generate()` to a full multi-turn agent, and the built-in `react()` agent runs a reason-act-observe loop with tools. Scorers cover text comparison (`includes()`), model-graded QA (`model_graded_qa()`), and custom logic. Sandboxing is first-class — Docker, Kubernetes, Modal, Proxmox, Vagrant, plus an extension API. Twenty-plus model providers including Anthropic.

The reason it matters here is the **agent bridge**, which explicitly names Claude Code as a supported case. `sandbox_agent_bridge()` runs a proxy inside the sandbox container on port 13131 that relays Anthropic, OpenAI, and Gemini API requests back to the Inspect model provider. To wrap a CLI agent, you bake the binary into the sandbox image, launch it via `sandbox().exec()` with `ANTHROPIC_BASE_URL=http://localhost:13131`, and return `bridge.state`. The bridge tracks messages and output automatically, so standard Inspect scorers work on bridged agents and you get the full transcript and log viewer.

Two caveats specific to bridging. Provider-side tools (`web_search`, `web_fetch`, `code_execution`, remote MCP) are withheld unless explicitly granted, since they'd bypass sandbox network restrictions; host-side tools can be exposed as MCP via `bridged_tools`. And client generation parameters like `max_tokens` and `temperature` are dropped by default unless you set `forward_generation_config=True`.

**Fit verdict:** the most capable option and the only framework with documented Claude Code integration plus real sandboxing and the best transcript viewer. But it inverts the control relationship — Claude Code's model calls get routed through Inspect's model configuration, so you're testing your artifacts under Inspect's harness rather than under Claude Code's normal one, which is a subtle fidelity difference for prompt-artifact testing. Python plus Docker is heavy for a markdown plugin repo's first eval.

## 3. Braintrust, LangSmith, OpenAI Evals

**Braintrust** structures an eval as data plus task plus scorers, where the task can be "a multi-step agent, a retrieval pipeline, or a custom workflow." Scorers come from built-in autoevals, LLM-as-judge, or custom code, and the documented workflow explicitly includes running evals on every pull request to catch regressions. The docs don't state SDK languages or licensing, but the feature set (browser playgrounds, shared URLs, hosted online scoring) is SaaS-shaped. Trajectory-specific scoring isn't documented. **Fit verdict:** competent and CI-aware, but coupling a public open-source plugin repo's test gate to a hosted platform with an API key is a real cost for no capability you can't get locally.

**LangSmith** centers on datasets and evaluators, supporting human review, code rules, LLM-as-judge, and pairwise comparison, and frames the output as experiments you compare for regression testing. Offline and online modes both exist; deployment is cloud, hybrid, or self-hosted. Nothing on the evaluation overview requires LangChain, and runs capture intermediate steps — but the page documents no pytest/vitest plugins and no dedicated trajectory evaluators, so agent-trajectory judging would be custom work. **Fit verdict:** the self-hosted option removes the SaaS objection, but you'd be adopting a large observability platform to get a test runner, and its agent-trajectory story is weaker than Inspect's.

**OpenAI Evals is being retired — rule it out.** Per the docs, it goes read-only for existing users on 2026-10-31 and shuts down 2026-11-30, with Datasets suggested as the replacement. Separately, its grader templates assume the eval run generates samples from an OpenAI model (`{{sample.output_text}}`); bring-your-own-completions from an external process isn't documented, and there's no CI guidance beyond webhooks and polling.

## 4. Anthropic-native paths

This is where the strongest material is, in three layers.

**Headless mode is more capable than the "shell out and grep" mental model suggests.** `claude -p` takes `--output-format json` (result, session ID, usage) or `stream-json`, and `--json-schema` forces schema-conforming output into a `structured_output` field — which makes the *judge* call trivially machine-readable without parsing prose. The JSON payload includes `total_cost_usd` and a per-model cost breakdown, both client-side estimates, so the harness reports its own spend. Sessions resume via `--resume "$session_id"`, and since v2.1.223 the session is findable by ID from any directory.

Three flags matter specifically for testing artifacts:

- **`--bare`** skips auto-discovery of hooks, skills, plugins, MCP servers, auto memory, and CLAUDE.md. The docs call it "the recommended mode for scripted and SDK calls" and say it will become the default for `-p`. You then load exactly what's under test with `--plugin-dir <path>`, `--agents <json>`, `--settings`, and `--append-system-prompt-file`. This is the hermetic-fixture lever: without it, a `-p` session in an untrusted folder still runs the project's `.claude/settings.json` hooks and connects its `.mcp.json` servers, because `-p` shows no trust dialog.
- **`--forward-subagent-text`** (v2.1.211+) makes subagent text and thinking blocks appear in the stream, tagged with `parent_tool_use_id`; nested subagents at every depth are included from v2.1.219. That is what makes phase two — skill+agent cluster edits — observable at all, since by default only subagent `tool_use`/`tool_result` blocks are emitted.
- **`--permission-mode dontAsk`** is the documented locked-down CI mode: everything outside `permissions.allow` and the read-only command set is denied.

And user-invoked skills work in `-p` — put `/skill-name` in the prompt string and it expands before the run; plugin skills use the namespaced `/plugin-name:skill-name`.

**There is a free deterministic gate before any LLM judging.** The `system/init` stream event carries a `plugins` array of what loaded and a `plugin_errors` array of load-time failures (`plugin`, `type`, `message`), with the key omitted entirely when there are none. The docs state the intended use directly: fail CI on a non-empty array. The same pattern exists for `mcp_server_errors`. For mochiko this catches malformed frontmatter, broken plugin manifests, and marketplace-sync drift for the price of one cheap session.

**The GitHub Action already knows how to install and invoke a plugin.** `anthropics/claude-code-action@v1` in automation mode (any workflow with a `prompt` input, on any GitHub event) accepts a skill invocation as the prompt, and `plugin_marketplaces` plus `plugins` install a plugin from a git URL before execution — then you pass `/plugin-name:skill-name` as the prompt. `claude_args` forwards arbitrary CLI flags (`--max-turns`, `--model`, `--allowedTools`). The Agent SDK is Python and TypeScript only; for other languages the documented path is running the CLI as a subprocess with `-p --output-format json`. The SDK loads skills, commands, memory, and plugins from `.claude/` and `~/.claude/` the same way Claude Code does.

**The most important find: Anthropic ships an official skill eval loop.** The `skill-creator` plugin (`/plugin install skill-creator@claude-plugins-official`) automates a with-skill-versus-baseline comparison inside Claude Code, and the format is documented at `agentskills.io/skill-creation/evaluating-skills` with background at `claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills` (dated 2026-03-03). The shape:

- Test cases live in `evals/evals.json` inside the skill directory: `id`, `prompt`, `expected_output` (human-readable), optional input `files`, and an `assertions` array added *after* you've seen the first round of outputs.
- Each case runs in an isolated subagent per configuration so context is clean; token count and duration land in `timing.json` (they come from the subagent completion notification and are persisted nowhere else).
- Grading writes `grading.json` — per assertion, a `text`/`passed`/`evidence` triple, where evidence must quote or reference the output. The guidance is to require concrete evidence for a pass and to use scripts rather than LLM judgment for anything mechanically checkable.
- `benchmark.json` aggregates pass rate, time, and tokens per configuration as mean and stddev, plus the with-versus-without delta.
- Version comparison runs a blind A/B between two skill versions; description tuning generates should-trigger and should-not-trigger prompts and measures hit rate.

The blog post names two uses directly relevant to your question: "catching quality regressions when models or infrastructure change," and detecting when the base model passes the evals *without* the skill — a sign the skill is obsolete rather than broken. It also says results stay local and "can feed into dashboards or CI systems." **But it ships no CI wiring.** The SKILL.md workflow is an interactive human-review loop with an HTML viewer and a `feedback.json`; there is no continuous-integration section anywhere in it. That gap is exactly the thing mochiko would be building.

## 5. Hand-rolled pytest/vitest plus LLM judge

Practitioners who skip frameworks converge on a consistent set of positions, best articulated in Hamel Husain's "critique shadowing" write-up. Use **binary pass/fail, not Likert scales** — "what makes something a 3 versus a 4? Nobody knows," and numeric scores don't tell you what to change. Pair every binary judgment with a critique detailed enough to reuse as a few-shot example. Anchor the judge to one principal domain expert's labels rather than a committee, and iterate the judge prompt against those labels until agreement converges; in his Honeycomb case that took three iterations to exceed 90% agreement. Track judge-versus-expert agreement over time, but measure precision and recall separately when pass/fail classes are imbalanced, since raw agreement misleads. Avoid off-the-shelf judge metrics — they "cause more confusion than value." And the framing that matters most here: the judge is secondary; the value comes from the discipline of looking at your data.

**Fit verdict:** for a repo that already runs `cargo test`/`fmt`/`clippy` under CI and whose primary artifacts are markdown, a shell-plus-jq runner over `claude -p --output-format json` with a `--json-schema` judge call is genuinely small — maybe 200 lines — and it inherits zero framework opinions about what an eval is. The risk is reinventing `--repeat`, result storage, and diff reporting badly.

## Prior art

**Nobody has consolidated this.** Every community harness I found is under 15 stars; there is no dominant tool as of August 2026. The largest body of prior art is Anthropic's own `skill-creator`, described above.

The two closest analogues:

**`mslavov/claude-code-eval`** — "A promptfoo wrapper for evaluating Claude Code custom slash commands and sub-agents," MIT-licensed. It is nearly your exact problem statement. It creates a **git worktree per test** to isolate runs, discovers slash commands and subagents at runtime so there's no registry to maintain, runs Claude Code headless with `--output-format json`, and bridges to promptfoo through a custom file provider registered as `id: file://providers/claudeCodeProvider.js` with config for model, `maxTurns: 3`, `permissionMode: plan`, and an `allowedTools` list. Test cases in `tests/cases.yaml` carry inputs (`command`, `args`, `subAgent`, `prompt`, `files`, `repoPath`, `gitRef`) and assertions (`expectedCreated`, `expectedModified`, `expectedContains` as a file-to-substring map, `expectedOutput` as a pattern). Judging is entirely assertion-based — git diffs and content checks, no LLM judge. Commands are `init` and `test`, with `--output html json csv`. No CI section, but everything needed for one.

**`bailejl/dev-plugins`** — structurally the closest to mochiko: a Claude Code plugin marketplace where every plugin ships an eval suite. The layout separates `plugins/` (what ships to users: commands, skills, agents, hooks) from `evals/` (test suites, graders, fixtures — kept in the repo, never shipped) and `eval-infra/` (shared utilities, scripts, rubric templates). Promptfoo is the harness and LLM grader, supplemented by ESLint/Prettier and axe-core for deterministic assertions. The pipeline is task → trial (a single promptfoo run) → graders (deterministic checks, LLM rubrics, transcript analysis) → **pass@k and pass^k** outcome scores, computed by a `compute-pass-at-k.py` script. Runs via `npm run eval:frontend` / `eval:readiness` / `eval:all` with `ANTHROPIC_API_KEY` in a gitignored `.env`. CI is drafted but not live — the README has a commented-out badge for an `eval-ci.yaml` workflow; baselines are currently tracked in a `BASELINE.md` file.

Smaller but on-theme: `daric93/code-review-skill` (a code-review skill shipping a promptfoo skill-vs-baseline A/B harness), `gcamilo/skill-eval` (A/B testing agent skills with pairwise tournaments and automated regression), `jeremylongshore/j-rig-skill-binary-eval` (binary-criteria harness for Claude skills, with planned extension to plugins, agents, and commands), `kayolyh/agent-skill-eval` (audits skills for trigger precision, regressions, and cost), and `Frank-debug666/agent-eval-regression-skill`.

## Variance mitigation

The practices that actually appear in shipped tooling, in rough order of leverage:

**Push everything you can out of the judge.** Both Anthropic's guidance and every serious harness say the same thing: for programmatically checkable assertions (valid JSON, file exists, row count, a string is present), write a script — "faster, more reliable, and reusable across iterations." Reserve the judge for things that genuinely require judgment. A judge you invoke on ten assertions has ten times the variance of one you invoke on two.

**Binary with evidence, not scores.** `grading.json`'s `{text, passed, evidence}` triple and Hamel's binary-plus-critique are the same idea. A judge forced to quote the output as justification for a pass has far less room to drift than one emitting a 1–5.

**Pairwise blind comparison for holistic quality; absolute assertions for objective criteria.** Both Anthropic sources recommend blind A/B when comparing two skill versions: present both outputs to the judge without revealing provenance and let it score organization, formatting, usability on its own rubric. The stated reason is that two outputs can both pass every assertion and still differ substantially in quality. The known-bias literature (Zheng et al., MT-Bench, NeurIPS 2023) backs this with the caveat that pairwise judging has **position bias** — so swap the order and require both orderings to agree before counting a win. The same paper documents verbosity bias (longer answers favored), self-enhancement bias (models favor their own family), and weak judging on reasoning-heavy tasks, with reference-guided grading as the mitigation for the last. Its headline number: a strong judge reaches over 80% agreement with humans, which is the same level humans reach with each other.

**Multiple trials, and the right aggregate.** `skill-creator` records mean ± stddev in `benchmark.json` and its analysis pass explicitly hunts for "high-variance evals (possibly flaky)." The agentskills.io guidance is blunt that stddev is meaningless with single runs — in early iterations with 2–3 cases you should read raw pass counts and the delta, and the statistics only become useful as the test set grows and each eval runs multiple times. The one concrete trial count anywhere in Anthropic's docs is for description tuning: **three runs per query to get a reliable trigger rate.** promptfoo's `--repeat <n>` is the framework equivalent. For a gate, `bailejl/dev-plugins`' **pass^k** (all k trials pass) is the right metric — pass@k (any of k passes) flatters a flaky artifact.

**Guard against overfitting the eval set.** `skill-creator`'s description-tuning loop splits 60% train / 40% held-out test, runs up to five iterations, and selects the final description by *test* score rather than train score. Worth copying if the harness ever drives automated artifact rewriting.

**Prune non-discriminating assertions.** Assertions that pass in both configurations inflate the with-skill pass rate without measuring anything; assertions that fail in both are broken or testing the wrong thing. Both are called out as explicit analysis steps.

**Threshold hysteresis is not solved by any framework.** promptfoo offers a single global `PROMPTFOO_PASS_RATE_THRESHOLD` with exit code 100, and nothing else in this survey ships per-test hysteresis at all. The pattern in the wild is `dev-plugins`' approach: commit a `BASELINE.md`, gate the PR against baseline-minus-a-margin, and regenerate the baseline as a deliberate, reviewed act — which maps cleanly onto mochiko's existing landing-ritual discipline.

## Cost

Current first-party per-million-token rates: **Opus 5 $5 / $25**, **Sonnet 5 $3 / $15** (introductory $2 / $10 through 2026-08-31), **Haiku 4.5 $1 / $5**, Fable 5 $10 / $50. Cache reads run about 0.1× base input, cache writes 1.25× at the 5-minute TTL. Batch API is 50% off but useless for interactive sessions.

A worked estimate for one scripted session — a moderate skill-exercising task, roughly 15 turns, with history resent each turn and prompt caching working: call it ~300K cumulative input tokens of which ~80% are cache reads, plus ~20K output. On Sonnet 5 that's 60K fresh input at $3/M ($0.18), 240K cache reads at $0.30/M ($0.07), and 20K output at $15/M ($0.30) — about **$0.55 per session**. The same on Opus 5 lands near **$1.00**. A Haiku judge over a 30K-token transcript is roughly $0.035; a Sonnet judge about $0.10.

So a per-PR grid of **20 scenarios × 3 trials = 60 sessions** costs roughly **$33 on Sonnet, $60 on Opus**, plus $2–6 of judging. That is the number to design around. Levers, in order of payoff: run the full grid nightly and a small smoke subset per PR; drive the session with Sonnet or Haiku where the artifact under test isn't model-sensitive (the skill text is what's under test, not the model); use Haiku for objective assertion grading and reserve a stronger judge for the blind comparisons; cap `--max-turns`.

Two practical notes. You don't have to estimate — `--output-format json` returns `total_cost_usd` plus a per-model breakdown, so the harness self-reports actual spend from the first run (client-side estimates, so they can diverge from the bill). And GitHub Actions minutes are a second, separate budget: session wall-clock dominates, so use a job matrix for parallelism, set workflow-level timeouts, and use concurrency controls to cap parallel runs.

## Ranked shortlist

**1. Hand-rolled runner over `claude -p`, structured after `skill-creator`.** Adopt Anthropic's file layout wholesale — `evals/evals.json` next to each artifact, per-run `grading.json` and `timing.json`, an aggregated `benchmark.json` with mean/stddev and a with-versus-without delta — and supply the CI wiring Anthropic omits. The session command is `claude -p --bare --plugin-dir plugins/mochiko --output-format json --permission-mode dontAsk --max-turns N`, and the judge is a second `claude -p --json-schema` call over the transcript. Ship the `plugin_errors` gate first: it's deterministic, costs one cheap session, and catches the whole class of "the plugin no longer loads" regressions before any judging exists. This ranks first because it matches the repo's constraints (no SaaS, no new language runtime, an advisory post-hoc exit-code check rather than a pipeline-gating brain), it composes with the existing `cargo test` CI gate, and the layered rollout — deterministic smoke, then scripted assertions, then a judge — lets you defer the expensive and variable part until the cheap part has proven its worth.

**2. promptfoo with a custom Claude Code provider.** Pick this if you'd rather not own `--repeat`, result storage, PR reporting, and threshold logic. You get the GitHub Action's before/after PR comment, `--repeat` for trials, `PROMPTFOO_PASS_RATE_THRESHOLD` with a distinct exit code, junit output, and configurable Anthropic graders — and `mslavov/claude-code-eval` is a working, MIT-licensed reference for the provider and the git-worktree isolation, while `bailejl/dev-plugins` is a working reference for the plugin-marketplace-with-eval-suites repo layout. The cost is a Node toolchain and a YAML config layer in a repo that currently has neither.

**3. Inspect AI.** Reach for this when the eval outgrows "did the skill fire and produce the right shape" and becomes a real agentic benchmark — sandboxed multi-step tasks, tool-use trajectories, many scenarios needing a proper log viewer. It is the only framework with documented Claude Code bridging, and its sandboxing and transcript tooling are the best available. It is third only because the bridge routes Claude Code's model calls through Inspect's provider config, which is a fidelity compromise when the system under test *is* the Claude Code harness, and because Python-plus-Docker is disproportionate machinery for a first eval on a markdown plugin.

**Ruled out:** OpenAI Evals (read-only 2026-10-31, shutdown 2026-11-30). **Ruled out on coupling:** Braintrust — capable and explicitly CI-oriented, but gating a public plugin repo on a hosted platform buys nothing you can't run locally. **Ruled out on weight:** LangSmith — self-hosting removes the SaaS objection, but adopting an observability platform to get a test runner is backwards, and its agent-trajectory evaluators aren't documented.
