## Decisions

*(appended as ruled; one `D…` namespace)*

### D1 — One eval layer, three targets
**Statement:** Skills, commands, and agents are three **targets** of one eval layer under one ruling set and one vocabulary — goldens · rules · arms · pre-registration · deterministic-may-block / judge-advisory · within-grid pre/post regression read. The old `primitive-eval-harness` record is superseded in full on acceptance: each of its D1–D5 is re-ruled by number in this record, and the two later sessions' rulings (`skill-compression-tooling` D1–D8, `command-plan-only-eval` D1–D11) are re-affirmed here where they still bind and superseded by number where they do not. Agents enter as the third target of the existing layer, not as a third design.
**Rationale:** The three instruments already share the old record's D2/D3/D4 in substance (F4) but diverge in file shapes and names (F2 vs F3), and every future persona edit wants the same `--old-ref` regression read the command runner has. Unification is the cleanup the user asked for; a separate agents-only session would leave a third vocabulary behind. Rejected: **B agents-only** (leaves the four unfilled post-cut eval slots and the stale backlog untouched — F2, F8); **C agents + cleanup without unification** (cleanup without a shared vocabulary re-creates the divergence at the next edit).
**Confidence:** Confident (user-ruled, adopted-as-recommended, unelaborated; adoption streak 1).

### D2 — Agent observable: plan-only elicitation (the command target's substrate), traps planted in the fixture text
**Statement:** A persona is graded on its **plan**, elicited headless against a fixture, never on an executed run. The persona is seated on the fixture with a read-only fence (reads allowed; writes, shell, and spawns denied), produces the plan it would execute, and the plan plus the read-trace that preceded it is the graded surface. Traps are planted where a plan can meet them — in the card text and the fixture files the persona can read: a contradiction between card and code, a declared-missing dependency, an existing interface the card asks to change without `[MODIFY]`, a flattering author summary beside a defective artifact. Execution-only behaviours — red actually run before green, a worker override actually passed, a return actually read back, report honesty about a real failure — are **declared out-of-instrument** for this target (the command target's D8 partition applied to personas) and keep their existing homes: the contract suite's recorded measurements and one-off live probes such as the 2026-09-05 worker-rung probe (F6).
**Rationale (user's, as read):** cost and reuse — one turn per golden, no filesystem or tool loop, and the command runner's wrapper, judge, `--old-ref` grid, and observable partition carry over nearly unchanged; the persona target then costs what the command target costs. The lead's recommendation was (a) trace-plus-report with per-class sizing; its case (recitation risk, traps that fire only at contact, claims-versus-proof on dispatch overrides, report honesty) was heard and the user chose (c) with those costs named. Rejected: **(a) executed trace** (an order of magnitude dearer, tool-loop noise, fixture upkeep, sandbox permissions); **(b) artifact-only** (a persona's judgment mostly precedes the artifact).
**Confidence:** Contested (user chose (c) over the recommended (a), deliberately, after the trade-offs were laid out; adoption streak reset to 0).
**Carried obligations:** (i) the judge clause *embodies, never recites* is mandatory for the persona target, because the rubric is derived from the persona's own text (F7) and a plan will echo it; (ii) the noise falsifier is pre-registered per persona pilot before any grid, because the same substrate was noise-dominated on `implement` (F3); (iii) the out-of-instrument set per persona is written down in the persona's observable partition, so nothing execution-only is silently assumed graded.

### D3 — Substrate: the persona is seated as the headless session itself via `--agent`
**Statement:** A persona golden runs as `claude -p <wrapper prompt> --agent mochiko:<persona> --plugin-dir <staged plugin> --setting-sources '' --disallowedTools 'Write,Edit,Bash,Agent,NotebookEdit' --output-format json` from the fixture directory. The persona is the session: the form-only elicitation wrapper is the prompt, the fixture is the cwd, the fence denies every write, shell, spawn, and skill-load tool while leaving reads open, so the graded surface is the plan plus the read-trace (which fixture files the persona opened before planning). No nested lead, no relay. The persona target is thereby the command target with two deltas — the `--agent` flag and the fence.
**Rationale:** Probe-verified today (F11): the working-tree persona loads, the fence holds, one turn costs ~$0.22. A nested spawn through a headless lead adds a turn, a relay, and lead noise to a substrate already shown noise-dominated (F3), and its one advantage — exercising the spawn path — is out-of-instrument under D2. Rejected: **(ii) nested spawn** as the default; kept only as an occasional manual cross-check when a dispatch-related question arises, never as a grid arm.
**Confidence:** Confident (user-ruled, adopted-as-recommended, unelaborated; adoption streak 1).

**Review folds (C1 · M2, user-accepted):** *Statement as amended —* the fence is `--disallowedTools 'Write,Edit,Bash,Agent,NotebookEdit,Skill'`: **`Skill` is denied too**, because F13 showed the tool present and every persona body defers procedure to its skills in prose it reads as instruction, so an open Skill tool makes the "persona alone" arm not alone and adds a per-replicate variance source to a substrate already recorded noise-dominated (F3). The run's permission mode is `--permission-mode acceptEdits`, the setting the sibling ruling settled by probe (`skill-compression-tooling` R5) and the one used in F11/F13; with every write tool denied it grants nothing, and it is recorded so the run condition is complete.

### D4 — Agents-as-schema: a door, not a wave
**Statement:** Converting persona rule-shaped content into the migration log (a fourth document kind, CLI-served) is recorded as a **candidate wave**, not ruled here. Its gate is a delivery channel that reaches the persona on both transports: `!` injection is ruled out by F12, so the candidate design is hook-based injection of `mochiko-cli rules <persona>` output — to be probed (does a hook fire for a `--agent` session, for an `Agent` subagent, and for an agent-team teammate; does the injected text land before the first model turn) before any census. Until then personas stay prose primitives under the plain ceremony (strips + audit), and the eval layer must not depend on the conversion.
**Rationale:** The benefit set is real and the same one that carried the skill conversion — ids, anchors, floor protection, migration history, mechanical rubric — but the cost is a wave (grammar kind, crate surfaces, contract cases, census-first rollout, ceremony extension), and the one fact it hinges on came back negative for the obvious channel (F12). Skill evals ran on hand-inventoried `rules.json` before skills were schema (F2); personas can take the same path. Rejected: **fold the conversion into this session** (scope creep, no census); **defer with no door** (loses the probe fact and the open question).
**Confidence:** Confident (user-ruled: "1, run the probe"; adoption streak 2).

**Review fold (M3, user-accepted):** the gate names **three** transports, not two — the `--agent` session (the one the eval uses), the `Agent` subagent, and the agent-team teammate; a hook-channel finding counts only with all three legs.

### D5 — Persona rubric: derived from the persona's own body, ids minted, partitioned, control-pruned
**Statement:** Each persona's `rules.json` is derived from its body: every bullet under Quality Standards, What You Reject, What You Embrace, Your Judgment, and the persona's craft sections becomes one claim with a **minted stable id** (`<persona>.<slug>`), compound bullets split by hand, nothing invented; Core Identity narrative is not a rule source. Each claim carries a partition value — `plan-observable` or `out-of-instrument` with its reason (the command target's D8 shape) — and the `nopersona` control arm prunes claims the bare model satisfies without the persona. The judge clause *embodies, never recites* is mandatory (D2 carried obligation i). If D4's conversion ever lands, these ids are the census and become the schema ids.
**Rationale:** The rubric stays in lockstep with the primitive, as the command rubric derives from the schema, so a persona edit is graded against what the persona now claims and the `--old-ref` diff measures the edit, not rubric staleness. The partition and the control arm are what keep a derived rubric honest against a plan-only substrate. Rejected: **hand-authored rubric** (drifts from the primitive); **grading through the persona's `skills:` rules** (measures procedure, not the judgment the persona owns — five-axis #4).
**Confidence:** Confident (user-ruled as part of option 1: "derive the rubric from prose now with minted ids"; adoption streak 3 — flagged; the next fork is posed recommendation-free per questioning discipline).

**Review folds (I3 · I4, user-accepted):** *(I3)* the rubric for a grid is minted from the **union of both refs** — the persona at `--old-ref` and in the working tree — each claim tagged `added` / `removed` / `common`, so a claim an edit deletes has an id and its disappearance is read, not silent; the D5 rationale's "the diff measures the edit" now holds for removals as well as additions. `model-native` tags **carry forward by claim id** across mints, and D7's bare-model pass runs only over ids not yet tagged — so a union-of-refs mint does not re-run the control every grid (verify residual R3). *(I4)* a **body-derived completeness check** is part of minting: every bullet under the named sections maps to exactly one claim id or carries an explicit `not-a-claim` tag, and the check fails the mint otherwise — the persona analogue of the command target's `check-rubric`, which is what makes the partition trustworthy there. Until D4's conversion lands this check is the only completeness verifier, and it is a script over the body, never a model read.

### D6 — Default grid: `pre` and `post`, the persona alone (no skills preload) *(amended in-session by the user)*
**Statement:** A persona grid runs two arms by default — `pre` (the persona at the `--old-ref` commit) and `post` (the persona in the working tree; arm names per the I6 fold) — each seated as **the persona alone**: no `skills:` preload, no skill text appended, which is exactly what `--agent` seating does (F13). The graded plan is the persona's own judgment on the fixture. Skills have their own target (D1); the persona-versus-skill attribution question is not bought. `nopersona` is not a grid arm; its role is settled in D7.
**Rationale (user's, as read):** grade the agent itself — the skill target already grades the skills, and loading them into a persona grid would blur which primitive an edit moved. This also matches the decoupling doctrine's own definition (agent-decoupling O2: a persona is *competent alone* — self-sufficient method, judgment, standards). Two arms keep the grid at goldens × replicates × 2. **Amendment trail:** first ruled "baseline with skills loaded, and edited with skills loaded too"; F13 then showed `--agent` seating does not preload skills and the lead posed the loading mechanism as a fork (pre-rendered append / Skill-tool invocation / nested spawn); the user withdrew the skills clause instead ("remove the skills from the previous answer, just agent"), which dissolves that fork — no loading mechanism is needed. Rejected: **skills loaded via `--append-system-prompt-file`** (a controlled variable no run uses in that position, and it would mix two targets); **`persona-only` vs `cluster` arms** (attribution not worth its cost).
**Confidence:** Confident (user-ruled with own shape at a recommendation-free fork, then amended by the user's own word on a new fact; adoption streak 0).

**Review fold (I6, user-accepted):** the two arms are named **`pre`** (the persona at `--old-ref`) and **`post`** (the working tree), so `baseline` names one thing only — the committed frozen result of D13(1). The persona target needs no committed baseline at pilot: its read is the `pre`/`post` diff.

### D7 — `nopersona` is a one-time pruning pass at rubric mint, never a grid arm
**Statement:** When a persona's `rules.json` is minted or re-minted (a persona edit that adds or removes claims, or a session-model change), the same goldens run once with the bare model — no `--agent`, same wrapper, same fence — for `k` replicates. A claim the bare model satisfies in every replicate is tagged `model-native` in `rules.json` and excluded from the regression read; it is never deleted. Grids run `pre` and `post` only (D6).
**Rationale:** The skill target's `noskill` arm showed that model-native claims dominate a fresh inventory, and the value of knowing which they are is realised once, at mint; paying it in every grid adds half again to every run for a signal that only moves when the model does — which is itself a re-mint event. Rejected: **control arm in every grid** (cost without new information between model changes); **no control** (absolute claims that "the persona does X" would carry no evidence the persona caused it).
**Confidence:** Confident (user-ruled, adopted-as-recommended, unelaborated; adoption streak 1).

**Review fold (I1, user-accepted):** **`--model opus` is passed explicitly on every arm — `pre`, `post`, and the `nopersona` pass** — matching the pin every persona carries, so treatment and control differ in one variable (the persona) and not two, whatever the pin probe finds (verify residual R5); the flag is recorded in the mint log. Pin resolution under `--agent` is settled before the pilot by a probe that pins a non-default model and reads the result JSON's model id (F11's single `claude-opus-5` observation cannot separate pin-resolution from a default-Opus session).

### D8 — Goldens: three to five hand-authored synthetic fixtures per persona, each keyed to the claims it tempts
**Statement:** A persona's goldens are hand-authored, synthetic, and few — three to five. One golden = a minimal fixture directory (two to five files) plus the card carried in the wrapper prompt, plus an `expectations` block naming the rule ids the trap targets. Traps are of the kind a plan can meet (D2): a card contradicting the code it shows; a dependency the card assumes and the fixture declares missing; an existing interface the card asks to change with no `[MODIFY]`; a flattering author summary beside a defective artifact (grader personas); a card inviting scope past the request. Goldens are frozen before the first grid and change only as a deliberate landing act; real-project fixtures stay deferred — the old record's D1 is **re-affirmed** for the persona target.
**Rationale:** Every rubric claim needs at least one moment of temptation or it is graded on nothing, and hand authorship keeps the bar independent of the thing it grades. Rejected: **one shared fixture bank** (a bank tuned for a builder tempts a reviewer poorly, and one change moves every persona's bar); **model-generated goldens** (generator and judge share a bias; the bar stops being fixed).
**Confidence:** Confident (user-ruled, adopted-as-recommended, unelaborated; adoption streak 2).

**Review fold (I5, user-accepted):** the golden count is **derived from the post-pruning claim count**, not fixed: three to five is a floor, and each `plan-observable` claim that survives D7's pruning must be tempted by at least one golden or carry an explicit **`untempted`** tag beside `model-native` — so D8's "every claim needs a moment of temptation" is either met or disclosed per claim, never assumed.

### D9 — Pilots: `staff-engineer` first, `validator` second
**Statement:** The persona target pilots on `staff-engineer` — the library's highest-volume seat, carrying a fresh edit (v0.107.0 → v0.108.0, the `## Delegating Bounded Work` section) so the runner's first grid is a real `--old-ref` read on the day it exists — then on `validator`, whose judgment (default FAIL, read the artifact never the author's summary) is the most plan-gradable in the library and whose rubric is short. Further personas follow only after both pilots' pre-registered ship bars are met or the instrument is re-keyed.
**Rationale:** The first pilot must have an edit to detect, or the grid measures only noise (F3's lesson); the second must prove the instrument on the persona class where plan-only is strongest. Rejected: **`qa-engineer` first** (edited today too, but its craft is execution against real infrastructure — out of instrument under D2); **a grader first** (best plan-only fit, no recent edit to read against).
**Confidence:** Confident (user-ruled, adopted-as-recommended, unelaborated; adoption streak 3 — flagged; the next fork is posed recommendation-free).

### D10 — Layout: the persona target lands inside the plan-only runner now; one runner is the promotion target, reached in landing acts
**Statement:** The persona target is built as a third elicitation mode of the existing plan-only runner (`evals/commands/run.py` today): the `--agent` seating and the read-only fence (D3) as the elicitation delta, the persona body as the rubric source (D5), the D8 observable partition and the `--old-ref` pre/post grid reused as they stand. No runner is refactored and no committed skill directory moves for this build. The one-layer shape D1 names is reached afterwards in separate landing acts, each its own audit: rename `evals/commands/` → `evals/plan/` (the plan-only runner now grades commands and personas; the two command dirs and their citations move with it); extract the shared core — session invocation, judge calls, grid math, report — into `evals/lib/` and make the skill runner import it; converge the CLI to `evals/run.py <target> <subcommand> <name>`. `evals/contract/` stays where it is as the release gate, never an eval. Until the convergence lands, D1's one vocabulary is carried by `evals/README.md`, which every runner cites.
**Rationale:** By D2/D3 the persona target *is* the command target with two deltas, so building it inside that runner is days of work and lands the first grid while the v0.107.0 → v0.108.0 edit is the live question (D9). A one-runner refactor first would rework two instruments whose only value is regression detection and move six committed skill dirs whose paths `DECISIONS.md` rows and strips cite — weeks before any persona signal. The skill and plan elicitations differ structurally (artifact across compression variants vs plan across ref pairs); the shared core is small and is exactly what old D4's promotion posture says to extract once proven.
