## Decisions

- **D1 — Plan's identity re-keyed: the lead is a delivery manager of the goal, and artifacts demote from goal-conditions to risk-scaled guidance.** The plan command's role is to deliver the goal outcome by working with an agent team / subagents — teammates plan, the lead gives feedback on plans, approves them, and distributes work. The artifact set is guidance, scaled by **complexity, size, and cost of getting it wrong** — not a mandated invariant checklist. This dissolves the fixed-set (A) and unbounded-depth (B) defects under one principle rather than patching either separately. *(User-stated direction; scope of the non-negotiable floor under it deliberately not yet ruled — Q2.)* — `Confident`

- **D2 — The floor is a plan-the-plan gate, not a fixed artifact list.** No artifact is unconditionally mandatory. Each run, the lead proposes the artifact list + depth for THIS feature with risk reasoning (complexity, size, cost of getting it wrong); the user approves the proposal; the approved list becomes that run's own default-FAIL floor. (Chosen over "cards only" and "cards + architecture sign-off" fixed floors — those are expected to be the gate's common *outputs*, not standing mandates.) *As amended at review (HF-5): the gate fires on selection-scope runs only; a delta-scope run keeps its existing collapse — its deliverable is the confirmed delta card, already minimal.* — `Confident`
- **D3 — The gate's decision instrument: a simplest-execution ladder, translated from `patterns-code-minimalism`.** User-directed, object corrected at Q3: the ladder does NOT grade the plan documents' weight — it grades the **solution the plan commits the build to**: "is this plan going to lead to the simplest execution that meets the requirement, and act as guidance for the implement command." Document thinness is a consequence, not the test. Plan = guidance for implement (WHAT + binding constraints), prescription only where cost-of-getting-it-wrong demands; implement's own code-minimalism ladder continues the same discipline at build time — two ladders, one philosophy, two altitudes. Rung set under construction — Q4. — `Confident` (direction) / rungs pending

- **D4 — The simplest-execution ladder, ratified with rung 1 strict.** Per design element (component, entity, contract, mechanism, flow), stop at the first failing rung, before it enters the plan: **1 Required?** — no ratified requirement names it, it does not enter the plan; strict, no glue exception (glue is exactly builder's room under rung 5) · **2 Simpler shape?** — a design with fewer parts meeting the same requirement wins; no new abstraction, boring choice · **3 Already exists?** — baseline / existing system / installed dep carries it: extend or reference, never re-design · **4 Minimum now** — sized to the requirement as ratified, future-proofing only where retrofit is expensive · **5 Builder's room** — plan states WHAT + binding constraints; HOW stays open, prescribed only where cost-of-wrong is high (boundary contracts, persisted shapes, security); everything else is guidance implement may improve on. Implement's `patterns-code-minimalism` continues the discipline at build time. *As amended at review (all user-ruled as recommended):* **HF-1 floor carve-out** — rung-1 "required" reads ratified requirements AND asserted floor obligations (production-floor categories, compliance-module obligations, NFR-derived floor elements: security controls, error/data-loss handling, observability, a11y); strictness against speculation survives, the floor never enters via imagination — mirrors the sibling ladder's floor protection. **HF-3 read obligation** — rungs 2/3 claims ("simpler shape" / "already exists") are made only after reading the baselines + current state, never on trust — mirrors ponytail D10. **HF-6 rung scoping** — rungs 1/4/5 apply to every package element (TRs included); rungs 2/3 to design elements. **CF-4 kind-awareness** — rung 2's text names the kind test: simpler shape includes "no rich-domain modeling for operational/mechanical features." — `Confident`

- **D5 — Carrier and teeth, ratified as recommended.** New model-invoked skill `mochiko:patterns-plan-minimalism` — single source of the five rungs, sibling to `patterns-code-minimalism`; plan's authoring skills (entity modeling, api-contracts, technical-requirements, system-design) carry one pointer line each, never restating rungs. Fires generation-time twice: the lead's D2 proposal justifies every proposed artifact + major element rung-wise (the thing the user approves), and each producing seat's plan discloses its ladder stops. Graded review-time once: `review-plan-artifacts` re-keys from fixed-checklist completeness to (a) conformance against the approved proposal and (b) honesty of disclosed rung claims. Teeth: blocking at exactly one point — user approval of the proposal; grader findings advisory at package acceptance *(this sentence superseded by the HF-2 amendment below — two blocking points; only rung-honesty findings stay advisory)*. **Scope: the whole package** — analysis elements (TRs) answer to the ladder per D4's rung scoping (rungs 1/4/5; design elements take all five). *As amended at review (HF-2, user-ruled): teeth at TWO points — the proposal approval stays the upfront block, and `review-plan-artifacts`' conformance-to-approved-proposal check becomes a **blocking** grade: material divergence from the approved proposal (unproposed artifacts, element classes materially past approved depth) auto-FAILs the package before acceptance. Rung-honesty findings stay advisory. Closes the FEAT-002 failure mode — drift caught mechanically, never on the user re-reading the package.* — `Confident`

- **D6 — Two riders, ratified as recommended.** (a) **Architecture sign-off: conditional-but-reserved** — the architecture delta enters the package only when the approved proposal includes it; whenever present, sign-off stays user-reserved on a rendered diagram, unchanged. (b) **Product baselines stay invariant substrate** — the v0.66.0 first-plan-run seeding enforcement is NOT reopened; only the per-feature deltas ride the D2 proposal. Session blast radius deliberately kept inside plan's per-feature surface. *As amended at review (HF-4): when the approved proposal omits architecture, the tie-back machinery goes quiet consistently — no In-flight pointer added to repo `ARCHITECTURE.md`, no feature-close diff owed against an approved target ("no structural change → no update", matching `authoring-architecture`); no dangling close-time obligation.* — `Confident`

- **D7 — Success criterion for the rebuild (CF-3 fold, ruled inline).** The build's first-live-run probe is a **FEAT-002 re-derivation under the rebuilt plan** (kinako-side execution, mochiko-side watch). Criterion: every package element carries a surviving rung justification; expected shape directionally ~3–4 entities and ~600–900 package lines against today's 12 / 3,057 — a target for the watch, not a hard threshold. n=1 evidence basis explicitly accepted for shipping the build; the probe is what would falsify it. — `Confident`

- **CF-1 fold (D1/D2 load-bearing rationale, ruled inline).** Why set-demotion + identity re-key ship alongside the ladder rather than a ladder-only intervention: (a) the D2 gate is the ladder's upfront blocking site — ladder-only would be advisory culture, the same failure mode HF-2 closed with the second (conformance) blocking point; (b) F6's default-FAIL clause means today's lead cannot drop an artifact even when rung 1 says drop — without set-demotion the ladder has no jurisdiction over the set; (c) D1's delivery-manager identity is the user's product direction, stated independently of the FEAT-002 evidence, not an inference from n=1. The set-mandate's own cost even at honest depth: 8 files + seeding + a grader keyed to set-completeness is standing ceremony a launch-check feature never earns.
