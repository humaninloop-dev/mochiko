# Record — Validator scope & description verbosity

**Status:** accepted (2026-08-10)
**Opened:** 2026-08-10
**Topic:** the scope of the validator when it validates changes to skills, agents, and commands in the mochiko workflow — the user's read is that it forces descriptions to be much more verbose than they need to be; re-examine the validating strategy.

## Reframe (user, turn 2)

The concern is not the validator seat itself — it is that the system keeps **adding detail nobody priced**. The user wants two things enforced:
1. **Every token has a cost** — a standing cost discipline on primitive content.
2. **Measure, don't assume** — test whether frontier models (Opus, Fable) actually need detail-level procedural description, or only guardrails (goals, constraints, floors), before the detail is allowed to stay.

## Decisions

- **D1 — Measure-then-gate: benchmark first, cost gate second.** `Confident` (user adopted the recommendation).
  - **Statement:** The detail-level question is settled empirically, not by argument: (1) a **guardrails-vs-detail benchmark** — heavy skills get guardrails-only variants, both variants run against the same task on frontier models (Opus/Fable), outputs cold-graded; detail earns its place per evidence or dies. (2) After the benchmark rules, a **cost gate at authoring time** — per-class token budgets checked in the author≠grader audit, over-budget = FAIL until justified — becomes the standing ratchet-stopper.
  - **Rationale:** The user's core ask is "measure if the model really needs such detail." Repo precedent (`adversarial-review-generality` D2) already rules that contested detail questions get stress-tested, not argued. Option A (extend goal+harness to skills unmeasured) rejected because commands ≠ skills — skills carry craft procedure, the one place detail might genuinely pay; deleting it unmeasured risks losing real value. C alone rejected because it enforces a budget without answering the underlying question.
  - **Supersession seam** *(amended at review, C2)*: `skill-succinctness-strip`'s cuts already executed (v0.24.0–v0.28.0, −23.7%); this session's benchmark gates any **further** cuts — blind percentage bands are dead going forward, evidence decides. Disposition ruled at D8 part 1 as amended.

- **D2 — Benchmark substrate: the setup + specify skill clusters.** `Contested` (user redirected from the lead's 2-skill proposal to the full two-cluster set).
  - **Statement:** The benchmark runs over **all skills reachable from `/mochiko:setup` and `/mochiko:specify`**, not a 2-skill sample. Measured cluster (11 skills, bodies + references): setup — `analysis-iterative` (12.4 KB body / 56 KB dir) · `analysis-codebase` (9.5/36) · `authoring-constitution` (21.2/104) · `authoring-feature-map` (17.5/20) · `review-governance-intent` (15.1/16) · `validation-constitution` (13.6/28) · `testing-governance-injection` (7.0/8); specify adds — `authoring-requirements` (5.7/36) · `authoring-user-stories` (6.3/32) · `authoring-prototype` (11.4/12) · `review-specifications` (13.7/16). Shared: `analysis-iterative`, `authoring-feature-map`. Agent seats carrying them: principal-architect, validator, devils-advocate, requirements-analyst, product-manager, product-engineer.
  - **Rationale:** User prefers whole-pipeline-stage evidence over nature-sampling — a 2-skill sample answers "does detail pay in these two natures"; the cluster answers "can the setup and specify stages actually run guardrails-only," which is the decision that matters for a build. Cluster spans all four skill natures anyway (analysis, authoring, review/validation, testing), subsuming the sample's generalization logic.
  - **Consequence:** benchmark unit becomes the **stage run** (a full `/mochiko:setup` run, a full `/mochiko:specify` run) rather than the single-skill fixture; per-skill attribution comes from the per-seat artifacts each skill produces within the run.
  - **Amended at review (I1 + I2, user-accepted batch):** the benchmark gains two arms beyond the body-detail arm, because the original design never varied the surfaces the topic actually named:
    - **Description arm (I1):** slim-description variants for the cluster's skills — trigger phrases + graded MUST/SHOULD kept, elaboration dropped — with an **invocation-fire-rate check** across replicates (did each skill fire when its moment came). Without this arm the benchmark structurally cannot answer "do frontier models need verbose descriptions," which was the user's opening complaint.
    - **Agent-description arm (I2):** example-blocks-removed variants of the six cluster agent descriptions (agents are the largest verbosity mass — up to 2,440 chars, example blocks the bulk, F2) with the same fire/route reliability check. Exempting agents from measure-first would contradict the session's own principle.

- **D3 — Model-played principal for run comparability.** `Confident` (user adopted the recommendation after a plain-language walkthrough).
  - **Statement:** Both variants' stage runs are driven by a **model-played principal**: a subagent answering the command's questions from a frozen persona + project-facts card. The card is written with deliberate vagueness — including at least two planted "I don't know" zones — so the synthetic user does not answer more cleanly than a real one. Same card serves every run of both variants; replicates are therefore possible (≥2 per variant, per the `adversarial-review-generality` D3 pinned-parameters precedent).
  - **Rationale:** Setup and specify are interactive; divergent user answers between runs contaminate the variant comparison. An answer sheet (A) breaks when the guardrails variant asks unpredicted questions; a live human driver (B) is primed on run 2 and makes replicates impractical. C is the only option under which the decision rule's replicate requirement is enforceable.
  - **Known weakness, accepted:** a synthetic principal under-represents real-user messiness; partially mitigated by the planted-vagueness requirement on the card.

- **D4 — The guardrails-only cut line.** `Confident` (user agreed with the proposed line; third consecutive unelaborated adoption — streak flagged at Q6 per doctrine).
  - **Statement:** A guardrails-only skill variant **keeps**: goal / output contract · non-waivable floor · anti-patterns and rejections · hard reference data under `references/` (on-demand, not always-read). It **drops**: step-by-step procedure (the model sequences itself) · worked examples in the body · content restating what the command or CLAUDE.md already carries. **Edge-case playbooks** ("if brownfield and no CI, then…") are the contested middle: the guardrails variant drops them, and they are precisely what the benchmark adjudicates — if guardrails runs re-make the old mistakes those playbooks encode, the verdict is "detail pays here" and they return, named.
  - **Rationale:** The keep-set is exactly what a frontier model cannot infer (the bar, the floor, the domain data); the drop-set is what it can (sequencing, style, obvious craft). The middle row is genuinely uncertain — which is why it is the benchmark's cargo rather than a ruling either way.

- **D5 — Grading: neutral rubric, LLM-as-judge.** `Confident` (user-ruled at a recommendation-free fork after the streak flag — options steelmanned, no lead recommendation).
  - **Statement:** Benchmark outputs are scored by an **LLM judge against a neutral outcome rubric authored fresh for the benchmark** by a party that authored neither variant. The rubric is outcome-keyed per artifact class ("is every principle enforceable," "would a builder be blocked," "are acceptance criteria measurable"), deliberately blind to both skills' internals, and yields a numeric score per artifact — enabling the pre-committed decision rule to bite on scores rather than on a judgment call. Judge seat is independent (never the author of either variant or the rubric-scored artifact).
  - **Rationale (user's):** a rubric gives a way to *score* — LLM-as-judge over a fixed rubric. Structural benefit over the alternatives: coupling to the shipped skills' vocabulary is impossible by construction (option A's risk), and numeric scoring keeps the threshold enforceable (option C's missing piece). Accepted cost: rubric authoring is real work, and a fresh rubric may be less battle-tested than the existing checklists — mitigated by keeping existing checklists as a secondary floor-conformance check, never the comparator.

- **D6 — Decision rule: 10% threshold, cost-aggressive.** `Confident` (user moved the lead's 5% proposal to 10% — deliberate cost-aggressive stance).
  - **Statement** *(run arithmetic reconciled at verify, V2, with D2's three arms)*: arms run as **separate variants** for attribution — baseline (full) · body-guardrails · slim-descriptions · slim-agent-descriptions = 4 variants × 2 commands × ≥2 replicates = **16+ stage runs**. Combining cuts into one variant is rejected: it defeats per-arm attribution (which cut moved the score would be unknowable). Cost note: the description and agent arms reuse the baseline *bodies*, so variant authoring cost concentrates in the body arm; run cost scales linearly and is priced in the cost ledger. Per-variant score = mean across replicates of the LLM-judge rubric score. Verdicts per command stage (each cut arm judged against baseline independently):
    - Guardrails within **10%** of the full variant (or better) AND zero floor violations — **detail dies** for that stage's cluster; guardrails variants ship.
    - Guardrails loses by **>10%** — the judge names which rubric rows lost; a **diagnostic trace-back pass** (amended at review, I4) then maps losing rows to the specific dropped sections: a separate seat, sighted on both variants' diffs, attributes each losing row to dropped content; only sections so attributed return. Where the mapping is genuinely unclear, the fallback is all-or-nothing for that stage. (The scoring rubric itself stays blind per D5 — blindness holds for scoring, sight is granted only to the post-hoc diagnostic.)
    - Any floor violation in any guardrails replicate — automatic "detail pays" for that floor's section, score notwithstanding.
    - **Noise guard:** same-variant replicate spread exceeding the variant gap = noise; one more replicate pair before any verdict.
    - **Cost ledger:** token spend per run reported alongside scores — the quality/cost trade is priced explicitly, never hidden.
  - **Rationale:** 10% encodes the user's stance that a visible-but-modest quality dip is worth a large token cut ("every token and every word has a cost"). Floor violations stay absolute — the threshold buys leniency on judgment quality, never on the non-waivable floor.

- **D7 — Cost gate: empirical budgets enforced in the existing audit.** `Confident` (user confirmed the proposal).
  - **Statement:** After the benchmark rules, per-class token budgets become a standing check:
    - **Budgets set empirically** — the benchmark's winning variant weight per class + 25% headroom is the budget baseline; no number invented today.
    - **Enforcement point** — the existing author≠grader audit gains one deterministic pre-assert: a **character count** against the class budget *(amended at review, I3: cap and budgets are pinned in **chars**, and the measurement must count chars — not `wc -c`, whose byte counts over-reject unicode-bearing descriptions that are under the char cap)*. Over budget = FAIL, with a named exemption path (overage justified in the audit brief; the grader rules whether the justification holds). No new seats, no new ceremony.
    - **Scope** — skill bodies · skill frontmatter descriptions (1,536-char delivery cap already binding) · agent descriptions · commands (budget ratifies the v8 goal+harness status quo). `references/` exempt as on-demand data, benchmark permitting.
  - **Near-cap watch note** *(amended at review, C1 — the original "unconditional defect" clause struck: no description exceeds the cap; the 1,544 figure was a label-inclusive line count; wording repaired at verify, V1)*: five skill descriptions sit within ~30 chars of the 1,536 cap (F1 as corrected); any growth truncates. The description benchmark arm covers only the in-cluster one (`authoring-constitution`); the other four sit outside the setup+specify substrate (open thread 1). The char-count cost gate catches over-cap growth on all five regardless of benchmark scope. No unconditional fix ships.
  - **Rationale:** the gate is the ratchet-stopper D1 called for; anchoring budgets to measured winners keeps the gate honest to the benchmark instead of to taste; riding the existing audit keeps enforcement cost near zero.

- **D8 — Prior-doctrine supersession + execution venue.** `Confident` (part 1 user-accepted; part 2 user adopted the recommendation after a plain-language walkthrough).
  - **Statement (1 — supersession, as amended at review per C2):** `skill-succinctness-strip` (2026-07-25) **already executed** (v0.24.0–v0.28.0, −23.7% across 27 skills); there is no pending execution to gate. What this session supersedes is narrower: its calibration-band method (30–70% / 10–40% percentage cuts) is dead **for any future pass** — further cuts happen only through the benchmark's evidence, never as blind percentages. Its **measure-first** principle and **true-reductions-only** accounting survive, absorbed as constraints on authoring the guardrails variants. Landing: a DECISIONS.md annotation on that row stating the method supersession — worded against the row's "executed" status, not contradicting it.
  - **Statement (2 — venue):** this session closes properly first (cold review → dispositions → acceptance → landing). The benchmark then starts **immediately in this same worktree** as its own piece of work, appetite permitting; the BACKLOG item is written cold-runnable regardless, so the work survives a stop after landing. Motivation: the `adversarial-review-generality` benchmark item (2026-08-04) has sat unrun — a landed-but-dormant item is the known failure mode this venue choice hedges against.
