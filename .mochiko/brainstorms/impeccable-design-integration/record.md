## Topic

The user's driver: *"incorporate part of impeccable into the product design skill and part of its workflow when creating design — how do we do that well."*

[Impeccable](https://github.com/pbakaus/impeccable) (Paul Bakaus, Apache 2.0) is a frontend-design skill for AI coding agents: one user-invoked skill, 24 commands, a Rust engine binary with 61 deterministic anti-pattern detector rules, edit-time hooks, and a live browser-iteration mode. This session decides which parts of it mochiko adopts, into which primitive(s), and how its design workflow composes with mochiko's pipeline when a feature creates UI — without breaking mochiko's non-negotiables.

Goal line: one hardened decision record naming (a) the adoption mechanism per part, (b) the mochiko home for each adopted part, (c) how the design workflow fires inside specify/implement, and (d) what stays out and why.

## Constraints carried in

- **GI-019 (kernel-class tooling by recorded ruling only; never gates pipeline progress, never dispatches, never holds judgment skills own).** Impeccable's engine is kernel-class by mochiko's definition. Advisory post-hoc checkers used as optional exit-code signals are *not* kernel-class — `impeccable detect` fits that carve as an advisory signal; its `PreToolUse` write-block does not, absent a ruling.
- **GI-020 (clone-only install; `mochiko-cli` the one required dependency).** A second required binary is a governance event, not a build detail.
- **Five-axis conventions** — #4 persona carries judgment, skill carries procedure, a persona contains no trace of any workflow; #5 producer↔validator pairing; #3 model-invoked description grammar (≤1,536 chars — measured at build, item 2/3).
- **Author ≠ grader; landing ritual; strips** for any shipped-primitive edit.
- **Licensing** — Impeccable is Apache 2.0; the posture is ruled at D14, not assumed here.
- **Production-only target** (PO-D1–D7) with the **low/high depth level and breadth invariant** (adaptive-depth D1–D8): customer-facing product apps; frontend shelf is Tier-I roadmap work; the design surface's depth behavior is ruled at D13.
- **Accessibility standard of record** — the `a11y` compliance module (legal-mandate, unwaivable) where attached, else the Essential Floor line carried by `patterns-code-minimalism`; ruled at D11 — the design surface routes to it, never restates it.

## Decisions (D)

### D1 — Scope: one design track spanning both pipeline moments — specify's UX-prototype stage and implement's UI cycles

**Statement.** Impeccable is adopted as a single design track that bites at the two places a *feature* makes UI (F11 i–ii): the specify UX-prototype stage (`product-designer` + `authoring-prototype`) and implement's UI cycle execution (staff-engineer builds, qa-engineer / devils-advocate verify). Not implement-only; not specify-only. The third moment F11 names — the architecture desk's frontend shelf — is not a feature moment; its relationship to this track is ruled at D12.

**Rationale.** Impeccable's own flow is shape → build → finish (F7): `shape` plans before code, `craft-floor` binds at the edit, `critique`/`audit`/`polish` close. That maps 1:1 onto specify (shape) → implement (build + finish). Choosing one moment would leave the other design-blind: a design-aware prototype built by a design-blind implement, or the reverse. The low-fidelity ruling at specify (F9, "pixels deliberately rough") is not reopened by D1 — it constrains *which* Impeccable parts land at specify (shape, modes, product truth) versus implement (craft floor, finish passes); D2+ allocate.

**Confidence.** `Confident` — user chose the recommended option without hesitation (Q1).

### D2 — Mechanism: port, zero dependency — mochiko-owned prose, attributed; no Impeccable plugin, binary, or shell-out, ever

**Statement.** Every adopted part of Impeccable enters as mochiko-authored skill/persona content (rewritten to mochiko's persona-carries-judgment / skill-carries-procedure split, attribution per D14). Mochiko never depends on, probes for, or shells to the Impeccable plugin or the `impeccable` binary — not as a requirement, not as an optional advisory signal. A run behaves identically whether Impeccable is installed or not. The 61 deterministic detector rules are **not** consumed as a tool; what survives of them survives as prose or as `**TEST:**` examples (D10).

**Licensing premise (stated so it can be graded — R02).** The port re-expresses design judgment in mochiko's own form and voice; it is a derivative work of an Apache-2.0 source, not a verbatim copy. Where any passage is nonetheless carried verbatim it is marked and attributed in place. The posture that makes this shippable under mochiko's declared license is ruled at D14.

**Rationale.** The user's driver: no Impeccable dependency of any kind. Governance agrees: GI-020 names `mochiko-cli` as the one required binary, and an optional third-party binary that downloads itself on first run is a supply-chain surface mochiko would carry without owning. Skills own judgment (non-negotiables) — porting makes the design judgment gradeable by mochiko's own validators and evolvable under its strip/audit ritual. Drift from upstream is accepted as a consequence and **not** watched: D10 rules no upstream tracking; the revisit trigger is mochiko's own evidence. Adopt-first disclosure: the shelf candidate (`impeccable detect`, off-the-shelf, exit-code advisory) was named and **rejected in writing** on the dependency-free driver, not on capability.

**Rejected roads.** Compose whole (axis #1 conflict, GI-020 event, artifact collision with F12). Hybrid port + optional detector (recommended by the lead; rejected — user wants no Impeccable presence at all). **Coexist-and-hand-off** — adopt nothing, keep both plugins installed, run Impeccable between mochiko runs (R20, raised at review): considered and **foreclosed by the driver** — the user asked to incorporate, not to document a hand-off; recorded so the road is visible, not reopened.

**Confidence.** `Contested` — the lead recommended the hybrid; the user ruled port-only deliberately.

### D3 — Home: no new persona — the ported judgment lands on the product-design persona, the procedure as skills and lens sections on the seats that already touch UI; the `ui-designer` Design track is superseded

**Statement.** The design-director judgment (Impeccable's POV: the brief wins · refinement preserves, redesign replaces · visual authority is evidence · mode chosen per surface) lands on the `product-designer` persona (renamed at D4). Procedure lands as: a **design-direction** model-invoked skill on `product-designer` at specify (modes + design laws + the `shape` checklist, feeding the Screens & Flows section); a **craft-floor** model-invoked skill loaded by `staff-engineer` immediately before any UI edit at implement; a **critique lens section** inside `testing-gap-finding` (the seat and pass it already rides — `devils-advocate` at final validation); the **audit lens, split by form (V1):** its pass/fail legs (the accessibility standard of record, the measurable asserts, responsive at the surface's declared viewports) are authored as `**TEST:**` cases on UX-bearing cards by `qa-engineer` at design time and executed by `testing-end-user` — declared tasks, the executor's own boundary; its finding-originating legs (slop tells, `polish` baseline alignment, `harden`, `optimize`) become a **design-audit review skill**, working name `review-design-audit`, in the `review-code-minimalism` form — a lens run by the verification seat, advisory findings block, scope the design-audit lens only — declared on `qa-engineer`. No `ui-designer` persona; the BACKLOG "Design track" item and its `analysis-screenshot` / `authoring-design-system` / `patterns-flow-mapping` / `patterns-interface-design` cluster close as superseded by this ruling. Roster stays at 10; new skills: **three** — two patterns skills and one review skill (R08's ladder killed `review-design-finish`; V1's ladder rung 2 then failed for the audit half — a section inside an executor breaks the executor's boundary — so the review-family sibling is the surviving simplest shape; disclosed in the build surface).

**Craft-floor is procedure, argued (R11).** Axis #4 asks where the *choice* is made. Every taste choice the floor could otherwise make — register (`bolder` / `quieter` / `distill`), visual world, type and color intent, motion stance — is made upstream, once, by `product-designer` in the surface's direction contract. Craft-floor carries that contract's already-made choices plus the absolute bans and the reflexes, all of them checkable against the edit in front of the seat: "no gray text on colored backgrounds", "no bounce easing", "honor the declared type scale". A seat with no design judgment can execute it because it decides nothing; where it would have to decide, it stops and the contract is the answer. That is procedure. The falsifier for this classification is named in Evidence honesty (a).

**Accessibility placement (amended at review, R01 → D11).** Accessibility is absent from the design-direction skill's *taste* content by design (F5's lesson) — it is never absent from the build. Craft-floor keeps the code-minimalism floor line in view; the audit lens verifies the standard of record; D11 rules precedence.

**Rationale.** Five-axis #4: judgment on a persona that already owns the UX surface, procedure as skills, no workflow trace in the persona. Impeccable itself is one skill with playbooks, not a designer agent (F1) — the port keeps that shape. A dedicated designer seat would add a run seat per UI feature and leave the `product-engineer` overlap unresolved; two design judgments (option 3) can disagree with no arbiter.

**Confidence.** `Confident` — user chose the recommended option; skill names are working names, minted at build.

### D5 — A design baseline in the product store: `.mochiko/product/design/`, two parts (design truth · design system); one writer; template-borne grammar; no derived index; mode and direction contract stay per surface in the spec

**Statement.** Mochiko gains a product baseline for design at `.mochiko/product/design/` beside `architecture/`, a `home` in the migration log like its siblings. Two parts: **design truth** — brand commitments, voice, design principles, an evidence fence (no claims, testimonials, or benchmarks invented where evidence is absent), and a **pointer** to the accessibility standard of record (D11 — never a restated floor) — durable and product-wide; **design system** — tokens, type scale, color, spacing, components, motion rules — evolving with code. **Writer (R04):** `product-designer` holds the pen on the store at every moment; the setup leg (D6) and the landing fold (D7) both write *through that seat* as graded writes, never around it. **Grammar (R04):** template-borne — the home's producer and checklist views rendered by `mochiko-cli template`, with ordered headings enforced by the artifact gate; no authoring skill is minted (plan-minimalism rung 2: a template is the simpler shape for a two-part record). **Derived index: declined** — two files under one home, nothing to index; `ARCHITECTURE.md` exists because the architecture store is many files. Baseline edits travel **only through the graded paths: the setup leg's producer + validator write and the unconditional scaffold at setup (D6), `baseline-delta.md` at build time, and the landing fold at feature close** (R13/W3). The sufficiency check reads it as it reads the other baselines (D13 names the clause). **Mode (Persuade / Operate / Read / Experience) and the direction contract are per surface** and live in the feature spec's Screens & Flows section — never in the product record. Landing-time built-vs-signed grading rides the same fold the architecture store uses (`As-built:` / `Drift:`).

**Rationale.** `authoring-prototype` step 2 "discovers an existing design system" with nothing durable to find (F9/F14); craft-floor at implement needs tokens to honor; brand commitments are unfindable at implement today (F12). Impeccable separates PRODUCT.md (truth) from DESIGN.md (system) from the surface brief (mode + direction) precisely so surface-level direction never contaminates product truth (F4, `CLAUDE.md` Modes §) — the two-part-plus-per-surface split carries that. Riding the product-baseline machinery (graded deltas, sufficiency clause, landing fold) costs no new mechanism. Audience and purpose already live in the intent stage and the product desk (F12) — the design baseline points at them, never restates them (GI-017 spirit).

**Rejected.** Design-system-only (brand voice stays unfindable at implement); nothing durable (every feature re-derives the system, n=0 evidence either way but the discovery step is already written to expect one); a store with its own authoring skill and derived index (R08/R04 — the architecture store's shape, unpaid-for by two files).

**Confidence.** `Confident` — user ruled "as recommended" and broadened toward setup (→ D6); R04/R13 folds user-ruled in the batch. Exact file split inside `design/` (one file vs two) is a build-time call under the home's template.

### D6 — Setup gains a bounded product-truth leg (Impeccable's `init` at product level): platform + design truth asked once, only for material gaps; brownfield seeds the design system from code

**Statement.** `/mochiko:setup` gains one leg that writes the design-truth part of the D5 baseline through the `product-designer` seat: **platform** (one validated value — `web` / `ios` / `android` / `adaptive` / `desktop`; an unrecognized value warns and never silently defaults), **brand commitments and voice**, **design principles**, the **pointer to the accessibility standard of record** (D11 — the leg asks nothing about a11y itself; the compliance module or the floor line already holds it), and the **evidence fence** (claims, testimonials, benchmarks, customers, pricing are never invented where evidence is absent). It asks only material gaps — what the repo, README, and existing brand assets cannot answer. It does **not** ask audience or purpose; those live in the product desk and the leg points there. **Seat wiring (V2):** the *asking* is the lead's own inline interrogation — `setup.interrogation-inline` (`class: must`, kind: duty) is honored, no seat interrogates; the *write* of the design-truth part is dispatched to the `product-designer` seat as a producer under the sound loop (producer on a lead-approved plan · non-author validator · user ratifies), the same pattern setup already runs for its governance surfaces — so D5's single-writer line holds at setup. `setup.baselines-bootstrap` gains a **third arm**: the design baseline's truth part is interrogation-sourced on every path, its system part is code-seeded on brownfield and scaffold on greenfield. The design home is **scaffolded unconditionally** at setup, the `setup.store-scaffold-unconditional` pattern — the store's birth moment is setup, never a feature run. Brownfield: `analysis-codebase` gains a design-system detection leg (UI framework · CSS system · fonts · token files · component library) that seeds the design-system part and feeds the frontend shelf's facts when that shelf lands (D12); greenfield: the system part stays a scaffold until the first UX-bearing feature lands (D7).
